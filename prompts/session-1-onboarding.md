# 세션 1 프롬프트 — 하네스 검증 + 코드베이스 진단 (개정판)

/init로 생성된 프로젝트 지식이 CLAUDE.md와 docs/ARCHITECTURE.md에 이미 반영되어 있다.
따라서 이 세션은 "처음부터 파악"이 아니라 "검증 + 빈칸 채우기 + 부채 진단"이다.
아래 전체를 Claude Code에 붙여넣는다. (Plan Mode로 시작 권장: Shift+Tab)

---

이 세션의 목표: (1) 하네스가 이 환경에서 실제로 동작하는지 검증, (2) 문서와 실제 코드의 대조,
(3) 기술 부채 진단. **이 세션에서는 제품 코드를 한 줄도 수정하지 않는다.**
산출물은 문서와 하네스 설정 수정뿐이다.

## 1단계 — 하네스 스모크 테스트
1. CLAUDE.md와 .claude/settings.json을 읽고 요약해라. 모순으로 보이는 규칙이 있으면 지금 물어라.
2. Rider MCP 연결 확인: get_run_configurations 같은 가벼운 툴을 P1 솔루션과 Server 솔루션
   양쪽에 projectPath를 명시해 호출하고 응답을 확인해라.
3. PreToolUse 훅 테스트: 임시 디렉토리를 만들고 `rm -rf {임시경로}`를 시도해서 차단되는지
   확인해라. 차단되지 않으면 이 OS/셸 환경에 맞게 settings.json을 수정하고 재테스트해라.
   (훅은 stdin으로 JSON을 받는 공식 스펙 기준으로 작성되어 있다.)

## 2단계 — 문서 대 실제 코드 대조 (읽기 전용)
CLAUDE.md의 도구 라우팅 규칙을 따라라 (analyze_calls / search_symbol 우선, grep 최소화).
1. CLAUDE.md와 docs/ARCHITECTURE.md의 서술이 실제 코드와 일치하는지 검증해라.
   자동 생성된 문서라 부정확한 부분이 있을 수 있다. 어긋난 곳은 목록으로 보고해라
   (문서 수정은 내 승인 후).
2. UserDB / GameDB의 스키마(주요 테이블과 용도)를 읽기 전용 연결로 파악해서
   ARCHITECTURE.md의 "미작성" 섹션 채울 내용을 준비해라.
3. 클라(P1) 폴더 구조를 레이어 분리 관점에서 훑어라. 아래 3단계의 진단 재료다.

## 3단계 — 산출물 작성
1. **docs/ARCHITECTURE.md 보강**: "미작성" 섹션 3개 항목을 채워라 (스키마, 클라 폴더 현황,
   프로토콜-핸들러 매핑). as-is 기준으로.
2. **docs/tech-debt.md**: 진단 리포트. 아래 항목들을 실제 코드에서 확인·구체화하고,
   각 항목에 [심각도: 상/중/하][수정 난이도: 상/중/하], 왜 문제인지 한 줄,
   어떤 방향으로 고칠지 한 줄. 고치지는 마라.
   - 관심사→레이어 분리가 안 된 클라 폴더 계층
   - BP 위젯에 있는 로직 (C++ 이관 대상 목록화)
   - 캐릭터 클래스에 뭉친 기능 (컴포넌트 분리 후보 목록화)
   - AuthServer의 eslint 미연결 (설치만 되고 flat config·lint 스크립트 없음)
   - GameServer 접속 문자열이 config.h 컴파일 타임 상수 (환경변수/설정파일 대비 트레이드오프 평가)
   - 그 외 탐색 중 발견한 항목
3. **CLAUDE.md 어긋남 보고**: 2단계 1에서 찾은 목록. 수정은 내 승인 후에 한다.

## 4단계 — 마무리
1. 다음 세션(검증 인프라)을 위해, GoogleTest를 붙이기 좋은 "입력 없는 순수 로직" 후보를
   3개 이내로 제안해라. Server.sln이 VS 솔루션임을 전제로 GoogleTest 통합 방식
   (NuGet vs 서브프로젝트 추가 vs 기타)의 추천안과 근거도 함께.
2. DummyClient를 검증 루프에서 어떻게 활용할 수 있을지 의견을 내라
   (수동 하네스 → 반자동 스모크로 승격 가능성).
3. 나에게 확인이 필요한 질문 목록을 만들어라.
