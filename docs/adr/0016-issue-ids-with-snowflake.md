# 캐릭터 ID와 아이템 UID는 게임 서버가 Snowflake 발급기 하나로 발급한다

캐릭터 ID와 아이템 UID는 DB가 아니라 게임 서버의 Snowflake 발급기(`Server/GameServer/Utils/SnowflakeIdGenerator`)가
발급한다. 두 ID는 발급기 하나를 같이 쓴다. 아이템은 룸 스레드가 메모리에서 먼저 만들고 DB에는 나중에 저장하므로,
행을 넣기 전에 서버가 ID를 알아야 한다. 노드가 늘어도 DB에 묻지 않고 겹치지 않는 방식이 Snowflake다.
2026년 10월 20일 GameDB 재구성(#247)에서 정했다.

## ID의 모양

| 비트 | 내용 |
|---|---|
| 1 | 부호. 항상 0 |
| 41 | 기준 시각 `2026-01-01T00:00:00Z`부터 지난 밀리초 |
| 10 | 노드 번호(0~1023). 환경 변수 `P1_SERVER_NODE_ID` |
| 12 | 같은 밀리초 안의 순번(0~4095) |

- 41비트 밀리초는 약 69년이다. 2095년까지 쓴다
- 노드 하나가 1밀리초에 4096개, 1초에 약 400만 개를 발급한다
- 같은 노드가 발급한 ID는 발급 순서대로 커진다

## 발급 규칙

**시계를 기다리지 않는다.** 발급기는 마지막으로 발급한 ID 하나를 원자 변수에 두고 CAS로 바꾼다. 락이 없다.
— 발급기는 여러 룸 스레드가 부른다. 룸 스레드가 시계를 기다리면 그 룸의 모든 잡이 함께 멈춘다.

**논리 시계를 쓴다.** 현재 시각이 마지막으로 쓴 시각보다 크지 않으면 마지막 시각을 그대로 쓰고 순번을 올린다.
순번이 넘치면 마지막 시각을 1밀리초 앞당긴다. 시계가 그 시각을 넘어서면 다시 시계를 따른다.
— 시계가 뒤로 가도(NTP 보정) ID는 줄지 않는다. 한 밀리초에 4096개를 넘게 발급해도 실패하지 않는다.

**부팅할 때 이 노드가 발급한 ID의 최댓값 뒤에서 시작한다.** `StartAfter`가 그 값을 받는다.
— 앞당긴 시각이 실제 시계보다 앞선 채로 서버가 내려갔다가 바로 다시 뜨거나, 시계가 뒤로 간 채로 다시 뜨면 이미
발급한 ID를 또 발급한다. 시계만으로는 막지 못한다.

**노드 번호는 Debug 빌드에서만 기본값(0)이 있다.** Release 빌드는 값이 없으면 기동을 거절한다. 0~1023이 아니거나
정수가 아닌 값은 두 빌드 모두 거절한다.
— 운영 서버 두 대가 같은 번호로 뜨면 두 서버의 ID가 겹친다. 개발 머신에는 노드가 하나뿐이다.

## 검토한 대안

- **부팅 때 DB의 최댓값을 읽어 메모리 카운터로 센다.** 옛 아이템 UID(`GNextItemUID`)가 이 방식이다. 서버가 한 대일
  때는 가장 단순하다. 서버가 두 대가 되면 두 서버가 같은 최댓값에서 세기 시작해 바로 겹친다. 노드마다 구간을
  나눠 주면 결국 노드 번호가 필요하고, 구간이 차면 사람이 다시 나눠야 한다.
- **`SEQUENCE`에서 범위를 예약해 메모리에서 나눠 준다.** 노드 번호가 없어도 겹치지 않는다. 하지만 범위가 바닥날
  때마다 DB 왕복이 생기고, 그 왕복을 룸 스레드에서 할 수 없으므로 DB 큐를 거치는 미리 받기가 필요하다. DB가 느리면
  범위가 바닥나 아이템을 만들지 못한다. ID를 만드는 데 DB가 살아 있어야 한다.
- **`IDENTITY`로 DB가 행을 넣을 때 발급한다.** 캐릭터 생성처럼 곧바로 행을 넣는 경로에는 맞는다. 아이템은 메모리에서
  만들고 접속 종료 때 한꺼번에 저장하므로, 저장 전까지 UID가 없다. 캐릭터만 `IDENTITY`로 두면 발급 방식이 둘이 되고
  둘 다 지켜야 한다.

## 결과

- `GameDB`의 `Character.CharacterId`와 `Item.ItemUid`에는 `IDENTITY`가 없다. 서버가 넣는다
- 발급기를 캐릭터 생성과 아이템 생성 경로에 연결하고 부팅 때 `StartAfter`를 부르는 일은 계정과 캐릭터 DAO 티켓(#256)이
  한다. 그때까지 아이템 UID는 옛 메모리 카운터가 발급한다
  - 2026-10-21 덧붙임: #256이 연결했다. 발급기는 `GIdGenerator`이고 `main`이 설정 검사 뒤에 만든다. 부팅할 때
    `IssuedIdDAO::GetLastIssuedId`가 `Character`와 `Item`에서 이 노드의 최댓값을 읽어 `StartAfter`에 넘긴다.
    옛 메모리 카운터(`GNextItemUID`)는 지웠고, 소모품과 기타 아이템도 빈 칸에 놓일 때 UID를 받는다
- 서버를 더할 때마다 사람이 노드 번호를 나눠 준다. 번호를 어디에 기록할지는 서버가 둘이 되는 날 정한다
- ID에서 발급 시각을 읽을 수 있다. 아이템 UID는 클라이언트에 가므로 아이템을 언제 얻었는지가 드러난다. 지금은 숨길
  이유가 없다
- 소모품과 기타 아이템도 UID를 받는다. 묶음을 나누고 합칠 때마다 UID를 쓰지만 노드당 초당 400만 개면 모자라지 않는다

## 틀렸다는 신호

- 게임 서버 노드가 1024개를 넘는다
- 노드 번호를 손으로 나눠 주다가 두 서버가 같은 번호로 뜬다. 이때는 노드 번호를 사람이 아니라 기동 시점의 임대(Redis
  키 등)로 받는 방식을 검토한다
