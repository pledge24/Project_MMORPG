# 서버 내비게이션은 추출한 충돌 형상으로 직접 빌드한 Detour navmesh를 쓴다

에디터가 레벨의 충돌 형상을 추출하고, 별도 도구(`Tools/NavBuilder/`)가 독립 recastnavigation으로 맵마다 navmesh를 빌드한다.
게임 서버는 같은 recastnavigation의 Detour로 그 navmesh를 읽어 길찾기, 벽 통과 검증, 바닥 높이를 질의한다. 별도의 충돌
격자는 두지 않는다. 2026년 10월 29일 맵 데이터 추출 작업의 설계에서 정했다.

## 무엇을 질의하는가

서버가 지형에 묻는 질문은 넷이다. 길찾기, 이동이 벽을 통과했는지, 바닥 높이, 투사체의 시야다. Detour는 앞의 셋에 답한다.
시야는 「걸을 수 없는 곳은 시야도 막는다」로 근사한다. 이 근사는 낮은 울타리 너머나 구덩이 건너편을 쏘는 경우에만 틀린다.
그런 원거리 공격이 기획에 들어오면 그때 충돌 표현을 더한다.

높이를 알게 되므로 이동 검증과 클라이언트 이동 보정이 Z를 다룬다.

## 검토한 대안

- **UE가 빌드한 NavMesh 타일을 꺼내 서버 Detour에 넣는다.** 추출이 가장 짧다. 하지만 UE는 Detour를 수정해서 쓰므로 직렬화
  형식이 엔진 버전에 묶인다. 엔진을 올릴 때마다 서버가 깨질 수 있다.
- **높이와 통행 가능 여부를 격자로 추출하고 서버가 A\*로 길을 찾는다.** 지금의 평평한 섬에서는 가장 가볍다. 하지만 건물과
  장애물이 늘면 Detour로 바꿔야 하고, 그때 형상 추출과 서버 질의 엔진을 모두 다시 만든다. 장애물을 더할 수 있는 구조를 지금
  만드는 비용과 나중에 바꾸는 비용을 비교해 지금 만드는 쪽을 골랐다.
- **NavMesh와 충돌 격자를 둘 다 둔다.** 정밀한 시야 판정까지 답한다. 하지만 지금 기획에 시야를 정밀하게 따질 공격이 없다.
- **서버가 기동할 때 navmesh를 빌드한다.** 바이너리 형식을 신경 쓸 필요가 없다. 맵이 커지면 기동이 느려지고, 빌드 결과를
  git diff로 볼 수 없어 별도 도구로 미리 빌드하는 쪽을 골랐다.

## 결과

- 빌드 도구와 서버는 같은 recastnavigation 소스를 링크한다. `.navmesh` 파일 머리에 형식 버전과 에이전트 설정의 해시를 넣고,
  서버는 어긋나면 기동을 거부한다
- 같은 입력이면 같은 바이트를 낸다. 레벨이 바뀌지 않았는데 navmesh가 바뀌면 diff로 드러난다
- 에이전트 설정(반경, 높이, 경사, 단차)은 클라이언트 캡슐에서 가져와 추출 데이터에 싣는다
- UE에서 서버의 navmesh를 눈으로 확인할 수단이 필요하다. 빌드 도구가 폴리곤을 JSON으로도 내보내고, 에디터가 레벨 위에 겹쳐 그린다
- UE 클라이언트는 내비게이션을 쓰지 않는다. 몬스터는 서버가 알린 위치를 따라갈 뿐이다
