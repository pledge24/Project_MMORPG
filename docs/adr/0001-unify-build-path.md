# 빌드를 터미널 한 경로로 통일한다

클라이언트와 서버의 빌드를 모두 터미널에서 돌리고 종료 코드로 판정한다. **빌드에 Rider MCP를
쓰지 않는다.** 클라이언트는 `Build.bat`, 서버는 `MSBuild`다. 이 결정은 CLAUDE.md 「도구 라우팅」이
2026년 9월 16일까지 유지하던 "UBT/Build.bat/MSBuild를 터미널로 직접 돌리지 않는다"를 뒤집는다.

## 왜 하나로 모으는가

**클라이언트 경로는 하나가 아니었다.** `build_solution_start`는 에디터가 연결되어 있으면 Live
Coding 컴파일로, 닫혀 있으면 UBT로 갈린다. 툴은 그 전환을 알리지 않는다. 두 경로는 결과가 다르다.
Live Coding은 헤더와 `UFUNCTION` 같은 리플렉션 변경을 반영하지 못하고, 패치를
`Binaries/Win64/UnrealEditor-P1.patch_N.*`로 따로 내보내며 `UnrealEditor-P1.dll`을 갱신하지
않는다. 2026년 9월 16일에 Live Coding으로만 검증한 코드를 커밋할 뻔했고, 메인 DLL의 PDB에서 새
심볼이 0건인 것을 보고서야 알아챘다.

**클라이언트의 성공 판정도 틀렸다.** 같은 Rider 세션 안에서 대조 실험으로 범위를 좁혔다.

| 대상 | 빌드 결과 | `problems` | `buildIsSuccess` |
|---|---|---|---|
| `Server` (MSBuild) | 성공 | 비어 있음 | `true` |
| `P1` (UBT) | 성공 | 비어 있음 | `false` |
| `P1` (UBT) | 실패 | 파일·줄·열까지 정확 | `false` |

Rider 내부에는 판정이 존재한다. 백엔드 로그가 빌드마다 `Fire build result Kind: Successful`을
남기고, 그 값이 MCP 계층까지 닿지 못한다.

**반대 방향의 오보도 있었다.** 2026년 9월 15일에 셸로 고친 `InventoryTests.cpp`를 23시 31분
26초에 빌드했으나 `.obj`는 23시 31분 11초에 멈춰 있었고, Rider는 `buildIsSuccess: true`를
돌려줬다. Rider가 바뀐 파일을 인식하지 못한 채 재컴파일을 건너뛴 것이다. `.obj`를 지우고 다시
빌드해도 재현됐다. 즉 이 경로는 성공과 실패를 양방향으로 잘못 보고한 전력이 있다.

**서버는 MCP가 정상인데도 함께 옮긴다.** 표에서 보듯 MSBuild 경로의 성공 판정은 맞다. 그럼에도
바꾸는 이유는 **티어마다 다른 방식을 두지 않기 위해서**다. 예외를 남기면 어느 티어가 어느 규칙을
따르는지 매번 기억해야 하고, 규칙이 둘이면 잘못된 쪽을 고르는 일이 생긴다. 게임 서버와 인증
서버의 테스트가 이미 종료 코드로 판정하므로, 빌드까지 같은 모델로 맞추면 세 티어가 하나가 된다.

## 실측

2026년 9월 16일에 두 티어를 각각 성공과 실패로 돌려 확인했다.

| 대상 | 성공 종료 코드 | 실패 종료 코드 | 성공 출력 | 실패 출력 |
|---|---|---|---|---|
| `P1` (`Build.bat`) | `0` | `6` | 30줄 | 33줄, 2,355바이트 |
| `Server` (`MSBuild /v:minimal`) | `0` | `1` | 117줄, 4,962바이트 | 20줄, 1,907바이트 |

실패 출력에는 에러 코드와 파일과 줄과 열이 함께 찍힌다. `Build.bat`은 문제 소스 줄과 캐럿 위치를,
`MSBuild`는 해당 `.vcxproj`를 덧붙인다. 기존 금지의 근거였던 "출력 절단으로 에러가 유실된다"는
증분 빌드에서 성립하지 않는다.

## 검토한 대안

**Rider MCP를 유지하고 3상태 판독 규칙을 적용한다.** `buildIsSuccess: false`에 `problems`가 비어
있으면 판정 불가로 읽고 UBT 로그를 한 번 더 확인하는 방식이다. 채택하지 않았다. 경로가 둘로
갈리는 문제를 그대로 두고, 판정마다 조회가 2회로 늘며, 그중 1회는 항상 거짓이고, 사람이 규칙을
계속 기억해야 한다.

**클라이언트만 옮기고 서버는 Rider MCP로 남긴다.** 서버 쪽은 고장나지 않았으므로 근거 없는 변경을
피한다는 논리다. 채택하지 않았다. 고치는 것이 목적이 아니라 하나로 모으는 것이 목적이기 때문이다.
티어별 예외가 남으면 통일이 아니다.

버리는 이점은 구조화된 `problems[]` 하나다. 다만 그 목록은 에러 코드를 담지 않는다. 터미널 출력은
`C3861` 같은 코드까지 함께 준다.

## 결과

- 빌드 경로가 하나가 된다. 에디터 연결 여부가 결과를 바꾸지 않는다.
- 판정 모델이 세 티어에서 같아진다. 빌드도 테스트도 종료 코드다.
- 대신 타깃과 구성과 경로를 문서가 직접 관리한다. 잘못 적으면 엉뚱한 대상을 빌드하고도 종료 코드
  `0`이 나온다.
- `MSBuild`는 `/v:minimal`을 전제로 측정했다. 기본 상세도는 출력이 훨씬 크다.
- 증분 빌드에서만 출력 규모를 확인했다. `Rebuild.bat`과 최초 전체 빌드는 모듈 수만큼 출력이
  늘어나므로 절단될 수 있다.
- Rider MCP 빌드의 함정 둘은 이 문서에만 남는다. `docs/testing.md`에서 해당 절을 걷어냈다. 그
  경로를 더는 쓰지 않으므로 운영 문서에 판독 규칙을 둘 이유가 없다.
