# 기획 데이터의 타입을 DataBuilder가 생성하고, 검증은 규칙의 원천에 따라 나눈다

`Tools/DataBuilder/`의 스크립트 하나가 `DesignData/`의 엑셀 원본을 읽어 검증하고, 서버와 클라이언트가 읽을 JSON과 그 JSON을
담는 타입(서버의 C++ 구조체, 클라이언트의 `USTRUCT`)을 함께 생성한다. 게임 코드는 생성된 타입을 그대로 쓴다. 기획 데이터
자체의 규칙은 DataBuilder가 검사하고, 코드가 정한 제약만 서버가 기동할 때 검사한다. 2026년 10월 27일 기획 데이터 처리 방식
재설계에서 정했다.

엑셀의 열 하나를 늘리면 지금까지는 서버의 열 이름 상수, 템플릿 구조체, 파서의 변환, 클라이언트의 행 구조체를 따로 고쳤다.
네 곳 중 하나를 빠뜨려도 빌드가 통과했다. 원본이 하나인 정보를 사람이 네 곳에 옮겨 적지 않게 하려는 것이다.

## 열거형은 `.proto`가 원천이다

아이템 종류와 직업처럼 패킷에도 실리는 열거형은 `.proto`에 이미 있다. DataBuilder는 열 타입에 적힌 열거형 이름으로 `.proto`의
열거형을 찾아 값 이름을 읽고, 생성 코드는 프로토콜 헤더의 열거형을 쓴다. `.proto`에 없는 기획 데이터 전용 열거형(재화 유형,
드롭 그룹의 판정 방식)만 DataBuilder가 생성한다.
— DataBuilder가 열거형을 모두 생성하면 같은 열거형이 두 곳에 정의된다. 한쪽에만 값을 더해도 빌드가 통과한다.

## 검증은 규칙을 정한 쪽이 맡는다

| 규칙 | 검사하는 곳 | 예 |
| --- | --- | --- |
| 기획 데이터 자체의 규칙 | DataBuilder | 타입, 필수 값, 키 중복, 다른 표의 키 참조, 최솟값과 최댓값의 순서, 드롭 그룹의 판정 방식과 항목 열의 짝 |
| 코드가 정한 제약 | 서버 기동 | DB 열 크기를 넘지 않는 값, 로비와 게임의 데이터 대조 |

DataBuilder가 실패하면 산출물을 하나도 바꾸지 않는다. 서버는 생성된 역직렬화가 형식을 확인하고, 코드 제약을 어긴 값이 있으면
뜨지 않는다.
— 기획자는 엑셀을 고친 직후 DataBuilder로 규칙 위반을 알아야 한다. 반대로 DB 열 크기나 UI 고정값을 DataBuilder에 적으면,
코드가 바뀔 때 파이썬도 고쳐야 한다는 사실이 코드 쪽에서 보이지 않는다.

## 산출물 폴더는 생성기가 소유한다

DataBuilder는 실행할 때마다 자기 산출물 폴더를 비우고 다시 쓴다. 그 폴더에는 사람이 쓴 파일을 두지 않는다. 한 폴더에는
생성기 하나만 쓴다. 에디터에서 서버 데이터를 추출하는 생성기가 생기면 그 생성기는 다른 폴더를 갖는다.
— 원본에서 표를 지워도 옛 산출물이 남아, 생성물이 아닌 파일을 생성물로 오해하는 일이 있었다.

## 검토한 대안

- **생성된 구조체를 행 계층으로만 쓰고, 손으로 쓴 변환이 도메인 템플릿을 만든다.** 지금의 파서를 모양만 바꿔 남기는 것이다.
  열을 하나 늘릴 때 고칠 곳이 줄지 않는다.
- **모든 검증을 DataBuilder에 둔다.** 서버는 생성된 JSON을 믿기만 한다. 코드가 정한 제약이 파이썬에 적혀 코드와 따로 바뀐다.
- **지금처럼 서버 기동에서 모든 규칙을 검사한다.** 기획자가 규칙 위반을 서버를 띄워야 알고, 클라이언트용 데이터는 아무도 검사하지 않는다.
- **원본을 엑셀에서 CSV나 JSON으로 바꾼다.** 원본을 diff하려는 목적이었다. 생성된 JSON을 한 행 한 줄로 쓰고 키 순으로 정렬하면
  엑셀을 고친 결과가 산출물의 diff로 드러나므로, 기획자가 쓰기 편한 엑셀을 원본으로 남긴다.

## 결과

- 표의 열을 늘리면 엑셀을 고치고 DataBuilder를 돌린 뒤, 그 값을 쓰는 코드만 고친다.
- 생성된 타입은 열 이름을 그대로 필드 이름으로 쓰므로, 엑셀의 열 이름이 코드의 이름이 된다. 열 이름을 바꾸면 그 필드를 쓰는
  코드가 빌드에서 깨진다.
- 서버의 기획 데이터 파서 테스트는 코드 제약과 대조만 남고, 기획 데이터 규칙의 테스트는 DataBuilder 쪽으로 옮긴다.
- 에셋 참조를 기획 원본에 두지 않는다는 결정(ADR-0009)은 그대로다. 생성된 수치 테이블과 에디터가 소유하는 에셋 테이블은 행
  이름으로 짝을 맺고, 에디터 검증기가 짝이 맞는지 확인한다.
