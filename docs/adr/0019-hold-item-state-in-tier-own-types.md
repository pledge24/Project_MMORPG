# 아이템과 칸의 상태는 티어마다 전용 타입으로 들고, Protocol 타입은 패킷 경계에서만 쓴다

게임 서버와 클라이언트는 아이템과 칸의 상태를 각자 정의한 타입으로 든다. 서버는 표준 라이브러리 타입으로 된 구조체를,
클라이언트는 `USTRUCT`를 쓴다. `Protocol::Slot`과 `Protocol::Possession`은 패킷을 만들고 읽는 자리에서만 쓰고, 상태를
담는 멤버의 타입으로 쓰지 않는다. 칸 변경을 알리는 패킷은 「이 주소의 칸은 이제 이 내용이다」만 싣고, 추가·수정·삭제를
나타내는 `UpdateState` 필드는 없앤다. 2026년 10월 21일 슬롯 구조 재설계 논의에서 정했다. 이 ADR을 쓴 시점에는 아직
구현하지 않았다.

## 전용 타입을 두는 이유

전송 형식과 상태 형식은 바뀌는 이유가 다르다. 둘을 같은 타입으로 두었더니 전송에만 쓰는 값이 상태에 남았다.
`UpdateState`가 권위 상태에 그대로 남아서, 불러온 칸이 `ADDED` 상태로 입장 패킷에 실렸다. 클라이언트에는 이 값을
무시하는 우회 코드가 있었다. 반대로 한쪽 티어만 쓰는 값을 상태에 더하려면 `.proto`를 고쳐야 했다. 상대 티어와 무관한
변경이 프로토콜 변경이 되면, 여러 사람이 작업할 때 한쪽의 변경이 다른 쪽의 빌드와 검토를 부른다.

양쪽 티어의 인벤토리와 장비 클래스는 `Possession` 메시지 안쪽을 가리키는 원시 포인터로 상태를 고쳤다. 이 구조는
`Possession`을 새 객체로 바꾸지 않는다는 주석에 기댔고, 범위를 검사하지 않는 인덱스 접근과 초기값이 없는 포인터가 여기서
나왔다. 상태를 전용 타입으로 들면 컨테이너가 자기 칸 배열을 소유하므로 이런 포인터가 필요 없다.

클라이언트는 상태를 `USTRUCT`로 들어야 블루프린트와 리플렉션에 노출할 수 있다. Protocol 타입은 `UPROPERTY`가 될 수 없다.

## 감수하는 비용

칸에 필드를 더하면 `.proto`, 서버 타입, 클라이언트 타입, 변환 함수 넷을 함께 고친다. 변환 함수는 서버의 입장 패킷 작성,
칸 변경 패킷 작성, DB 행 변환과 클라이언트의 입장 패킷 수신, 칸 변경 수신에만 둔다. 왕복 변환 테스트로 필드 누락을 잡는다.

## 검토한 대안

- **Protocol 타입을 상태로 유지하고 `UpdateState`만 뺀다.** 변환 코드가 없다. 하지만 메시지 안쪽을 가리키는 포인터와
  한쪽 티어 전용 값을 둘 자리가 없는 문제가 그대로 남는다.
- **서버만 전용 타입을 두고 클라이언트는 Protocol 타입을 유지한다.** 클라이언트의 변환 코드가 없다. 하지만 클라이언트의
  포인터 래퍼와 위젯이 들던 칸 사본이 그대로 남고, 블루프린트에 노출할 수 없다.
- **Protocol 메시지에 티어 전용 필드를 넣고 상대 티어에서는 무시한다.** 타입이 하나로 끝난다. 하지만 무시해야 할 필드를
  보낼 때마다 비워야 하고, 한 번 잊으면 전송된다. `UpdateState`가 이미 이 모양으로 새어 나갔다.

## 결과

- 서버의 DB 저장은 지금처럼 접속 종료 때 아이템 전체를 MERGE한다. 컨테이너가 응답 패킷을 만들려고 모으는 변경 목록은
  DB 저장에 쓰지 않는다(ADR 0012)
- 요청 패킷은 칸 사본 대신 칸 주소와 아이템 uid로 칸을 가리킨다

## 틀렸다는 신호

- 변환 함수에서 필드 누락이 반복된다. 이때는 변환을 생성기로 만드는 것을 검토한다
