# 로비를 게임 서버 안의 최상위 모듈 폴더로 두고, 게임과는 창구 둘로만 잇는다

캐릭터 목록, 생성, 삭제, 선택을 맡는 로비를 `Server/GameServer/Lobby/` 폴더 하나에 모은다. 프로세스와 `.vcxproj`는
나누지 않는다. 로비와 게임은 게임 입장 창구(로비 → 게임)와 로비 복귀 창구(게임 → 로비) 둘로만 잇고, 두 창구로 오가는 값은
계정 번호와 캐릭터 번호다. 나중에 로비를 별도 프로세스로 옮길 때 이 폴더를 새 프로젝트로 옮기고, 게임 입장 창구를 「로비가
발급하고 게임 서버가 소비하는 입장 티켓」으로 바꾸면 되게 하려는 것이다. 2026년 10월 23일 로비 분리와 게임 입장 흐름
설계에서 정했다.

## 폴더에 드는 것

- 로비 접속(인증 티켓 소비)과 로비 패킷의 핸들러
- 캐릭터 생성과 삭제의 규칙(지금의 `Game/Characters/`)
- 로비가 쓰는 DAO. `GameDB`의 계정 행과 캐릭터 행을 다룬다
- 로비의 기획 데이터(`Lobby/Data/`). 기본 슬롯 수와 생성할 수 있는 직업이다

세션과 세션 관리자, DB 연결과 큐, ID 발급기는 배선이므로 지금 자리에 둔다. 로비는 이 배선과 게임 입장 창구만 부른다.
게임은 로비 복귀 창구로만 로비를 부른다. 생성된 패킷 핸들러 헤더는 선언만 하므로 로비 패킷의 핸들러는 `Lobby/` 안에서 정의한다.

## 기획 데이터는 소비자별로 나눈다

로비와 게임은 서로의 기획 데이터를 읽지 않는다. 생성할 수 있는 직업마다 레벨 표가 있는지는 서버가 기동할 때 `Core/`가
두 데이터를 대조한다.

옛 생성 표의 다섯 열 중 로비가 쓰는 것은 기본 슬롯 수 하나였다. 나머지 넷(시작 맵, 위치, 방향, 골드)은 새 캐릭터의 초기
진행이므로 `Game/Data/`의 표로 옮긴다. 로비가 읽던 게임 쪽 표 셋(직업별 레벨 표, 재화 표, 맵 표)도 직업 판정을 빼면 모두
초기 진행을 쓰기 위한 것이었다.

## 초기 진행은 첫 게임 입장이 만든다

캐릭터를 만들 때 로비는 `Character` 행만 쓴다. 게임 입장의 불러오기 잡은 진행 행이 없으면 같은 트랜잭션에서 초기 진행 행을
만들고 이어서 불러온다. 「진행 행이 없는 캐릭터는 아직 게임에 입장한 적이 없는 캐릭터다」가 로비와 게임 사이의 불변식이 된다.

## 검토한 대안

- **로비를 별도 정적 라이브러리 프로젝트로 나눈다.** 컴파일러가 경계를 강제한다. 하지만 로비가 기대는 세션, DB 큐, 기획
  데이터, ID 발급기, 생성된 핸들러 표가 모두 `GameServer` 안에 있어서, 그것들을 먼저 공용 라이브러리로 옮겨야 한다. 그 이동이
  이 작업만큼 크다. 클라이언트가 도메인을 모듈로 나누지 않은 근거(ADR-0005)도 같다.
- **로비를 `Game/` 아래에 둔다.** `Game/`은 게임 규칙을 담는 층인데, 로비는 핸들러와 DAO까지 함께 담는 세로 묶음이라 그
  층의 뜻과 맞지 않는다.
- **로비가 캐릭터 행과 초기 진행 행을 한 트랜잭션으로 쓴다.** 「캐릭터가 있으면 진행 행도 있다」가 유지된다. 하지만 로비가
  직업별 레벨 표, 재화 표, 맵 표를 읽어야 해서 기획 데이터를 나눌 수 없다.
- **게임 모듈이 초기 진행을 만드는 함수를 제공하고 로비가 부른다.** 진행 테이블을 쓰는 코드는 게임에 남는다. 하지만 로비를
  별도 프로세스로 옮기면 그 함수와 그 함수가 읽는 기획 데이터가 로비 서버에도 들어가야 한다.

## 결과

- `docs/folder-structure.md`가 `GameServer/`의 최상위를 배선과 `Game/` 두 가지로만 나누던 데에 세로 모듈 `Lobby/`가 더해진다
- `docs/ARCHITECTURE.md`의 「DB 접근은 `DB/`의 DAO가 데이터별로 맡는다」에 「로비의 DAO는 `Lobby/`에 있다」가 더해진다
- 기획 원본 `Original_Character_Creation.xlsx`를 로비용과 게임용으로 나누고, 변환 스크립트의 목적지가 두 폴더가 된다
- 클라이언트에도 `Lobby/`가 생긴다. 양쪽에 있는 도메인이므로 이름을 맞춘다(ADR-0007)
- 2026년 10월 23일 덧붙임: 생성 표를 로비 표(`Original_Lobby.xlsx` → `Lobby/Data/Json/S_Lobby.json`)와 게임의 초기 진행 표
  (`Original_Initial_Progress.xlsx` → `Game/Data/Json/S_Initial_Progress.json`)로 나눴다. 생성할 수 있는 직업은 레벨 표의 유무가
  아니라 로비 표가 정하고, 기동할 때의 대조는 `Core/DataCrossCheck`가 한다
- 2026년 10월 27일 덧붙임: 로비 표는 설정 워크북의 `Lobby` 시트(`DesignData/Config.xlsx`)가 됐고, 초기 진행 표는 같은 워크북의
  `Progress` 시트가 됐다. DataBuilder가 `Lobby` 시트를 로비 모듈의 산출물 폴더(`Lobby/Data/Generated/`)로, `Progress` 시트를 게임
  모듈의 산출물 폴더로 생성한다. 두 모듈의 생성된 헤더는 C++ 네임스페이스가 다르고(`LobbyDesignData`, `DesignData`), 로비 코드는
  게임의 기획 데이터 헤더를 include하지 않는다

## 틀렸다는 신호

- 캐릭터 목록에 착용 장비의 외형처럼 진행의 일부를 보여 줘야 한다. 로비가 게임의 상태를 읽게 되므로 경계를 다시 본다
- 두 창구로 오가는 값이 계정 번호와 캐릭터 번호 말고도 늘어난다
- 로비와 게임이 같은 기획 데이터를 함께 읽어야 하는 표가 생긴다
