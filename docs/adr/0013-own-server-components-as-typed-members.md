# 서버 컴포넌트는 엔티티가 타입이 정해진 멤버로 소유한다

게임 서버 엔티티의 기능 단위(인벤토리, 장비)는 `EntityComponent`(`Server/GameServer/Game/Entities/EntityComponent.h`)를
상속한다. 베이스가 공유하는 것은 소유자를 가리키는 `weak_ptr`와 `Start`/`Tick` 두 함수뿐이다. 엔티티는 컴포넌트를
`InventoryComponentRef _inventory`처럼 타입이 정해진 멤버로 직접 들고, 자기 `Start`와 `Tick`에서 컴포넌트의
`Start`와 `Tick`을 부른다. 컴포넌트를 타입으로 찾는 범용 조회(`GetComponent<T>`)는 두지 않는다.
2026년 10월 9일 #208에서 정했다.

## 범용 조회를 두지 않는 이유

컴포넌트를 쓰는 곳이 모두 그 컴포넌트를 가진 엔티티의 타입을 안다. 인벤토리와 장비는 `Player`만 갖고, 호출자는
`Player`의 요청 처리와 DB 불러오기, 저장 사본을 만드는 코드다. 조회가 실패할 일이 없는 자리에서 조회를 거치면
「없으면 어떻게 하나」라는 분기만 늘어난다. 멤버로 들면 빠진 컴포넌트를 컴파일러가 잡는다.

## 검토한 대안

- **엔티티에 컴포넌트 컨테이너를 두고 `GetComponent<T>`로 찾는다.** 언리얼의 액터와 같은 모양이라 클라이언트와
  대칭이 된다. 하지만 언리얼이 컨테이너를 쓰는 이유는 에디터와 블루프린트가 런타임에 컴포넌트를 붙이기 때문이다.
  서버에는 그런 조립 단계가 없고, 엔티티마다 가질 컴포넌트가 코드로 정해져 있다. 컨테이너는 타입 검사를
  런타임으로 미루고 `dynamic_cast`나 타입 id 표를 끌어들인다.
- **베이스 없이 각 컴포넌트를 독립 클래스로 둔다.** 소유자 포인터와 수명 규칙이 클래스마다 따로 적힌다. 틱을
  룸이 일괄로 돌리게 되면(#211) 틱을 받는 단위가 엔티티와 컴포넌트 두 가지가 되는데, 그때 묶을 공통 타입이 없다.

## 결과

- 서버는 `EntityComponent` 파생에만 이름에 `Component`를 붙인다(`docs/conventions.md` 3.10).
- 클라이언트의 대응 클래스는 `UActorComponent`가 아니면 `Component`를 붙이지 않는다. 서버의 `EquipmentComponent`에는
  `UObject`인 `UP1Equipment`가 대응한다.
- 컴포넌트는 소유자를 `weak_ptr`로 가리키므로 순환 참조가 없다. 소유자의 구체 타입이 필요한 컴포넌트는
  `static_pointer_cast`로 내린다. 그 컴포넌트를 만드는 엔티티가 하나뿐이라 캐스트가 틀릴 일이 없다.
- 컴포넌트를 타입으로 찾아야 하는 호출자가 셋 이상 생기면 이 결정을 다시 본다.
