# 인증 서버의 코드는 도메인 폴더 하나에 네 계층을 모은다

인증 서버의 `src/`는 도메인 폴더와 공용 폴더 `common/`으로 나눈다. 도메인 폴더 하나에 그 도메인의 router, handler,
service, repository 네 계층을 `<도메인>.<계층>.ts` 이름으로 모으고, 도메인이 아닌 코드는 평평한 `common/`에 둔다.
목표는 「도메인 폴더 하나를 지우면 그 도메인 로직만 사라진다」이다. 2026년 10월 19일 인증 서버 재구성(#231)에서
그릴링으로 정했고, 저장소 밖의 개인 프로젝트 Project_Dedicated의 `Backend/src` 구조를 기준으로 삼았다.

## 도메인 폴더로 모으는 이유

재구성 도중의 구조는 저장 대상(`accounts/`, `tickets/`), 유스케이스(`auth/`), 기술 계층(`http/`)이 한 높이에 섞여
있었다. 로그인 하나를 따라가려면 네 폴더를 오가야 했고, 어떤 폴더를 지워도 되는지 이름만으로 알 수 없었다.
도메인 폴더에 계층을 모으면 한 도메인을 고치는 일이 한 폴더 안에서 끝난다. 그 도메인을 없앨 때도 폴더 하나와 조립 쪽의
등록 줄만 지우면 된다.

지금 도메인은 `auth/`(회원가입과 로그인) 하나다. 인증 티켓은 도메인이 아니다. 로그인이 발급하지만 다른 도메인도 쓸 수 있는
공용 부분이므로 `common/`에 둔다. 전역 에러 카탈로그(`common/errors.ts`)도 `common/`에 남는다. 그래서 도메인을 지우면
그 도메인의 에러 코드는 카탈로그에 남는다. 클라이언트와의 계약을 한곳에서 보는 쪽을 택했다.

`common/`은 도메인 폴더를 import하지 않는다. 도메인을 지워도 `common/`과 그 테스트는 그대로 타입 검사를 통과한다.
티켓 저장소가 계정 번호를 `auth/`의 `AccountId` 타입이 아니라 문자열로 받는 것은 이 때문이다.

## 참고 구조와 다른 점

Project_Dedicated는 저장소를 함수 모듈로 두고 service가 직접 import한다. 이 서버는 저장소를 인터페이스로 두고
service 생성자로 주입한다. 테스트가 메모리 구현을 넣어 「가입 → 로그인 → 티켓」을 실제 흐름처럼 검사하기 때문이다.
그래서 계층 파일의 본체(`auth.repository.ts`)에는 인터페이스와 실제 구현을 두고, 메모리 구현은 `.memory.ts` 접미사의
파일에 둔다. 실제 서버가 쓰는 구현은 하나뿐이므로 파일 이름에 DB 기술 이름을 넣지 않는다.

테스트는 참고 구조처럼 한 폴더(`Backend/tests/`)에 모으지 않고, 폴더마다 그 아래의 `tests/`에 둔다(`auth/tests/`,
`common/tests/`). 도메인 경로의 HTTP 테스트도 그 도메인의 `tests/`에 있어, 도메인을 지우면 그 테스트도 함께 사라진다.
계층 파일과 테스트 파일이 한 폴더에 섞이지 않아 도메인 폴더에서 계층 파일 네 개가 바로 보인다.

## 검토한 대안

- **계층별 폴더(`http/`, `services/`, `repositories/`)로 나눈다.** 계층의 경계는 폴더로 드러나지만, 한 기능을 고칠 때
  여러 폴더를 오가고 도메인 하나를 지우는 단위가 없다.
- **유스케이스별 폴더(`register/`, `login/`)로 나눈다.** 두 유스케이스가 같은 계정 저장소와 입력 형식 규칙을 쓰므로,
  함께 쓰는 코드가 어느 폴더에도 속하지 않게 된다.
- **참고 구조처럼 저장소를 함수 모듈로 두고 테스트에서 `vi.mock`으로 바꿔 끼운다.** 구조는 참고 구조와 같아지지만,
  메모리 구현이 하던 「저장하고 다시 읽는」 동작을 목마다 다시 써야 한다.

## 결과

- 도메인을 더할 때는 `src/<도메인>/`을 만들고, `app.ts`에 라우터를 한 줄로 붙이고, `main.ts`에서 실제 구현을 조립한다
- 계층 파일 하나가 여러 유스케이스 때문에 읽기 어려울 만큼 커지면 이 결정을 다시 본다
- 실제 서버가 쓰는 구현이 둘 이상이 되면 파일 이름에 기술 이름을 넣지 않는 규칙을 다시 본다
