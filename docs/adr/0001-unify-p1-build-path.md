# P1 빌드를 Build.bat 한 경로로 통일한다

`P1`의 빌드를 `Build.bat` 하나로 통일하고, 성공 여부는 그 종료 코드로 판정한다. 그전까지는 Rider
MCP의 `build_solution_start`를 썼는데, 그 경로는 에디터 연결 여부에 따라 두 갈래로 갈렸고 성공
판정도 UE 타깃에서 틀렸다. 이 결정은 CLAUDE.md 「도구 라우팅」이 2026년 9월 16일까지 유지하던
"UBT를 터미널로 직접 돌리지 않는다"를 뒤집는다.

## 왜 하나로 모으는가

**기존 경로는 하나가 아니었다.** `build_solution_start`는 에디터가 연결되어 있으면 Live Coding
컴파일로, 닫혀 있으면 UBT로 갈린다. 툴은 그 전환을 알리지 않는다. 두 경로는 결과가 다르다. Live
Coding은 헤더와 `UFUNCTION` 같은 리플렉션 변경을 반영하지 못하고, 패치를
`Binaries/Win64/UnrealEditor-P1.patch_N.*`로 따로 내보내며 `UnrealEditor-P1.dll`을 갱신하지
않는다. 2026년 9월 16일에 Live Coding으로만 검증한 코드를 커밋할 뻔했고, 메인 DLL의 PDB에서 새
심볼이 0건인 것을 보고서야 알아챘다.

**성공 판정도 틀렸다.** 같은 Rider 세션 안에서 대조 실험으로 범위를 좁혔다.

| 대상 | 빌드 결과 | `problems` | `buildIsSuccess` |
|---|---|---|---|
| `Server` (MSBuild) | 성공 | 비어 있음 | `true` |
| `P1` (UBT) | 성공 | 비어 있음 | `false` |
| `P1` (UBT) | 실패 | 파일·줄·열까지 정확 | `false` |

MSBuild 경로는 정상이고 UE 경로만 틀린다. 실패는 정확히 전달되므로 고장난 것은 성공 판정 하나다.
Rider 내부에는 판정이 존재한다. 백엔드 로그가 빌드마다 `Fire build result Kind: Successful`을
남기고, 그 값이 MCP 계층까지 닿지 못한다.

기존 금지의 근거였던 "출력 절단으로 에러가 유실된다"도 성립하지 않았다. `Build.bat`의 증분 빌드
출력은 성공 30줄, 실패 33줄에 2,355바이트였다. 종료 코드는 성공 `0`, 실패 `6`으로 갈렸다.

## 검토한 대안

**Rider MCP를 유지하고 3상태 판독 규칙을 적용한다.** `buildIsSuccess: false`에 `problems`가 비어
있으면 판정 불가로 읽고 UBT 로그를 한 번 더 확인하는 방식이다. 채택하지 않았다. 경로가 둘로
갈리는 문제를 그대로 두고, 판정마다 조회가 2회로 늘며, 그중 1회는 항상 거짓이고, 사람이 규칙을
계속 기억해야 한다.

버리는 이점은 구조화된 `problems[]` 하나다. 다만 그 목록은 에러 코드를 담지 않는다. `Build.bat`의
출력은 `C3861` 같은 코드와 문제 소스 줄과 캐럿 위치까지 함께 준다.

## 결과

- 빌드 경로가 하나가 된다. 에디터 연결 여부가 결과를 바꾸지 않는다.
- 판정 모델이 세 티어에서 같아진다. 게임 서버와 인증 서버가 이미 종료 코드로 판정한다.
- 대신 타깃과 `-Project` 경로를 문서가 직접 관리한다. 잘못 적으면 엉뚱한 타깃을 빌드하고도 종료
  코드 `0`이 나온다.
- 증분 빌드에서만 출력 규모를 확인했다. `Rebuild.bat`과 최초 전체 빌드는 모듈 수만큼 출력이
  늘어나므로 절단될 수 있다.
- `build_solution_state`의 3상태 판독 규칙은 `docs/testing.md`에 남긴다. 누군가 MCP로 빌드할 때를
  위한 기록이다.
