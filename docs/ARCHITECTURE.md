# Architecture

이 문서는 코드를 읽어서 알 수 있는 내용을 반복하지 않는다.
**왜 이렇게 되어 있는지**, 그리고 **깨면 안 되는 것**만 적는다.

최종 수정: 2026-10-24
검증: 세션 1(2026-08-19)에서 실코드·라이브 DB·UE 에디터와 대조.

불변식은 `**Architecture Invariant:**`로 표시한다. 대부분 **무언가의 부재**를 가리킨다 —
코드를 읽어서 알아내기 가장 어려운 종류다.

---

## Bird's Eye View

UE5 클라이언트 · 외부 IOCP C++ 게임 서버 · Node 인증 서버의 3티어 MMORPG.
세 티어를 반드시 함께 띄워야 동작한다.

**ground state**는 인증 서버의 계정 DB와 `GameDB`의 행, 그리고 Redis의 로그인 세션과 인증 티켓이다.
Redis의 월드 항목은 게임 서버가 주기적으로 다시 쓰는 derived state다.
**derived state**는 룸 안 오브젝트의 런타임 상태다 — 접속 종료 시 `CharacterState`와 `Item`으로
내려가고, 재접속으로 재생성된다. 진실의 원천으로 삼지 않는다.

세 티어를 잇는 선은 두 개뿐이다.

- 인증 티어 ↔ 게임 티어: **Redis의 월드 집합, 월드 항목, 인증 티켓 키**
- 클라 ↔ 게임 서버: **`.proto`에서 생성된 패킷**

## Code Map

### Server/AuthServer

회원가입으로 계정을 만들고, 로그인을 판정해 로그인 세션을 발급하고, 월드 목록과 월드 선택을 맡는다. 이 네 가지 외의 일은
하지 않는다. 월드 선택이 그 월드에서만 쓸 수 있는 인증 티켓을 발급한다. `AccountDB`를 소유한다.
흐름과 Redis 계약을 정한 근거는 `docs/adr/0020-issue-auth-ticket-at-world-selection.md`에 있다.
닉네임처럼 계정 단위로 다른 사람에게 보이는 이름은 받지 않는다. 화면에 캐릭터 이름이 아닌 계정 단위의 이름이 필요해지면
이 결정을 다시 본다.

회원가입은 아래 세 단계다.

1. 로그인 ID를 소문자로 바꾸고, 로그인 ID와 비밀번호의 형식을 검사한다
2. 비밀번호를 bcrypt로 해시해 계정을 만든다. 인증 티켓은 발급하지 않는다
3. 같은 로그인 ID의 계정이 이미 있으면 거절한다. 미리 조회하지 않고, 계정을 만들 때 `Account.LoginId`의 UNIQUE 제약 위반으로 알아낸다

— 미리 조회하면 조회와 생성 사이에 같은 로그인 ID의 가입이 끼어들 수 있다.

로그인은 아래 일곱 단계다.

1. 회원가입과 같은 방식으로 로그인 ID를 소문자로 바꾸고 형식을 검사한다
2. 로그인 ID로 계정을 찾는다
3. 비밀번호를 검증한다. 2번과 3번의 실패는 같은 응답이다. 로그인 ID가 없어도 미리 만든 더미 해시로 검증을 한 번 한다
4. 정지 여부를 본다. `BannedUntil`이 현재 시각(UTC)보다 뒤이면 정지 중이다. 정지 중이면 거절하고 5번과 6번을 하지 않는다
5. `LastLoginAt`을 갱신한다
6. 로그인 세션을 만들어 Redis에 넣는다. 수명은 지금부터 1시간으로 고정이다
7. Redis에서 살아 있는 월드 항목을 읽어 로그인 세션과 함께 돌려준다. 접속 주소는 싣지 않는다

— 2번과 3번의 응답이 다르면 로그인 ID가 있는지를 밖에서 알아낼 수 있다. 응답 본문뿐 아니라 응답 시간도 같아야 하므로
없는 로그인 ID에도 검증을 건너뛰지 않는다. 4번을 3번 앞에 두면 비밀번호를 모르는
사람도 그 로그인 ID가 정지되었다는 것을 안다.

월드 선택은 아래 네 단계다.

1. `Authorization: Bearer <로그인 세션>`에서 로그인 세션을 꺼내 계정 번호를 찾는다
2. 계정의 정지 여부를 다시 본다. 로그인 세션은 1시간 살아 있으므로, 그사이 정지된 계정을 여기서 막는다
3. 고른 월드의 항목을 찾는다. 혼잡도는 보지 않는다
4. 인증 티켓을 만들어 그 월드의 키로 Redis에 넣고, 그 월드의 주소와 함께 돌려준다

**Architecture Invariant:** 게임 상태를 모른다. `GameDB`에 접근하지 않는다. GM 권한처럼 게임 서버만 쓰는 계정 속성도
`AccountDB`에 두지 않는다.
— 게임 서버는 `AccountDB`를 읽지 못하므로, 그런 열은 아무도 읽지 않는다.

**Architecture Invariant:** 인증 티켓을 발급하는 경로는 월드 선택 하나뿐이다.
— 다른 경로가 생기면 그 경로에서 정지 검사가 빠진다. `LastLoginAt`은 로그인이 갱신한다.

**Architecture Invariant:** 로그인 세션의 수명은 로그인한 시각부터 고정이다. 월드 목록이나 월드 선택에 써도 늘리지 않고,
월드 선택에 써도 지우지 않는다. 같은 계정으로 다시 로그인해도 이전 로그인 세션과 쓰지 않은 인증 티켓을 지우지 않는다.
— 쓸 때마다 수명이 늘어나면 탈취한 로그인 세션이 끝없이 살아 있다. 이전 티켓으로 들어온 세션은 게임 서버의 「나중에 온
로비 접속이 이긴다」 규칙으로 밀려나므로 결과가 같다. 지우려면 계정에서 값을 찾는 키가 하나 더 생기고, 두 키가 어긋나는
경우까지 다뤄야 한다.

**Architecture Invariant:** 월드 목록의 원천은 게임 서버가 쓴 Redis의 월드 항목 하나다. 인증 서버는 월드를 설정으로 갖지 않고,
항목을 고치거나 지우지 않는다. 항목이 없는 월드는 목록에 나오지 않고 고를 수도 없다.
— 인증 서버가 월드를 따로 알면 월드 목록의 원천이 둘이 된다.

**Architecture Invariant:** 접속을 받기 전에 설정 검사, `AccountDB` 연결, Redis 연결을 이 순서로 모두 확인한다.
하나라도 실패하면 에러 원문을 남기고 종료 코드 1로 끝난다. Redis 클라이언트는 처음 연결에 실패하면 다시 시도하지 않는다.
— 연결에 실패한 채 포트를 열면 서버가 떠 있는 것처럼 보이지만 모든 로그인이 500으로 실패한다. node-redis의 기본 재연결
전략은 처음 연결도 끝없이 다시 시도해서, Redis가 없으면 기동이 끝나지도 실패하지도 않는다.

**Architecture Invariant:** 판정 코드(`*.service.ts`)는 저장소를 인터페이스로 받는다. 계정 저장소(`auth/`),
계정 상태 저장소(`world/`), 로그인 세션 저장소, 월드 디렉터리, 티켓 저장소(`common/`)다.
MSSQL과 Redis를 아는 코드는 이 인터페이스의 구현과 AccountDB 연결을 만드는 `common/db.ts`뿐이다.
— DB나 Redis를 바꿀 때는 구현만 바꾼다. 테스트는 메모리 구현을 넣어 판정과 HTTP 계약을 검사한다.

**Architecture Invariant:** 계정 번호(`AccountId`)는 `BIGINT`이고, 인증 서버 안에서는 10진수 문자열로 다룬다.
— `mssql` 드라이버는 `BIGINT`를 문자열로 돌려준다. 인증 서버는 계정 번호로 계산하지 않으므로 숫자로 바꾸지 않는다.

**API Boundary(클라이언트):** HTTP와 JSON이다.

| 요청 | 본문 | 성공 응답 |
|---|---|---|
| `POST /api/auth/register` | `{ loginId, password }` | 201 `{ ok: true, data: { loginId } }` |
| `POST /api/auth/login` | `{ loginId, password }` | 200 `{ ok: true, data: { loginSession, worlds } }` |
| `GET /api/worlds` | `Authorization: Bearer <로그인 세션>` | 200 `{ ok: true, data: { worlds } }` |
| `POST /api/worlds/{worldId}/select` | 같은 헤더 | 200 `{ ok: true, data: { host, port, ticket } }` |

회원가입의 `data.loginId`는 소문자로 바꾼 뒤의 값이다. `worlds`의 항목은 `{ worldId, name, congestion }`이고 월드 번호 순이다.
`congestion`은 `SMOOTH`, `NORMAL`, `CROWDED` 가운데 하나다. `host`는 IPv4 주소다. 실패 응답은 `{ ok: false, error: { code, message } }`다.
`message`는 클라이언트가 화면에 그대로 보여 주는 한국어 문장이다. 클라이언트는 분기할 때 `message`가 아니라 `code`를 본다.

| 상태 | `code` | 경우 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | 본문이 JSON이 아니거나, 로그인 ID 또는 비밀번호가 형식 규칙에 맞지 않음 |
| 400 | `VALIDATION_FAILED` | 월드 선택의 `worldId`가 1 이상의 32비트 정수가 아님 |
| 401 | `INVALID_CREDENTIALS` | 로그인 ID가 없거나 비밀번호가 틀림 |
| 401 | `LOGIN_SESSION_EXPIRED` | 로그인 세션이 없거나, 만료됐거나, `Bearer` 형식이 아님. 클라이언트는 다시 로그인한다 |
| 403 | `ACCOUNT_BANNED` | 정지 중. 로그인과 월드 선택이 돌려준다. `error.bannedUntil`에 해제 시각(UTC 기준 ISO 8601 형식) |
| 404 | `NOT_FOUND` | 없는 경로 |
| 409 | `DUPLICATE_LOGIN_ID` | 회원가입한 로그인 ID가 이미 있음. 대소문자만 다른 것도 같은 로그인 ID다 |
| 409 | `WORLD_UNAVAILABLE` | 고른 월드의 항목이 없음. 그 월드의 게임 서버가 꺼졌거나 항목이 만료됐다 |
| 500 | `INTERNAL_ERROR` | 그 밖의 모든 실패. 에러 원문은 서버 로그에만 남긴다 |

형식 규칙은 로그인 ID가 영문 소문자와 숫자 4~10자(소문자로 바꾼 뒤 검사), 비밀번호가 영문과 숫자 4~20자다.
비밀번호에 특수문자를 쓰지 못한다는 불만이 나오면 비밀번호 규칙을 다시 본다.

**API Boundary(게임 서버):** Redis의 키 세 종류다. 게임 서버가 월드 집합과 월드 항목을 쓰고, 인증 서버가 인증 티켓을 쓴다.
아래 표가 티어 간 계약이다. JWT는 쓰지 않는다. 게임 서버 말고도 인증 티켓을 검증해야 하는 티어가 생기면 이 결정을 다시 본다.
로그인 세션(`loginSession:{값}`, 값은 계정 번호, TTL 1시간)도 Redis에 있지만 인증 서버만 읽고 쓴다.

| 키 | 값 | TTL | 쓰는 쪽 → 읽는 쪽 |
|---|---|---|---|
| `worlds` (집합) | 월드 번호의 10진수 문자열 | 없음 | 게임 서버가 기동할 때 자기 번호를 넣음 → 인증 서버 |
| `world:{worldId}` (해시) | 필드 `name`(UTF-8), `host`(IPv4), `port`, `congestion`(`SMOOTH`·`NORMAL`·`CROWDED`) | 15초. 게임 서버가 5초마다 다시 씀 | 게임 서버 → 인증 서버 |
| `authTicket:{worldId}:{티켓}` | 계정 번호의 10진수 문자열 (예: `"42"`) | 30초. 환경 변수 `TICKET_TTL_SECONDS`로 바꾼다 | 인증 서버 → 그 월드의 게임 서버가 소비 |

- 티켓은 `crypto.randomUUID()`가 만든 UUID 문자열이다. 키에 월드 번호가 들어가므로 다른 월드의 게임 서버는 그 티켓을 찾지 못한다
- 소비는 게임 서버가 값을 읽고 키를 지우는 것이다. 키를 실제로 지운 쪽만 통과한다
- 월드 항목이 없는 월드는 목록에서 빠진다. 게임 서버가 꺼지면 집합에 번호가 남아도 15초 안에 목록에서 빠진다
- 혼잡도는 게임 서버가 연결된 계정 수를 자기 정원에 비춰 정한다. 정원의 50% 미만이면 `SMOOTH`, 80% 미만이면 `NORMAL`,
  그 이상이면 `CROWDED`다. 인증 서버와 클라이언트는 정원을 모르고, 혼잡도는 월드 선택을 막지 않는다
- 게임 서버는 월드 항목의 쓰기와 TTL을 한 트랜잭션(`MULTI`/`EXEC`)으로 보낸다. 둘 사이에 죽으면 TTL 없는 항목이 남아 꺼진 월드가
  목록에 계속 보인다. 인증 서버는 형식이 틀린 항목을 목록에서 빼고 서버 로그에 남긴다

소비에 쓰는 Redis 명령은 계약에 넣지 않는다. 이 머신의 Redis는 3.0이라 `GETDEL`(6.2부터)이 없고, `GET` 뒤에 `DEL`을 부르고
`DEL`이 1을 돌려준 쪽만 통과시키면 같은 일회성이 지켜진다. 같은 티켓으로 두 요청이 동시에 와도 `DEL`이 1을 돌려주는 것은 한 번뿐이다.

티켓의 TTL은 월드 선택 응답부터 로비 접속까지의 유효 시간이고, 게임 세션의 길이와 무관하다.
이 머신의 Redis는 3.0이라 `HSET`이 필드를 하나만 받는다. 게임 서버는 월드 항목을 `HMSET`으로 쓴다.

### Server/GameServer

게임 서버는 위 「Server/AuthServer」 절의 Redis 계약을 따른다. 게임 서버 하나가 월드 하나를 맡는다. 월드 번호, 이름, 접속
주소, 정원은 게임 서버 설정(`Core/Config`, 환경 변수 `P1_WORLD_*`)이다. `Network/WorldListing`이 기동할 때 월드 집합에 번호를
넣고, 접속을 받기 시작한 뒤 갱신 스레드가 5초마다 월드 항목을 다시 쓴다. 인증 티켓은 `Network/AuthTicket`이 이 서버의 월드
키로만 소비해 계정 번호로 읽는다. 클라이언트는 로비 접속(`C_CONNECT_LOBBY.auth_ticket`)에 티켓을 담아 보낸다. 게임 서버에는
로그인이 없다.

**Architecture Invariant:** 인증 서버의 DB를 모른다. 로비 접속의 계정 확인은 Redis의 인증 티켓을 되읽어서 하고,
계정 정보를 DB에서 직접 조회하지 않는다.

**Architecture Invariant:** 룸 소유 상태 변경은 그 룸의 큐 위에서만 일어난다. 락이 없다.
`Room`이 `JobQueue`를 상속하고, 패킷 핸들러는 룸 상태를 직접 바꾸지 않고 `DoAsync`로 잡을
밀어넣는다. **다른 룸의 오브젝트에 직접 손대지 않는다.**
`JobQueue::Push`는 큐가 비어 있고 그 스레드가 다른 큐를 실행하고 있지 않으면 잡을 그 자리에서 실행한다.
그래서 대개 같은 IOCP 워커가 룸 잡까지 실행한 뒤에 핸들러에서 돌아온다. 룸 잡이 무거우면 IOCP 처리량도 그만큼 준다.
DB 작업도 같은 형태다 — 핸들러가 `DBQueue`에 push하고 전용 DB 스레드가 소비한다
(유저 친화도가 필요한 작업은 id 기반 큐로, 그 외는 랜덤 큐로 보낸다).

**Architecture Invariant:** 요청의 검증은 검증 대상에 따라 자리가 정해져 있다.

| 검증 대상 | 위치 |
|---|---|
| 세션 단계(로비 접속 전, 로비 접속 중, 로비, 게임 입장 중, 게임, 로비 복귀 중) | 세션이 핸들러에 넘기기 전에 단계별 허용표(`SessionPhaseTable`)로 |
| 플레이어 유무 | 패킷 핸들러 |
| 불변 데이터만 보는 형식 검사 | 패킷 핸들러 |
| 룸이나 플레이어 상태 | 룸 큐 |
| 판정 규칙 자체 | 룸과 세션을 모르는 도메인 함수 |

세션 단계는 `GameSession::OnRecvPacket`이 핸들러를 부르기 전에 본다. 받는 패킷마다 받는 단계를 `Network/SessionPhase`의 표
하나로 정하고, 단계에 맞지 않는 패킷은 경고 로그를 남기고 버린다. 표에 없는 패킷은 어느 단계에서도 버린다. 로비 접속은
로비 접속 전 단계에서만, 캐릭터 생성·삭제·선택은 로비 단계에서만, 게임 패킷은 게임 단계에서만 받는다. 캐릭터 선택을 받으면
세션은 게임 입장 중이 되고, 입장 결과의 응답을 보내기 직전에 게임이나 로비로 바뀐다. 게임 입장 중에는 로비 요청을 받지 않는다.
로비 복귀를 받으면 세션은 로비 복귀 중이 되고, 저장이 끝나 로비 복귀 창구가 플레이어를 비운 뒤 로비로 바뀐다. 로비 복귀 중에는
게임 요청도 로비 요청도 받지 않는다.
— 단계를 보지 않던 때는 게임에 입장한 세션이 플레이 중인 캐릭터를 지울 수 있었고, 입장한 세션이 다른 계정의 인증 티켓으로
로비 접속을 다시 보내면 세션의 계정 번호만 바뀌어 접속 종료 저장의 대기가 풀리지 않았다.

보낸 사람은 패킷 안의 id가 아니라 세션의 플레이어로 식별한다. 룸 큐로 넘기는 핸들러는 `DispatchToPlayerRoom`이
세션의 플레이어와 그 소속 룸을 찾아 잡에 넘긴다. 예외는 없다. 맵 로드를 기다리는 플레이어는 들어갈 룸이 소속 룸이므로,
맵 로드 완료도 같은 함수로 그 룸의 큐에 간다. 계정 번호도 핸들러가 세션에서 한 번 읽어 잡에 넘기고, 잡 안에서
다시 읽지 않는다.
— 패킷의 엔티티 번호로 대상을 찾던 이동 요청은 같은 룸의 다른 플레이어를 옮길 수 있었다.

**Architecture Invariant:** `Room`에는 룸 상태를 쓰는 처리(입장, 퇴장, 이동, 전투, 리스폰)만 둔다. 아이템 요청은
`Network/ItemRequests`가, 채팅 요청은 `Network/ChatRequests`가 룸 큐 위에서 처리한다. 아이템 판정은 `Player::Process*`가
결과 구조체나 거절 사유(`ItemOutcome`)로 돌려준다. 응답 패킷은 핸들러 쪽이 판정으로 만든다. 엔티티와 세션의 상태 멤버는 다른 클래스가 직접 읽거나 쓰지 않는다. 읽기는 `const` 참조 getter로,
쓰기는 의도를 드러낸 함수로 한다.

**Architecture Invariant:** 패킷 핸들러는 전용 스레드가 아니라 **IOCP 워커 스레드에서 돈다.**
워커는 `WORKER_TICK` 예산 안에서 IOCP 디스패치 → 예약 잡 분배 → 글로벌 큐 소비를 반복한다.
워커 풀과 DB 풀은 별개이고, **메인 스레드가 워커 풀의 마지막 하나로 합류한다.**
핸들러 안에서 블로킹하면 IOCP 처리량이 그만큼 줄어든다.

**Architecture Invariant:** DB 접근은 DAO가 데이터별로 맡는다. 로비의 DAO(`GameDB`의 계정 행과 캐릭터 행)는 `Lobby/`에,
게임의 DAO는 `DB/`에 있다. 게임의 DAO는 로비의 DAO를 부르지 않는다. SQL을 실행하는 클래스만 DAO라고
부른다. 여러 DAO를 차례로 부르는 `ProgressStorage`는 DAO가 아니다. DAO는 세션과 패킷을 모른다. 연결은
DB 잡이 `DBConnectionGuard`로 빌려 DAO에 넘기고, 잡이 어떻게 끝나든 풀로 돌려준다. 접속 종료 저장 하나는
트랜잭션 하나다. DB 아이템 행과 패킷 칸 사이의 변환은 DB를 모르는 `ItemRows`가 맡고, 불러오기와 저장이 이 변환 하나를 쓴다.
— 두 방향이 다른 변환을 쓰면 아이템이 다른 구역이나 부위로 옮겨 가거나 사라진다. 그래서 이 변환만 떼어 테스트한다.
DAO의 바인딩과 흐름은 가짜 연결(`GameServerTests/FakeDBConnection.h`)로, SQL 문장은 `GameDB_Test`에 붙는 실제 DB 테스트로 테스트한다.

**Architecture Invariant:** DB 작업의 실패는 `DBError` 예외이고, 클라이언트에 보낼 거절(캐릭터 생성의 이름 중복 등)은
예외가 아니라 결과다. DB 잡은 `DBError`를 포함한 표준 예외를 받아 실패 응답을 보내고, 접속 종료 저장 잡은
저장 대기를 푼다. DB 스레드(`DBWorker::RunJob`)는 잡이 던진 예외를 종류에 상관없이 받아 로그를 남기고 다음 잡을 돌린다.
— 잡 밖으로 나간 예외는 `std::terminate`로 서버 전체를 내린다.

**Architecture Invariant:** 입장은 진행을 모두 불러오고 검증을 통과한 뒤에야 세션에 플레이어를 등록한다
(`GameEntry`). DB 스레드는 불러오기에서도 살아 있는 `Player`를 만지지 않고 진행 사본(`PlayerProgress`)만 채운다.
근거는 `docs/adr/0012-load-and-save-one-progress-copy.md`에 있다.

**Architecture Invariant:** 맵이 바뀌는 입장(게임 입장, 다른 맵으로 가는 포털, 다른 맵으로의 리스폰)은 맵 로드 절차 하나를 따른다.
서버는 플레이어를 앞 룸에서 빼고 들어갈 맵을 응답에 실어 보낸다. 플레이어는 어느 룸에도 넣지 않고, 위치와 맵을 목적지의 것으로
바꾼 뒤 들어갈 룸을 소속 룸으로 정해 둔다(`Player::BeginMapLoad`). 클라이언트가 그 맵을 다 열었다고 알리면
(`C_MAP_LOAD_COMPLETE`) 그 룸의 큐가 플레이어를 넣는다. 맵 로드를 기다리는 동안 온 룸 요청은 그 룸에 없는 플레이어의 요청이라
버리고, 기다리지 않는 플레이어의 로드 완료도 버린다. 같은 맵 안의 포털 이동과 리스폰은 맵 로드 없이 곧바로 목적지 룸의 큐에 입장을
넣는다. 사망한 룸으로 리스폰해도 퇴장과 입장을 거친다. 맵 로드 시간 제한은 없다.
— 맵 간 이동이 맵 입장 요청과 룸 입장 요청 두 단계로 나뉘어 있던 때는 첫 입장만 맵을 연 뒤에 들어갔고, 맵 간 이동은
클라이언트가 보내지 않는 경로로 남아 있었다. 첫 입장의 들어갈 룸 번호를 IOCP 스레드가 읽고 룸 큐가 써서 둘이 같은 큐에 있지
않았다.

**Architecture Invariant:** 룸 입장 응답(`S_ENTER_ROOM`)은 그 룸에서의 내 엔티티를 싣고, 스폰(`S_SPAWN`)은 다른 엔티티만
싣는다. 게임 입장 응답(`S_ENTER_GAME`)은 맵 번호와 내 캐릭터의 개인 정보(이름, 직업, 레벨, 스탯, 골드, 소지품, 퀵슬롯)를 싣는다.
맵을 여는 동안 만들어지는 화면이 이 값을 읽는다.

**Architecture Invariant:** DB를 거치는 요청(로비 접속, 캐릭터 생성·삭제, 입장)은 핸들러가 `DBQueue`에 잡을 넣는다.
계정을 아는 요청은 계정 번호로 고른 큐(`GetDBQueueFromId`)에 넣어 한 계정의 DB 잡이 순서대로 돈다. 로비 접속만
계정을 모르는 채로 시작하므로 랜덤 큐에 넣고, 그 잡 안에서 인증 티켓 확인, `GameDB` 계정 행 기록, 캐릭터 목록
불러오기를 이어 한다. 계정 행은 이 월드에 처음 들어올 때 만들어지고, 캐릭터 슬롯 수의 원천이다.

**Architecture Invariant:** 한 계정은 세션 하나만 갖고, 나중에 온 로비 접속이 이긴다. `Handle_C_CONNECT_LOBBY`는
Redis의 인증 티켓 키를 읽고 지우며, 키를 지운 쪽만 통과한다. 통과하면 배선 함수 `GSessionManager->BindAccount`가
계정에 세션을 묶고, 앞 세션이 있으면 진행 조율자에 알린 뒤 밀어낸다. 로비는 계정 번호와 세션만 넘기고 진행 조율자와
플레이어를 모른다. 확인과 교체(`RegisterUser`)는 관리자의 락 하나 안에서 한다. 로비 접속 잡은
랜덤 DB 큐에서 돌아서 같은 계정의 로비 접속이 동시에 올 수 있기 때문이다. 밀려난 세션에는
`S_DISCONNECT(DUPLICATE_CONNECTION)`을 보내고, 그 패킷의 송신이 끝난 뒤에 끊는다(`Session::DisconnectAfterSend`).
로비 접속이 실패해도 같은 방식으로 `S_CONNECT_LOBBY`의 결과를 보낸 뒤 끊는다.
상대가 받지 않아 송신이 끝나지 않으면 1초 뒤에 끊는다. 그 세션의 저장은 아래의 접속 종료 경로를 탄다.
서버가 건 끊기(`DisconnectEx`)는 상대가 소켓을 닫아야 끝나므로, `Session::DISCONNECT_TIMEOUT_MS`(1초) 안에 끝나지 않으면
세션이 소켓을 닫아 `OnDisconnected`까지 가게 한다. 이 상한은 서비스의 타이머 큐로 예약하고 워커의 `JobTimer` 분배로 돈다.
— 끊기가 끝나지 않으면 저장 대기가 풀리지 않아 그 계정은 서버를 다시 띄울 때까지 입장하지 못한다.

**Architecture Invariant:** 캐릭터를 다루는 요청(입장, 삭제)은 그 계정이 가진 캐릭터에만 동작한다.
클라이언트가 보낸 `character_id`를 믿지 않고, SQL이 세션의 계정 번호를 `Character.AccountId`와 함께 대조한다. 생성 요청은
`Handle_C_CREATE_CHARACTER`가 `CharacterCreation::Validate`로 먼저 거른다. 캐릭터 선택은 로비가 받아 그 계정의 삭제되지
않은 캐릭터인지 확인한 뒤 계정 번호와 캐릭터 번호만 게임 입장 창구(`GameEntry::RequestEnter`)로 넘긴다. 저장 대기,
불러오기, 룸 배정은 게임 쪽이 한다. 불러오기의 SQL도 계정 번호를 다시 대조한다.

**Architecture Invariant:** 진행 행이 없는 캐릭터는 아직 게임에 입장한 적이 없는 캐릭터다. 로비의 캐릭터 생성은 `Character` 행만
쓴다. 게임 입장의 불러오기(`ProgressStorage::Load`)는 진행 행(`CharacterState`와 골드의 `CharacterCurrency`)이 없으면 같은
트랜잭션에서 초기 진행 행을 만들고 이어서 불러온다. 초기 진행의 시작 맵, 위치, 방향, 골드는 게임의 초기 진행 표에서, HP와 MP는
그 직업 레벨 표의 1레벨 행에서 온다. 로비와 게임은 서로의 기획 데이터를 읽지 않는다. 생성할 수 있는 직업마다 레벨 표가 있는지는
서버가 기동할 때 `Core/DataCrossCheck`가 대조하고, 어긋나면 서버가 뜨지 않는다.
— 로비가 진행 행까지 쓰면 직업별 레벨 표, 재화 표, 맵 표를 읽어야 해서 기획 데이터를 소비자별로 나눌 수 없다. 근거는
`docs/adr/0021-split-lobby-as-top-level-module.md`에 있다.

**Architecture Invariant:** 캐릭터는 소프트 삭제한다. 삭제는 `Character.DeletedAt`만 적고 그 캐릭터의 다른 행은 남긴다.
슬롯 한도와 캐릭터 목록은 삭제하지 않은 캐릭터만 센다. 이름의 고유 인덱스(`UX_Character_Name_Active`)도 삭제하지 않은
캐릭터만 덮으므로, 삭제한 캐릭터의 이름은 바로 다시 쓸 수 있다. 삭제한 캐릭터를 되살리는 경로는 없다.
— 삭제한 캐릭터를 복구해 달라는 요구가 나오면 이 결정을 다시 본다.

**Architecture Invariant:** 캐릭터 이름의 중복은 미리 조회하지 않는다. 생성 쿼리 안의 `TRY...CATCH`가 고유 인덱스 위반(2601)을
「이름 중복」 결과로 바꾼다.
— 미리 조회하면 조회와 생성 사이에 같은 이름의 생성이 끼어들 수 있다. C++에서 ODBC 진단 기록으로 판정하면 이름이 겹칠
때마다 `DBConnection`이 DB 오류 로그를 남긴다.

**Architecture Invariant:** 캐릭터 이름은 최대 32자이고, 이 한도를 기획 데이터로 옮기지 않는다.
— 한도는 DB 열(`NVARCHAR(32)`)의 크기에 묶여 있어서, 기획이 바꿀 수 있는 값이 아니다. 기획이 이름 길이를 바꾸고 싶어 하면
이 결정을 다시 본다.

**Architecture Invariant:** 아이템의 컨테이너는 서버 C++ enum `ItemContainer`이고 DB에 그 값이 들어간다. 1은 인벤토리,
2는 착용 장비다. 인벤토리는 컨테이너 하나이고, 그 안의 구역은 `Item.ItemType`으로 나뉜다. 값을 바꾸거나 다시 쓰지 않는다.
— DB에 저장된 값이므로, 번호를 바꾸면 이미 저장된 아이템이 다른 컨테이너로 읽힌다.

**Architecture Invariant:** 장비의 추가 공격력은 DB에 없다. 패킷에는 0을 채우고 저장할 때 버린다. `ItemGearOption` 테이블은
쓰지 않고, `ItemGear.Durability`에는 0을 넣는다.
— 장비 옵션 기능을 만들기 시작하면 이 결정을 다시 본다.

**Architecture Invariant:** 경험치는 누적값이 원천이다. `CharacterState.Exp`에 누적 경험치를 저장하고, 레벨은 입장할 때
레벨 표로 다시 계산한다. `Character.Level`은 캐릭터 목록이 읽는 사본이고, 저장할 때 계산한 레벨로 덮어쓴다. 최대 레벨을
넘는 누적값은 잘라 쓰고 경고를 남긴다. 클라이언트에는 레벨 안의 경험치를 보낸다. 사망 페널티는 그 레벨 요구치의 10%이고,
레벨 안에 쌓인 양보다 많이 잃지 않으므로 레벨이 내려가지 않는다.
— 레벨과 레벨 안의 경험치를 따로 저장하면 기획이 레벨 표를 바꿀 때 두 값이 어긋난다. 레벨 표가 바뀌어도 기존 캐릭터의
레벨은 그대로여야 한다는 요구가 나오면 이 결정을 다시 본다.

GameDB의 표현과 패킷의 표현이 다른 곳(아이템의 자리, 골드, 맵과 룸, 경험치, 장비의 추가 공격력)은 게임 서버가 바꾼다.
프로토콜을 다시 짤 때까지 `.proto`는 DB에 맞추지 않는다. 차이와 바꾸는 함수의 목록은
`docs/work/2026-10-20-game-db.md`의 「패킷과 DB 사이의 변환 지점」에 있다.

**Architecture Invariant:** 룸 퇴장과 진행 저장은 접속 종료(`GameSession::OnDisconnected`)와
로비 복귀(`C_RETURN_TO_LOBBY`의 핸들러) 두 경로에서만 시작하고, 두 경로는 같은 저장 절차
(`ProgressCoordinator`의 `LeaveGameAndSave`)를 쓴다. 사용자가 게임을 끄면 클라이언트는 소켓만 닫고, 서버는 그 끊김을 접속 종료 경로로 처리한다.
저장은 룸 큐 위에서 뜬 `PlayerSaveData` 사본으로 하고, DB 스레드는 살아 있는 `Player`를 읽지 않는다.
저장 잡은 입장 불러오기와 같은 `userId` 큐에 넣는다.
— 경로가 하나면 정상 종료와 크래시, 네트워크 단절이 같은 처리를 받는다. 로비 복귀는 연결을 유지하므로 접속 종료를
탈 수 없다. 그래서 퇴장과 저장, 사망한 채 떠난 플레이어의 마을 리스폰, 저장 대기를 접속 종료와 함께 쓰고, 저장 뒤의
일만 다르게 한다. 로비 복귀는 저장이 끝난 뒤 로비 복귀 창구(`LobbyReturn::Accept`)가 세션을 로비로 받고 캐릭터 목록을
보낸다. 복귀 중에 연결이 끊기면 접속 종료가 같은 플레이어로 저장 절차를 다시 부르지만, 진행 표시가 이미 바뀌었고 플레이어가
이미 룸에서 빠졌으므로 저장은 한 번만 돈다.

**Architecture Invariant:** 접속 종료 저장이 끝나기 전에는 같은 계정의 입장 불러오기를 하지 않는다.
같은 큐에 넣는 것만으로는 부족하다. 저장 잡은 룸 큐를 거쳐 늦게 들어가므로 새 세션의 불러오기가 먼저
들어갈 수 있다. 그래서 `SaveGate`가 계정마다 저장 대기를 표시한다. 대기를 걸고 푸는 곳은 진행 조율자
`ProgressCoordinator` 하나다. 접속 종료(`GameSession::OnDisconnected`), 로비 복귀(`C_RETURN_TO_LOBBY`의 핸들러), 같은 계정의 새 로비 접속(`GameSessionManager::BindAccount`), 입장 요청
(게임 입장 창구 `GameEntry::RequestEnter`)은 조율자의 함수를 하나씩만 부르고, 저장 대기를 직접 다루지 않는다. 대기는 플레이어가 있는
세션을 밀어낼 때와 플레이어가 있는 세션이 끊길 때 걸고, 저장 잡이 끝나면 푼다. 룸에 들어간 적이 없는 플레이어는
저장하지 않으므로 접속 종료가 대기를 곧바로 푼다. 대기 중에 온 `C_ENTER_GAME`은 불러오기를 하나만 맡겨 두고
저장 잡이 끝난 뒤 그 자리에서 실행한다. 5초 안에 풀리지 않으면 그 입장을 거절하되 대기는 저장이 끝날 때까지 남긴다.
두 시간 제한은 룸 큐가 아닌 `GSessionJobQueue`에서 돈다. 로비 복귀는 캐릭터 목록을 보내는 일을 같은 자리에 맡겨 두고
만료 시간을 두지 않는다. 기다리는 저장이 그 세션의 것이고, 저장 잡은 실패해도 대기를 풀기 때문이다. 그 자리에 다른 연결의
입장이 먼저 맡겨져 있으면 이 세션은 밀려나 곧 끊기므로 로비로 받지 않는다.

**Architecture Invariant:** 접속 종료와 첫 룸 입장 중 무엇이 먼저였는지는 플레이어의 진행 표시(`Player::Presence`)
하나로 정한다. 세션 스레드의 `MarkDisconnected`와 룸 큐의 `MarkEnteredRoom`이 같은 atomic 값을 읽고 바꾸는 일을
한 번에 한다. 첫 룸 입장 전에 끊긴 플레이어는 룸 입장 잡이 저장하지 않고 빼기만 하고, 룸에 들어간 뒤 끊긴
플레이어는 소속 룸 큐나 들어갈 룸 큐가 저장한다. 다른 맵의 로드를 기다리다 끊긴 플레이어는 기다리던 룸의 큐가 저장한다.
접속 종료가 소속 룸을 읽은 뒤에 플레이어가 다른 맵으로 떠났으면, 떠난 룸 큐의 저장 잡이 바뀐 소속 룸의 큐로 넘긴다. 저장 잡은 대기를 풀기 직전에 표시를 `SAVED`로 바꾼다. 끊긴 세션이 계정
등록에서 빠지기 전에 온 새 로비 접속은 그 세션을 밀어내며 대기를 거는데, 표시가 `LEFT_BEFORE_ROOM`이나 `SAVED`면 풀어 줄
접속 종료가 이미 지나갔으므로 그 자리에서 푼다.
— 판정이 두 곳에 나뉘어 있던 때는 첫 룸 입장 잡이 대기 없이 저장을 넣어, 그사이 입장한 새 세션의 불러오기 뒤에
저장이 돌았다(TD-003).

**Architecture Invariant:** 서버 종료도 접속 종료 경로로 저장한다. 종료 전용 저장 경로를 만들지 않는다. 콘솔 종료 신호
(Ctrl+C, 창 닫기, 로그오프)를 받으면 메인 스레드가 워커 루프를 빠져나와 `GameServer.cpp`의 `Shutdown`을 돈다. 리스너를
닫고, 세션을 모두 끊고, 세션이 다 빠질 때까지 기다리고, 룸 큐를 두 바퀴 비우고, DB 큐를 멈춰 남은 저장을 다 돌린 뒤
스레드를 합류시킨다. 그동안 나머지 워커가 끊기 완료와 룸 잡을 처리한다.
— 창 닫기 신호는 처리기가 돌아가는 즉시 프로세스를 끝내므로, 처리기는 종료 절차가 끝날 때까지 기다린다. 시스템은 약 5초
뒤에 프로세스를 끝내므로 세션 대기는 2초, 룸 큐 대기는 바퀴마다 1초가 상한이다. 룸 이동 중에 끊긴 플레이어는 떠난 룸이
들어갈 룸 큐로 넘긴 뒤에 저장되므로 룸 큐를 한 바퀴만 비우면 놓친다.

**Architecture Invariant:** 몬스터의 `S_DIE`는 디스폰을 겸한다. 서버는 사망한 몬스터를 룸에서 곧바로
지우고 `S_DESPAWN`을 보내지 않는다. 클라이언트의 `AP1Monster`가 사망 애니메이션을 보여 준 뒤 스스로
지운다. 플레이어의 `S_DIE`는 디스폰을 겸하지 않는다. 사망한 플레이어는 리스폰할 때까지 룸에 남는다.
— 서버가 몬스터에 `S_DESPAWN`을 보태면 사망 애니메이션이 끝나기 전에 액터가 사라진다.

**Architecture Invariant:** 피격과 처치는 `Game/Combat/`이 판정한다. 판정은 룸과 세션을 모른다.
룸은 공격자가 아직 룸에 있는지 대조하고, 대상을 찾고, 결과를 패킷으로 보낸다.
— 판정이 룸에 묶여 있으면 룸 큐와 세션 없이는 테스트할 수 없다.

**Architecture Invariant:** 리스폰 요청은 사망한 플레이어의, 게임 서버가 지원하는 유형(지금은 마을 리스폰뿐)만
받는다. 룸 이동과 리스폰 요청의 판정은 `Game/Room/RoomTransfer`가 맡고 룸 큐와 세션을 모른다. 퇴장과 입장,
목적지 룸의 큐로 넘기기와 결과 전송은 룸이 맡는다. 판정으로 거절한 요청에는 실패 응답을 보낸다.
— 검증이 없던 때는 살아 있는 플레이어가 어디서든 마을로 이동했고, 목적지가 없는 유형이 서버를 죽였다.

**Architecture Invariant:** 아이템 요청(판매·착용·해제·사용)은 칸 주소(컨테이너 종류, 칸 번호)와 클라이언트가 그 칸에서 본
아이템의 `item_uid`로 칸을 가리킨다. 서버는 그 칸에 든 아이템으로 판정하고, `item_uid`는 클라이언트의 칸이 어긋났는지 대조하는
데만 쓴다. 칸이 비었거나 `item_uid`가 다르면 `ITEM_RESULT_SLOT_CHANGED`로 거절한다. 착용과 해제는 상태를 바꾸기 전에 거절해서, 모두 성공하거나 아무것도
바꾸지 않는다. 구매는 아이템 표에 있는 번호만 받는다. 기획 데이터 표는 `Gamedata`의 private 멤버이고 `Find*`로만
조회한다.
— 요청이 칸 사본을 싣고 서버가 그 사본의 아이템으로 판정하던 때는 싼 아이템을 비싼 번호로 팔거나, 아무 장비나 입거나,
해제하며 다른 아이템을 받을 수 있었다.

**Architecture Invariant:** 아이템 응답(구매·판매·사용·착용·해제)은 바뀐 칸을 칸 변경(`SlotChange`) 목록 하나로 싣는다.
칸 변경은 「이 주소의 칸은 이제 이 내용이다」만 뜻하고, 아이템이 없으면 그 칸이 비었다는 뜻이다. 추가와 수정과 삭제를
가르는 표시는 없다. 착용과 해제의 스탯은 칸 변경과 따로 싣는다. 입장 패킷은 컨테이너마다
빈 칸을 포함한 모든 칸을 싣는다. 착용 장비 컨테이너의 칸 번호는 장비 부위 값이고 0번 칸이 없다.

**Architecture Invariant:** 아이템 응답은 요청한 플레이어에게만 가고, 1번 필드의 아이템 결과(`ItemResult`)가 성공과 거절
사유를 싣는다. 세션 단계에 맞는 아이템 요청에는 거절해도 응답하고, 거절한 응답은 칸 변경과 스탯을 싣지 않는다. 응답은 엔티티
번호를 싣지 않는다. 착용과 해제의 외형(장비 부위와 그 부위의 아이템)은 응답이 아니라 통지 `S_GEAR_APPEARANCE`가 착용한
플레이어를 포함한 룸의 모든 플레이어에게 알린다.
— 응답의 성공 여부가 참과 거짓뿐이던 때는 클라이언트가 거절 사유를 알 수 없었다. 외형을 응답에 함께 실어 룸에 보내던 때는
다른 플레이어도 칸 변경을 받을 뻔했고, 응답의 엔티티 번호로 내 응답인지 가려야 했다.

**Architecture Invariant:** 퀵슬롯은 컨테이너도 칸도 아니다. 아이템 하나가 아니라 아이템 정의를 가리키는 참조(종류와 id)이고,
지금 종류는 아이템 정의 하나다. 착용 장비는 칸 주소를 쓰는 독립 컨테이너이고, 퀵슬롯은 칸 주소 체계에 들어가지 않는다.
퀵슬롯 개수는 기획 데이터의 퀵슬롯 표(`S_Quick_Slot.json`) 한 곳에서 오고, 클라이언트는 입장 패킷에 실린 퀵슬롯 수를 쓴다.
입장 패킷은 빈 퀵슬롯도 싣는다. 등록 요청(`C_SET_QUICK_SLOT`)은 퀵슬롯 번호와 참조 하나이고, 참조가 없으면 해제다.
같은 참조는 퀵슬롯 하나에만 있다. 그래서 다른 퀵슬롯에 있던 참조를 등록하면 두 퀵슬롯이 맞바뀌고, 응답(`S_SET_QUICK_SLOT`)은
바뀐 퀵슬롯을 모두 싣는다. 서버는 등록할 대상이 소모품인지만 보고 소지 여부는 보지 않는다. 다 떨어진 소모품도 등록이 남는다.
퀵슬롯 등록은 진행이다. 접속 종료 저장의 트랜잭션 안에서 아이템 다음에 퀵슬롯 전체를 MERGE하고, 빈 퀵슬롯은 행을 두지 않는다.
불러온 등록 중 넣을 수 없는 행(범위 밖 번호, 소모품이 아닌 대상, 겹친 대상)은 경고를 남기고 버린 채 입장시킨다.
— 소지 여부를 보면 개수가 0인 퀵슬롯끼리 자리를 바꾸는 요청이 거절된다. 아이템과 달리 퀵슬롯은 버려도 잃는 것이 없으므로,
기획이 퀵슬롯 개수나 아이템 종류를 바꿨다고 입장을 막지 않는다.

**Architecture Invariant:** 퀵슬롯 사용 요청(`C_USE_QUICK_SLOT`)은 퀵슬롯 번호만 싣는다. 서버가 소모품 구역에서 그 소모품이
든 칸 중 칸 번호가 가장 작은 칸을 고르고, 칸을 가리킨 사용과 같은 판정(`Player::ProcessUseItem`)으로 넘긴다. 응답도 같은
`S_USE_ITEM`이다.
— 사망과 재사용 대기 같은 사용 규칙이 두 곳으로 갈라지지 않는다. 클라이언트도 응답 대기를 칸 사용과 함께 쓴다.

**Architecture Invariant:** 소모품의 재사용 대기도 게임 서버가 템플릿마다 판정하고, 인벤토리 컴포넌트의 메모리에만 두어
접속이 끊기면 사라진다. 클라이언트의 재사용 대기 표시는 보여 주기만 한다.

**Architecture Invariant:** 서버 오브젝트는 복제되는 엔티티 상태(엔티티 정보, 위치, 스탯)만 protobuf 메시지로 들고, DB 계층(DAO와
진행 사본 `PlayerProgress`)은 protobuf를 모른다. 엔티티 상태의 복제는 변환이 아니라 복사다. 복제되는 상태 필드를 서버 클래스에
더하는 것은 곧 프로토콜 변경이다. 아이템과 칸, 플레이어의 맵 번호와 룸 번호처럼 복제하지 않는 상태는 서버 전용 타입과 필드로 들고,
패킷을 만드는 자리에서 바꾼다. 근거는 `docs/adr/0019-hold-item-state-in-tier-own-types.md`에 있다.
— DB 계층이 Protocol 타입을 쓰면 프로토콜을 다시 짤 때 DAO와 저장 사본까지 함께 바뀐다.

**Architecture Invariant:** 틱은 룸이 소유한다. 룸 틱(`Room::Tick`)이 `ROOM_TICK_INTERVAL_MS`마다 셀 갱신, 엔티티
`Tick`, 몬스터 위치 전송을 이 순서로 한 잡 안에서 돈다. 엔티티와 컴포넌트는 `DoTimer`로 자기 일을 예약하지 않는다.
틱보다 긴 주기(몬스터의 상태 전환 판정, 피격 판정)는 누적 시간으로 센다. 그래서 룸의 타이머 잡 수는 몬스터 수와 무관하다.
근거는 `docs/adr/0011-tick-entities-from-room.md`에 있다.

**Architecture Invariant:** 몬스터는 대상이 자기 룸에 있을 때만 대상의 상태(위치, 사망)를 읽는다. `MonsterAIComponent`가
틱마다 이것부터 확인하고, 피격 판정 시점에도 대상과의 거리를 다시 본다.
— 대상 확인이 200ms 판정에만 있던 때는 그사이의 틱이 다른 룸 큐가 쓰는 위치를 읽었다.

**Architecture Invariant:** `GRoomManager`는 부팅 때 `CreateAllRooms`로 모든 룸을 한 번 만들고, 그 뒤로는 `FindRoom`으로
조회만 한다. 룸 목록이 바뀌지 않으므로 조회에 락이 없다. 룸은 `Room::Create`로만 만든다. 엔티티는 룸 관리자를 부르지 않는다.
마을 리스폰의 목적지는 `RoomTransfer::FindTownRespawn`이 맵 표에서 찾는다.
— 사망한 채 끊긴 플레이어의 저장은 룸에서 뺀 뒤에 뜨므로, 리스폰 규칙이 소속 룸이나 룸 객체에 기대면 실패한다.

**Architecture Invariant:** 이동 요청(`C_MOVE`)의 위치는 `MoveValidation`이 판정한다. 직전에 받아들인 위치에서 평면 거리가
최대 속도(500) × 경과 시간 × 1.5 + 50을 넘거나 룸 경계 밖이면 패킷을 버리고 서버의 위치를 그대로 둔다. 경과 시간은 서버가
위치를 정했거나(룸 입장, 리스폰) 이동을 받아들인 시각부터 잰다. 높이는 보지 않는다. 버린 이동은 보낸 클라이언트에 알리지 않는다.
— 클라이언트가 보낸 위치를 그대로 쓰면 조작한 클라이언트가 룸 안 어디로든 순간이동하고, 그 위치로 저장된다.

**Architecture Invariant:** 위치에 묶인 룸 이동 요청은 서버가 플레이어 위치로 판정한다. 포털 이동은 플레이어와 포털 출발
위치의 평면 거리가 맵 기획표의 `portalRadius` 안이어야 한다. 목적지가 다른 맵이어도 같다. 판정은 `RoomTransfer`가 한다.

`Room`은 몬스터의 근접 탐색을 위해 `CELL_SIZE` 단위 셀 행렬(`CellMatrix`)을 들고, 룸 틱마다 엔티티 `Tick`보다 먼저
다시 채운다. `CellMatrix`는 엔티티 번호와 위치만 아는 공간 색인이고, 탐색 대상인지와 실제 거리는 룸이 판정한다.
브로드캐스트는 셀과 무관하게 룸 전체로 간다.

**Architecture Invariant:** 채팅은 룸 단위로 들린다. `ChatRequests`가 말한 플레이어의 룸 큐에서 메시지를 검사해 결과를 응답하고,
받아들인 메시지를 그 룸에만 브로드캐스트한다. 메시지(`S_CHAT_MESSAGE`)에는 말한 플레이어의 이름을 싣는다.
— 클라이언트의 말풍선이 같은 룸에서 보이는 플레이어에게만 뜨므로 채팅도 같은 범위로 맞춘다. 이름을 싣는 것은 받는 쪽에서
말한 플레이어의 엔티티가 이미 사라졌어도 채팅창에 이름을 보여 주기 위해서다. 맵 로드를 기다리는 플레이어는 아직 룸에 없으므로
그동안의 채팅을 받지 못한다.

**API Boundary:** 패킷 핸들러. `C_*` 로만 진입한다. 처리 경로는 네 가지뿐이다 —
`DBQueue`(로비 접속·캐릭터 생성/삭제·게임 입장), 룸 큐(그 외 대부분), 혼합, 스텁.
새 핸들러는 이 넷 중 하나에 들어가야 한다. **다섯 번째를 만들지 않는다.** 로비 패킷(로비 접속, 캐릭터 생성·삭제·선택)의
핸들러는 `Lobby/LobbyPacketHandlers.cpp`에, 나머지는 `Network/ServerPacketHandler.cpp`에 정의한다. 새 핸들러는 단계별
허용표에도 더한다. 더하지 않으면 그 패킷은 어느 단계에서도 버려진다.

일부 패킷은 의도적으로 스텁이다(핑/퐁).

### P1 (UE 클라이언트)

**Architecture Invariant:** 네트워크 스레드는 UObject를 절대 만지지 않는다.
`PacketSession`이 소유한 두 `FRunnable` 워커는 바이트를 큐에 쌓기만 하고,
게임 스레드의 수신 펌프가 그것을 비운다.

**Architecture Invariant:** 수신 펌프는 `UP1ConnectionSubsystem`이 코어 티커로 돌린다. 게임 인스턴스 서브시스템이라 레벨과 무관하게 돈다.
게임 인스턴스의 `UWorld`가 `BeginPlay` 전이거나 해체 중이면 그 틱을 건너뛰고 큐를 비우지 않는다. 그래서 레벨 전환 중에 온
패킷은 새 `UWorld`가 준비된 뒤에 처리된다. 레벨 블루프린트에서 펌프를 부르지 않는다.

**Architecture Invariant:** 연결이 끊기면 수신 워커만 `PacketSession`에 끊김 표시를 세운다. 펌프는 표시를
먼저 읽고 큐를 비운 뒤, 표시가 서 있었으면 연결을 정리하고 `UP1ConnectionSubsystem::OnConnectionLost`를
`DISCONNECT_REASON_NONE`으로 알린다. 서버가 `S_DISCONNECT`로 끊으면 그 핸들러가
`UP1ConnectionSubsystem::HandleDisconnect`를 부른다. 이 함수가 연결을 닫고 같은 델리게이트를 그 사유로 알린다.
끊김을 알리는 델리게이트는 이 하나뿐이다. 접속 흐름 서브시스템(`UP1EntryFlowSubsystem`)이 이것을 구독해 사유를 문구로 바꾼다.
월드 선택 단계(로비 접속 응답을 기다리는 중)면 월드 선택 화면에 문구를 알리고, 그 밖의 단계면 로그인 세션을 버리고 로그인 단계로
돌아간다. 게임 중이면 로그인 맵을 열고, 로그인 맵에 있는 단계면 맵을 다시 열지 않고 열린 화면에 문구를 알린다.
수신 워커는 마지막 패킷을 큐에 넣은 뒤 표시를 세우므로 끊기기 직전에 온 `S_DISCONNECT`를 놓치지
않는다. 로비 접속이 거절되면 서버가 결과를 보낸 뒤 끊는다. 접속 흐름 서브시스템은 결과를 받는 즉시 연결을 닫고 결과의
문구를 월드 선택 화면에 띄우므로, 뒤따르는 끊김이 사유 없는 끊김으로 그 문구를 덮지 않는다. 사용자가 게임을 끄는 경로(서브시스템의 `Deinitialize`)는 소켓만 닫고 이 경로를 타지 않는다.
— `Network/`는 끊김과 사유를 알리기만 하고, 화면 문구와 레벨 전환은 접속 흐름 서브시스템이 갖는다.

**Architecture Invariant:** 소켓과 세션은 `UP1ConnectionSubsystem`만 소유한다. 게임 코드는
`FP1PacketSender`로 보내고, 액터가 세션을 직접 잡지 않는다.
`S_*` 핸들러는 그 상태를 소유한 곳을 부른다. 엔티티는 `UP1StatefulEntityManager`가, 내 플레이어의 정보와
소지품은 `UP1MyPlayerData`가, 캐릭터 목록과 로비 요청의 응답은 `UP1LobbySubsystem`이 맡는다. 액터와 위젯에는
멀티캐스트 델리게이트로만 전파된다. 인증 서버와의 HTTP는 `UP1AuthClient`가 맡고 게임 서버를 모른다. 인증 클라이언트는
로그인 세션과 월드 목록의 사본을 갖고, 인증 티켓은 저장하지 않고 월드 선택 결과로 넘긴다. 게임 서버의 주소도 설정에 두지 않고
월드 선택 결과로 받는다.

**Architecture Invariant:** 로그인부터 게임까지의 단계(로그인, 월드 선택, 로비, 맵 로드, 게임)는 `UP1EntryFlowSubsystem`만 갖는다.
로비에서 월드 선택으로 돌아갈 때는 연결을 닫고 남은 로그인 세션으로 월드 목록을 다시 받으며, 다시 로그인하지 않는다.
인증 클라이언트, 연결 서브시스템, 로비 서브시스템은 서로의 함수를 부르지 않고 자기 일의 결과를 델리게이트로 알린다.
로비 서브시스템은 송신 창구로 패킷을 보내고, 입장 응답의 핸들러는 내 플레이어 데이터를 채운다. 두 경우 모두 다른 단계로 넘어가는 일은 하지 않는다. 접속 흐름 서브시스템이 그것을 구독해 허용된 단계 전이만 받고 다음 일을 부른다. 연결 서브시스템은 주소로 연결하고
끊기만 하며, 로비 접속 패킷은 로비 서브시스템이 보낸다. 서브시스템 사이의 의존은 접속 흐름 서브시스템의 `Initialize`에서
`InitializeDependency`로 선언한다.

**Architecture Invariant:** 레벨 전환은 패킷 핸들러 호출 밖에서 일어난다. 접속 흐름 서브시스템이 핸들러에서 온 알림을
받으면 다음 코어 티커 틱에 레벨을 연다. 열 레벨은 서버가 알린 맵 번호로 데이터 설정(`UP1GameDataSettings::MapLevels`)의 표에서
고른다. 표에 없는 맵 번호를 받으면 연결을 끊고 로그인 화면에 사유를 보여 준다. 맵 로드 단계에서 이 게임 인스턴스의 맵이
열리면(`PostLoadMapWithWorld`) 맵 로드 완료를 알리고 게임 단계로 넘어간다. 같은 맵 안의 포털 이동과 리스폰은 레벨을 다시 열지
않는다. 게임 인스턴스와 인게임 컨트롤러는 입장 흐름을 갖지 않는다.
— 레벨을 여는 시점이 패킷 처리 순서에 묶이지 않고 접속 흐름 서브시스템 한 곳에서 정해진다.

**Architecture Invariant:** 내 플레이어의 스탯, 레벨, 골드는 `UP1MyPlayerData`의 `ApplyStat`, `ApplyLevel`,
`ApplyGold`로만 바꾼다. 이 함수들이 사본에 쓰고 델리게이트로 알린다.
— 위젯은 생성될 때 사본을 읽는다. 알리기만 하고 사본을 두면 레벨을 옮긴 뒤 옛 값이 보인다.

**Architecture Invariant:** 위젯과 액터의 블루프린트에는 레이아웃, 스타일, 에셋 참조만 둔다. 게임 로직은
C++에 있고, 블루프린트 그래프에는 이벤트와 함수가 없다. 애님 블루프린트는 예외로, 게임 판정 없이 이동
컴포넌트와 `OnDie`를 읽기만 한다.
— 그래프에 로직이 있으면 검색과 리뷰와 테스트가 닿지 않는다. 블루프린트를 C++로 옮긴 경위는 #120에 있다.

**Architecture Invariant:** 폴더가 도메인으로 갈려 있고 `#include`는 경로를 한정한다.
`P1.Build.cs`의 `PrivateIncludePaths`에는 모듈 루트 `P1/`과 생성물 폴더 `P1/Network`만 남는다.
서버의 `.vcxproj`도 같다. `IncludePath`에는 프로젝트 루트, 솔루션 폴더, 생성물 폴더 `Protocol` 중
그 프로젝트에 필요한 것과 서드파티 경로만 남는다. 프로젝트별 목록은 ADR-0005에 있다.
도메인을 넘는 참조가 `#include` 줄에 드러나므로 **검색 한 번으로 잡힌다.**
> 컴파일러는 경계 위반을 막지 않는다. UBT가 모듈 루트를 include 경로에 넣으므로, 경로만
> 한정하면 어느 도메인이든 부른다. 차단하려면 도메인을 별도 모듈로 나눠야 하고 지금 규모에서는
> 나누지 않는다. 근거는 `docs/adr/0005-drop-include-path-flattening.md`에 있다.

**API Boundary:** `P1/Source/`에는 모듈이 둘이고(`P1`, `ProtobufCore`), protobuf를 아는
경계는 `ProtobufCore`다. 상세는 `docs/build.md`.

### 생성물

**Architecture Invariant:** 패킷 정의와 게임 데이터는 생성물이다.
저장소에 커밋되어 있어 직접 고쳐도 되는 파일처럼 보이지만, 생성기를 다시 돌리면
덮어써진다. **손으로 쓰는 파일은 정해져 있다.**
그 목록과 절차, 목적지는 `docs/codegen.md`.

**Architecture Invariant:** 패킷 접두사가 방향을 정한다. `C_*`는 클라→서버,
`S_*`는 서버→클라이며, 생성기가 이 접두사로 핸들러 테이블을 나눈다.
요청과 응답이 같은 이름을 쓰는 것은 관례이고, 서버가 먼저 보내는 통지에는 짝이 없다.
**접두사만 기능이고 짝은 관례다.**

**Architecture Invariant:** 패킷 번호는 스키마 파일마다 정한 범위 안에서 선언 순서로 매긴다.
한 파일에 패킷을 끼워 넣어도 다른 파일의 번호는 밀리지 않는다. 범위가 겹치거나 모자라면
생성기가 실패한다. 범위와 절차는 `docs/codegen.md`.

## Layering Rules

**클라와 서버의 클래스 계층이 대칭이다.** 서버는 `Entity → Creature → { Player, Monster }`, 클라는
`AP1Creature → { AP1Player, AP1Monster }`다. 클라에는 서버의 `Entity`에 해당하는 클래스가 없고 `AP1Creature`가
`ACharacter`를 상속한다. 서버는 상태를 protobuf로 들고 클라는 그것을 액터에 반영한다.

그래서 게임플레이 변경은 **클라 + 서버 + 프로토콜 3곳을 기본으로 잡는다.**
한쪽만 고치면 어긋나고, 어긋남을 빌드가 잡아주지 않는다.

**하나의 동작을 세 곳에 걸쳐 세로로 자른다.** 프로토콜을 전부 먼저 하고 서버를 전부 하는
방식은 중간 상태가 검증 불가능해진다.

**계층을 자르는 쪽이 이 저장소의 최대 위험이다.** 3곳을 건드리는 구조라 계층별로 자르고
싶어지는데, 그렇게 쓴 테스트는 러너가 잡지 못한다. 통과하면서 실질적으로 아무것도 주장하지 않는다.

### 티어 간 계약

| 계약 | 형태 | 깨지면 |
|---|---|---|
| 인증 ↔ 게임 | Redis의 월드 집합, 월드 항목, 인증 티켓 키의 형태, 값, TTL | 월드가 목록에 안 보이거나, 월드 선택이 통과해도 로비 접속이 실패 |
| 클라 ↔ 인증 서버 | HTTP 경로, 응답 봉투, 실패 코드, 혼잡도 이름 | 로그인이나 월드 선택이 화면에서 멈추거나 엉뚱한 문구가 뜸 |
| 클라 ↔ 게임 서버 | 생성된 패킷 | 빌드는 통과하고 런타임에 어긋남 |
| 게임 서버 ↔ GameDB | 마이그레이션 파일(`Server/GameServer/Migrations/`) | 부팅 또는 첫 쿼리에서 터짐 |

**주의: 계정 번호는 두 티어 모두 `BIGINT`이고, Redis에는 10진수 문자열로 들어간다.** `AccountDB`의 `Account.AccountId`와
`GameDB`의 `Account.AccountId`, `Character.AccountId`는 모두 `BIGINT`다. 인증 서버는 `mssql` 드라이버가 돌려준 문자열을 숫자로 바꾸지 않고 그대로 넣으므로,
2^53을 넘는 계정 번호도 정확히 전달된다. 게임 서버는 이 문자열을 `int64`로 읽고, int64 범위를 넘는 값은 거절한다.

## Cross-Cutting Concerns

### 저장소

LocalDB 인스턴스는 그 인스턴스를 소유한 티어마다 하나다. 인스턴스 이름은 티어를, 데이터베이스 이름은 데이터 영역을
따른다. 인증 서버의 DB는 `(localdb)\P1Auth`의 `AccountDB`다. 게임 서버의 DB는 `(localdb)\P1Game`의 `GameDB`이고,
같은 인스턴스의 `GameDB_Test`는 실제 DB에 붙는 테스트만 쓴다.
근거는 `docs/adr/0014-split-db-instances-by-tier.md`에 있다. 접속 문자열의 출처도 다르다. 게임 쪽은 `Config`의 기본값과
환경 변수이고, 인증 쪽은 환경 파일이다.
**Architecture Invariant:** 각 DB는 소유 티어만 접근한다. 교차 접근 경로가 없다.
인스턴스·경로·스크립트 목록은 `docs/build.md`. 스키마의 원본은 각 서버의 마이그레이션 파일이다
(`Server/AuthServer/migrations/`, `Server/GameServer/Migrations/`).

### 코드 생성

`docs/codegen.md`. 생성물을 직접 고치지 않는다.

### 테스트

판정은 종료 코드다. 로그 문자열로 성공을 판단하지 않는다.
계층별 실행 경로와 현재 커버리지는 `docs/testing.md`.

**Architecture Invariant:** 프로토콜 회귀 그물은 매크로 목록과 리플렉션으로 돈다.
메시지가 늘어도 테스트를 고칠 필요가 없다. **고쳐야 한다면 뭔가 잘못된 것이다.**

### 인코딩

`CLAUDE.md` 「컨벤션」.

### 빌드 환경

런처 설치본 엔진 고정. 엔진 소스 패치와 프로젝트 내 `TargetType.Program` 타깃이
불가능하다. 무언가를 계획하기 전에 이 제약부터 본다. 상세는 `docs/build.md`.
