0. 한눈에 — 세션 하나의 생애

1. 세션 시작 — 무엇이 로드되는가

세션이 열릴 때 들어오는 것은 성질이 다른 두 묶음이다. 하나는 우선순위가 있어 위가 아래를 덮는 설정이고, 다른 하나는 우선순위 없이 전부 합쳐지는 지시문이다. 이 둘을 같은 것으로 착각하면 "왜 내 설정이 안 먹지"에서 막힌다.

1-1. 설정 3층의 실제 내용

.claude/settings.json:2 — 첫 줄부터 하네스의 결정이다.

{
  "cleanupPeriodDays": 365,
왜 365인가 — Claude Code는 세션 transcript를 ~/.claude/projects/에 평문으로 기본 30일 보관하고 지운다. 30일은 이 프로젝트의 세션 간격(수일~수주)에 비해 짧다. 판정 ADR §2가 "재현성 원본은 이미 전부 기록되고 있으니 별도 로그 시스템을 만들지 말고 그 구멍만 메운다"고 결정했고, 구멍은 둘이었다 — 보존 기간과 위치. 365는 전자를 메운 값이고, 후자는 아래 6장의 아카이브 훅이 메운다. 트레이드오프: 디스크에 평문 대화 기록이 1년 쌓인다.

1-2. 지시문 3층 — 강제력이 없다는 점이 중요하다

규칙 파일은 모델이 읽고 따르는 것이지 기계가 검사하는 것이 아니다. 그래서 이 프로젝트는 규칙을 두 부류로 나눠 관리한다. 위반이 드물고 손해가 작은 것은 글로 두고, 두 번 이상 반복됐거나 손해가 큰 것은 훅으로 내린다(7장).

2. 계획 — 파일 밖으로 나가는 계획은 없다

복잡한 작업은 docs/plans/active/{작업명}.md에 계획을 먼저 쓰고 시작한다. 완료하면 completed/로 옮긴다. 지금 completed/verification-infra.md 하나가 그 형식의 실물이고, 여기에 세 가지 관행이 들어 있다.

관행표기왜
[x] + summary 한 줄완료 항목 옆에 생성·수정 파일 경로와 핵심 결정체크박스만 남으면 무엇이 왜 그렇게 됐는지가 사라진다. 차기 세션 프롬프트의 원료다

실제로 작동한 사례 — docs/plans/completed/verification-infra.md:62의 Phase B가 [B] blocked로 멈췄다. UE Low-Level Tests가 런처 설치본에서 Targets with a unique build environment cannot be built with an installed engine.로 거부됐고, 에이전트는 우회를 찾지 않고 UBT 소스에서 원인(TargetRules.cs:2690-2693 + RulesAssembly.cs:677-680)까지만 확인한 뒤 기록하고 멈췄다. 같은 날 사용자가 "이 프로젝트는 소스 빌드를 하지 않는다"고 확정하면서 blocked가 폐기로 전환됐고, 보류를 전제로 만든 파일들은 제거됐다 a04b75d.
왜 계획을 대화가 아니라 파일에 쓰는가 — 세션 컨텍스트는 세션과 함께 사라진다. Planner/Generator/Evaluator를 서브에이전트로 쪼개는 대안(판정 ADR 결정 1)은 기각됐다. 계획 품질은 사람과의 왕복에서 나오는데 서브에이전트는 자율 실행 후 결과 보고 모델이라 그 루프에 사람을 태울 수 없고, 본 세션이 쌓은 코드베이스 이해를 격리된 Planner가 다시 탐색하는 토큰 비용도 든다. 대신 Plan Mode = Planner(쓰기 금지 + 사람 승인 게이트), 본 세션 = Generator로 축소하고, 컨텍스트 분리는 세션 경계와 docs/plans/ 외부화가 담당한다. 격리가 정말 필요한 역할은 자기평가 편향이 걸리는 Evaluator 하나뿐이다 — 그 자리는 아직 비어 있다(8장).

prompts/의 세션 프롬프트 2개가 이 단계의 입력이다. 반복 골격(목표 선언 → 제약 명시 → 단계 → 산출물 정의 → 확인 질문)까지만 관행으로 인정되어 있고, 같은 유형을 세 번째 쓰게 되는 시점에 .claude/commands/ 슬래시 커맨드로 승격하기로 예약돼 있다.

3. 도구 라우팅 — 왜 grep이 아닌가

탐색·빌드·리팩토링은 Rider MCP로 간다. 이건 취향이 아니라 이 코드베이스의 성질에서 나온 결정이다.

왜 grep 금지인가 — UE의 RPC는 선언과 구현의 이름이 다르다(_Implementation 접미사). 텍스트 검색은 여기서 호출 사슬이 끊긴 것을 알려주지 않고 그냥 조용히 놓친다. analyze_calls는 심볼 해석 결과를 쓰므로 이 지점을 넘어간다. 트레이드오프: MCP 왕복이 grep보다 느리고, Rider가 떠 있어야 한다.
왜 빌드는 터미널이 아니라 MCP인가 — UBT/MSBuild를 셸로 돌리면 출력이 잘려 에러가 유실된다. 그래서 빌드는 build_solution_start → build_solution_state 폴링으로 간다. 단 이 근거는 빌드에만 성립한다 — gtest 출력은 짧고 완결적이라 실행은 셸로 간다(5장). 같은 규칙을 기계적으로 확장하지 않은 자리다.

여기에 하나 더 붙는 함정이 있고, 이건 글로는 못 막아서 훅으로 내려갔다.

Rider 인스턴스 하나가 열린 솔루션 전부(P1, Server)를 한 엔드포인트로 서빙한다. 대상을 고르는 건 rootFolder 인자뿐이다. 솔루션이 둘 이상 열려 있으면 서버가 모호성을 느껴 거부하지만, 하나만 열려 있으면 거부하지 않고 그대로 실행한다. Server를 빌드하려는데 P1만 열려 있으면 P1이 빌드되고, 아무도 그걸 알려주지 않는다.

4. 게이트 — PreToolUse 훅이 실제로 막는 것

도구 호출 하나하나가 guard_dangerous_cmd.py를 지난다. 훅은 stdin으로 JSON을 받아 툴 이름에 따라 다른 필드를 다른 방식으로 검사한다. 모든 툴이 같은 검사를 받는 게 아니라는 점이 핵심이다.

4-1. 두 단계의 코드

.claude/hooks/guard_dangerous_cmd.py:199-210 — 1차. 상태를 바꾸는 Rider 툴 20종에만 건다.

if tool_name in ROOT_FOLDER_REQUIRED:
    root = tool_input.get("rootFolder")
    if not isinstance(root, str) or not root.strip():
        return deny(
            "BLOCKED: " + tool_name + " 를 rootFolder 없이 호출했다. …",
            tool_name,
            ["rootFolder 누락"],
        )

.claude/hooks/guard_dangerous_cmd.py:213-220 — 2차. 여기서 부류에 안 들면 즉시 통과한다. ue_execute_python이 빠져나가는 지점이 정확히 이 else다.

if tool_name in SQL_TOOLS:
    target = tool_input.get("queryText", "")
    is_sql = True
elif tool_name in SHELL_TOOLS:
    target = tool_input.get("command", "")
    is_sql = False
else:
    return 0
왜 인라인 한 줄이 아니라 파일인가 — 이전 버전은 settings.json에 python3 -c "…" 한 줄이었다. 이 Windows에서 python3는 MS Store 앱 실행 별칭 스텁이라 스크립트를 실행하지 않고 exit 49로 죽는다. PreToolUse는 exit 2만 차단이고 그 외 non-zero는 non-blocking error라, 훅이 매번 조용히 실패하는 동안 위험 명령이 그대로 통과했다. 파일로 빼면서 인터프리터를 py -3(실제 exe)로 바꿨고, 덤으로 JSON 이스케이프 문제도 없앴다. 실패하는 안전장치는 없는 안전장치보다 나쁘다 — 있다고 믿기 때문이다.
왜 exit 2와 deny JSON을 둘 다 쓰는가 — deny()는 permissionDecision=deny JSON을 stdout에 쓰고 동시에 exit 2로 끝낸다. exit 2는 JSON 파싱 결과와 무관하게 차단되므로, 스키마가 어긋나도 "통과"로 새지 않는다. 이중 안전장치다. 반대 방향으로도 한 번 판단했다 — stdin을 못 읽으면 return 0으로 통과시킨다(:187-193). 여기서 exit 2를 내면 판단 근거가 없는 상태에서 모든 툴 호출이 막힌다.

4-2. 차단 카운터 — 왜 발생 지점에서 세는가

차단 1건마다 block_counter.log에 TSV 한 줄이 append된다. 지금까지 누적 1건이다.

2026-08-26T17:35:50+09:00	mcp__rider__build_solution_start	rootFolder 누락
왜 세션 리포트에 손으로 누적하지 않는가 — 차단 건수는 소급 생성이 불가능한 데이터다. 지나간 차단은 다시 셀 수 없다. 손 집계는 몇 세션 안에 부패한다(집계를 잊은 세션은 영구 결손). 그래서 발생 지점에서 자동으로 쌓고, 세션 리포트는 집계 장부가 아니라 카운터와 git에서 읽어오는 조회 창이 된다(판정 ADR 결정 5). 카운터 쓰기가 실패해도 조용히 넘어간다(:146-163) — 로그를 못 쓴다는 이유로 위험 명령이 통과하면 주객이 전도된다.
이 카운터의 첫 1건은 훅이 스스로를 증명한 기록이다. 3장에서 서술한 "솔루션 하나만 열려 있으면 Rider가 거부하지 않는다"는 구멍을 글로만 막아뒀다면 이 호출은 그냥 잘못된 솔루션을 빌드했을 것이다. 실제로는 exit 2로 멈췄고 한 줄이 남았다.

4-3. 훅이 자기 커밋 메시지를 막은 사건

훅은 명령 문자열 전체를 본다. 그래서 위험 패턴을 언급만 하는 텍스트도 걸린다 — 대표적으로 그 패턴을 설명하는 커밋 메시지. git commit -m "… FLUSHALL 차단 추가"가 자기 자신에게 막혔다. 해결책은 예외 추가가 아니라 텍스트를 명령에서 빼는 것 — git commit -F <파일>을 쓴다. 예외를 늘리면 규칙이 무의미해지고, 경로를 바꾸면 규칙이 유지된다.

5. 검증 — 완료를 선언할 자격

이 하네스에서 "완료"는 선언이 아니라 실행 결과다. 그런데 증거의 강도는 영역마다 다르고, 그 차이가 이 프로젝트의 현재 한계다.

왜 빌드는 Rider인데 실행은 셸인가 — 셸 금지의 근거는 출력 절단으로 에러가 유실되는 것이고 그건 빌드에만 성립한다. 반대로 Rider의 execute_run_configuration은 호출마다 확인 대화상자를 띄우고, 그걸 끄는 수단은 Brave 모드(IDE 전역으로 셸·실행구성 확인 해제)뿐이다. 테스트 하나 돌리자고 IDE 전역 안전장치를 내리는 건 교환이 맞지 않는다. 그래서 빌드는 Rider, 실행은 셸로 갈랐다.

SessionEnd는 한 세션에 여러 번 발동할 수 있어서(clear 후 재개 등) 매번 오늘 날짜를 붙이면 같은 세션의 사본이 날짜별로 흩어진다. 기존 파일이 있으면 덮어쓴다 — 나중 사본이 항상 더 완전하기 때문이다.

실측된 구멍 — ~/.claude/projects/D--Unreal-Projects-Project-MMORPG/에 세션 jsonl이 5개 있는데 .claude/transcripts-archive/에는 1개뿐이다. 8/11·8/22 세션은 훅 도입(8/26) 이전이라 정상이지만, 8/27 세션(3.6MB)은 훅이 있는 상태에서 종료됐는데도 빠졌다.

추정: settings.json:44의 matcher는 공식 문서가 정의한 종료 사유 5종(clear|resume|logout|prompt_input_exit|other)을 전부 덮는다. 그러므로 사유 누락이 아니라 훅이 돌 기회를 못 얻은 것(터미널 강제 종료 등)으로 보인다. 훅 자신의 주석도 이 한계를 인정하고 있다 — SessionEnd는 차단이 불가능한 이벤트라 실패해도 세션에 영향이 없고, 프로세스가 강제 종료되면 애초에 훅이 실행되지 않는다. 이 아카이브는 최선 노력이지 보장이 아니다.

6-2. git 추적 정책 — 전역 규칙의 의도적 예외

왜 뒤집었나 — 이 프로젝트에서 하네스는 부수 설정이 아니라 보여줄 산출물이다(포트폴리오). "실수 → 문서 → 규칙 → 훅"의 승격 서사는 git 이력에 남아야 읽히고, 하네스 파일이 추적 밖이면 그 이력이 통째로 사라진다. 그래서 루트 .gitignore에는 예외 두 줄만 남았다 — block_counter.log(머신 로컬 통계라 브랜치 간 병합이 불가능)와 transcripts-archive/(jsonl 하나가 수 MB라 리포가 부푼다). 두 파일 다 백업 대상에는 포함이라고 주석에 명시돼 있다.

7. 승격 — 실수가 규칙이 되고 규칙이 기계가 되는 길

CLAUDE.md의 규칙 하나: 같은 실수가 두 번 반복되면 규칙 한 줄을 제안하고, 세 번이면 훅·규칙으로 승격을 제안한다. 이 사다리가 실제로 어떻게 밟혔는지가 이 하네스의 이력 전부다.

왜 어떤 것은 1회에 기계로 가고 어떤 것은 2회에 문서로 가는가 — 갈림길은 횟수가 아니라 재발 확률이다. python3 스텁과 rootFolder 누락은 환경·API의 구조적 성질이라 다음에도 100% 재발한다 — 기다릴 이유가 없다. 반면 "존재를 능력으로 오해한다"는 판단 습관이라 재발 확률이 불확실했고, 실제로 두 번(노출 목록에 없는 build_project를 "없다"고 단정 / 설치본에 Catch2가 있으니 LLT "가능"이라고 계획) 발생한 뒤에야 규칙이 됐다. 2회/3회는 상한이지 하한이 아니다.

8-3. 남아 있는 함정

MCP 등록이 레포를 따라가지 않는다 — Rider MCP는 .mcp.json이 아니라 ~/.claude.json의 이 프로젝트 항목에 {"type":"http","url":"http://127.0.0.1:64482/stream"}로 박혀 있다. 클론해도 안 따라오고, 포트가 Rider 인스턴스에 종속이라 IDE 재시작 후 포트가 바뀌면 조용히 죽는다. CLAUDE.md의 도구 라우팅 규칙은 이 엔드포인트가 살아 있다는 전제 위에 서 있다.
실행 순서에 대한 침묵 — Server/Binary/는 gitignore다. 그래서 빌드 없이 GameServerTests.exe를 부르면 새 코드가 아니라 옛 exe가 돌거나 파일이 없다. "테스트 초록"이 사실은 지난 빌드의 초록일 수 있는 자리다.
인코딩 — .proto와 .bat만 cp949, 나머지는 UTF-8(.gitattributes가 강제). 그래서 이 두 종류의 한국어 주석을 UTF-8로 읽으면 깨져 보인다. 정상이며, "고치면" 이 파일들을 소비하는 툴 쪽이 깨진다. 테스트 러너도 같은 문제를 겪어서 TestMain.cpp가 gtest_main.cc를 대체하고 SetConsoleOutputCP(CP_UTF8)를 부른다 — 읽히지 않는 진단은 하네스로서 제 역할을 못 한다.
