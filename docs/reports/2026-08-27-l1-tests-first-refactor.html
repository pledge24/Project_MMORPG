0. 한눈에 — 여덟 번의 판정

세 줄 요약:

  • 서버 L1(GoogleTest) 파이프라인을 세우고 여덟 번의 빌드-실행 루프로 인벤토리를 고쳤다.
  • 테스트가 잡은 프로덕션 버그는 2건. 하나는 예약돼 있던 것(D-01), 하나는 계획에 없었다.
  • 계획에 없던 쪽이 더 심각했다 — 코드를 눈으로 읽어서는 나오지 않는 종류였다.

2. 첫 실전 — 넣을 때와 꺼낼 때가 다른 표를 본다

Inventory는 서로 정합해야 하는 표를 셋 들고 있고, 셋 다 생성자에서 손으로 채운다. 결정적으로 아이템을 넣는 경로와 꺼내는 경로가 서로 다른 표를 본다.

2-1. 실패를 먼저 눈으로 봤다

수정 전에 테스트부터 썼다. 픽스처는 Gamedata::ItemDataTable을 손으로 시드하고 Player를 Init()만 한다 — DB·Redis·Room·세션이 필요 없다.

3. 계획에 없던 수확 — 검증보다 먼저 부른 mutable_item()

다음 예정 항목은 D-15("실패한 제거가 더티 플래그를 세운다")였다. 한 줄을 아래로 옮기면 끝나는 일이라 생각했는데, 테스트를 붙이는 과정에서 같은 자리에 더 큰 것이 있었다.

수정 전 removeItem의 앞 여섯 줄은 이랬다.

Protocol::Slot* updatedSlot = inventorylookupMappings[itemType]->Mutable(slotId);
Protocol::Item* item = updatedSlot->mutable_item();     // ← 검증보다 먼저

dirtyFlagsMappings[itemType][slotId] = true;            // ← D-15: 이것도 먼저

if (updatedSlot->has_item() == false || item->count() < count)
    return false;

protobuf의 mutable_ 계열은 없던 필드를 만들면서 presence 비트를 켠다. 그래서 저 줄이 실행된 뒤에는 has_item()이 항상 참이다 — 바로 아래 검증의 첫 조건이 죽은 코드였다.

이 버그를 드러낸 테스트는 다섯 줄이다.

Server/GameServerTests/InventoryTests.cpp:160-172

Server/GameServer/Game/System/Inventory.cpp:136-146

// 검증보다 먼저 부르면 빈 슬롯이 "아이템 있음"으로 오염돼 다시는 채워지지 않는다.

이 세션에서 가장 값이 나간 지점. D-01은 이미 진단서에 적혀 있던 것이고 테스트는 그것을 확인했을 뿐이다. 반면 이 버그는 아무도 찾고 있지 않았다. 코드를 읽으면 "검증하고 있네"로 보이고, 실제로 return false도 정상적으로 나온다. 부작용은 다음 addItem이 슬롯 1로 밀린다는 관측으로만 드러난다 — 그건 실행해야 보이는 것이다.

5. 왜 이렇게 했나

왜 vcpkg가 아니라 소스 벤더링인가 — 세션 1의 권고는 vcpkg manifest였고, 재확인 과정에서 뒤집었다. 이 머신에 vcpkg가 없고, Microsoft 문서가 gtest를 "MSBuild 자동 링크가 안 되는 예외 라이브러리"로 명시하며(main() 재정의 충돌), VcpkgEnableManifest는 기본값이 false라 수동 설정이 세 군데 붙는다. 결정적인 건 마지막이다 — 이 리포는 이미 모든 서드파티를 벤더링한다. gtest만 다른 메커니즘을 들이면 새 클론에 "vcpkg를 설치하라"는 단계가 하나 늘고, 그 단계는 문서에만 존재하게 된다. 트레이드오프: 리포에 1.1MB의 소스가 들어온다.
왜 "필요한 파일만"이 아니라 "main 빼고 전부"인가 — Inventory.cpp → Player.cpp → Room.cpp → DBRequestFunctions.cpp로 전이 의존이 이어져 결국 대부분을 넣게 된다. 링크 에러가 날 때마다 파일을 하나씩 추가하는 루프는 비결정적이고 재현이 안 된다. 덤으로 얻은 것: 제외한 Main/GameServer.cpp가 gitignore된 config.h의 유일한 소비자라, 테스트 타깃은 비밀 없이 빌드된다. 트레이드오프: 테스트 한 줄을 고쳐도 서버 소스 전부가 컴파일 대상이라 빌드가 길다.
왜 실행만 셸로 뺐는가 — execute_run_configuration은 호출마다 Rider가 확인 대화상자를 띄운다. TDD는 red→green으로 매 수정마다 실행하므로 루프가 사람 클릭에 묶인다. 그걸 끄는 수단은 Brave 모드뿐인데, 그건 셸 명령과 실행 구성 확인을 IDE 전역으로 해제하는 설정이라 쓰지 않기로 했다. CLAUDE.md의 "터미널로 직접 빌드 금지"는 근거가 출력 절단으로 에러가 유실되는 것이고 그건 빌드에만 성립한다 — gtest 출력은 짧고 완결적이며 판정은 종료 코드 하나다. 그래서 빌드는 Rider, 실행은 셸로 갈랐다. 트레이드오프: 사람 클릭 게이트가 한 겹 없어진다. 대신 남는 게이트(위험 명령 훅)는 결정적이다.
왜 D-14는 고치지 않고 DISABLED_로 남겼나 — 스택 상한을 지키려면 초과분이 다음 슬롯으로 넘어가야 하는데, 그러면 한 번의 구매가 슬롯 두 개를 바꾼다. 그런데 S_BUY_ITEM은 Slot updated_slot 하나만 나른다. 제대로 고치려면 프로토콜을 repeated로 바꾸고 생성기를 다시 돌린 뒤 클라·서버 핸들러를 함께 고쳐야 한다 — 3곳 수정이다. 계획된 범위를 넘으므로 버그의 존재는 실행 가능한 형태로 남기고 수정은 넘겼다. --gtest_also_run_disabled_tests로 실제 빨강임을 확인해 뒀다 — 미검증 스텁이 아니다.

6. 시험이 드러낸 한계

그물이 닿는 범위가 좁다. 현재 테스트는 Inventory와 프로토콜 계약에만 있다. Room·DBRequestFunctions는 비어 있고, 그 둘이 서버 코드의 27%다. D-03(Room 분해)을 지금 착수하면 그물 없이 하는 리팩토링이 된다.
남은 구조 문제는 그대로다. D-01은 증상이었고 원인은 손으로 유지되는 매핑 3종이다 (D-23으로 기록). 두 표가 한 글자만 어긋나도 아이템이 다른 인벤토리로 새고, 둘 다 유효한 enum이라 컴파일러는 침묵한다. 지금은 테스트가 세 슬롯 타입을 전부 검사해 재발을 잡아 주지만, 어긋날 수 있는 구조 자체는 남아 있다.
클라 입력이 검증 없이 인덱싱으로 직행한다. removeItem은 slotTypeToItemTypeMappings에 unordered_map::operator[]를 쓴다 — 미등록 슬롯 타입(SLOT_TYPE_EQUIPPED 등)이 오면 ITEM_TYPE_NONE이 삽입되고 inventorylookupMappings[ITEM_TYPE_NONE]은 nullptr이라 널 역참조다. slotId 범위 검사도 없다. D-22로 기록했고 이번엔 고치지 않았다.
빌드가 루프의 비용 전부다. 테스트 실행 자체는 실측 3~32ms인데, 한 회차의 체감 시간은 거의 전부 빌드다. 테스트 한 줄만 고쳐도 서버 소스 전부가 컴파일 후보라 그렇다. 정확한 빌드 시간은 측정하지 않았다 — 다음에 루프가 답답해지면 그때 재 볼 것.
