1. 훅이 죽어 있었다 — exit 49의 정체

훅은 이렇게 생겨 있었다. 로직 자체는 멀쩡하다.

.claude/settings.json (수정 전)

"command": "python3 -c \"import json,sys,re; d=json.load(sys.stdin); ...
             sys.exit(2 if hit else 0)\""

문제는 python3다. 이 머신에서 where python3는 다음을 가리킨다.

C:\Users\zmwps\AppData\Local\Microsoft\WindowsApps\python3.exe

실제 파이썬이 아니라 Microsoft Store 앱 실행 별칭 스텁이다. 스크립트를 실행하지 않고 Python 한 단어를 출력한 뒤 exit 49로 죽는다. 같은 스크립트를 진짜 인터프리터에 물리면 정상적으로 exit 2가 나온다.

$ echo '{"tool_input":{"command":"rm -rf /tmp/foo"}}' | python3 -c "...(훅 스크립트)..."
Python
EXIT=49

$ echo '{"tool_input":{"command":"rm -rf /tmp/foo"}}' | \
    C:/Users/zmwps/AppData/Local/Programs/Python/Python313/python.exe -c "...(동일)..."
BLOCKED: rm\s+-rf
EXIT=2

여기서 결정적인 것은 49가 0이 아니라는 사실이 아무 도움이 안 된다는 점이다. Claude Code의 PreToolUse 규약은 다음과 같다.

왜 스크립트 파일로 뺐나 — 인터프리터만 py -3로 바꿔도 동작은 한다. 그런데 인라인 -c "…"는 JSON 안에 파이썬 코드를 넣는 구조라, 정규식에 따옴표나 백슬래시가 하나 늘 때마다 이스케이프가 깨진다. 그리고 깨져도 조용히 통과한다(위 밴드). 같은 사고를 반복할 구조 자체를 없애려고 .claude/hooks/guard_dangerous_cmd.py로 분리했다. 트레이드오프: 설정 파일 하나로 자족하지 않게 되고, 훅이 파일 경로에 의존한다 (${CLAUDE_PROJECT_DIR}로 완화).
왜 exec form(args)인가 — 셸 폼으로 두면 Git Bash를 한 번 더 거치면서 경로의 공백·백슬래시가 재파싱된다. exec form은 실행 파일을 직접 spawn하고 각 args 원소를 문자 그대로 넘긴다. 다만 exec form은 실제 .exe만 받는다 (.cmd/.bat 심 불가) — 그래서 python(PATH 순서에 의존)이 아니라 py(C:\Windows\py.exe, 파이썬 런처)를 골랐다.
왜 exit 2와 deny JSON을 둘 다 쓰나 — JSON permissionDecision: "deny"만 쓰면 스키마 검증에 실패했을 때 "비차단 오류"로 떨어져 통과한다. 반대로 exit 2만 쓰면 차단은 되지만 사용자에게 보이는 사유가 stderr 원문이 된다. 공식 규약상 exit 2는 JSON 파싱 결과와 무관하게 차단하고, 사유는 유효한 JSON이 있으면 거기서 가져간다. 둘을 겹치면 실패 모드가 사라진다.

1-1. 패턴도 CLAUDE.md와 어긋나 있었다

CLAUDE.md 안전 규칙은 DROP, TRUNCATE, WHERE 없는 DELETE/UPDATE, FLUSHALL, FLUSHDB, KEYS *를 금지한다. 옛 훅이 실제로 보던 것은 FLUSHALL, FLUSHDB, DROP TABLE 세 개뿐이었다.

수정 전 — 커버되던 것

rm -rf
git push --force / -f
git reset --hard
git clean -f
git checkout . / git restore .
git branch -D
FLUSHALL / FLUSHDB
DROP TABLE

수정 후 — 추가된 것

rd /s · rmdir /s · del /s
Remove-Item -Recurse -Force
TRUNCATE TABLE
DROP DATABASE|SCHEMA|PROCEDURE|VIEW|INDEX
ALTER TABLE / CREATE TABLE|DATABASE
WHERE 없는 DELETE FROM
WHERE 없는 UPDATE … SET
KEYS *

WHERE 판정은 주석과 문자열 리터럴을 먼저 지운 뒤에 한다. 안 그러면 DELETE FROM x -- WHERE y 같은 입력이 통과한다 (테스트 케이스에 포함).

.claude/hooks/guard_dangerous_cmd.py:74-82

def _strip_sql_noise(text):
    text = re.sub(r"--[^\n]*", " ", text)
    text = re.sub(r"/\*[\s\S]*?\*/", " ", text)
    text = re.sub(r"'(?:[^']|'')*'", " '' ", text)
    return text
검증 — 단위 테스트 27케이스 전부 통과(차단 16 / 통과 11). 그 뒤 실제 하네스에서 Bash rm -rf, PowerShell Remove-Item -Recurse -Force, MCP execute_sql_query의 WHERE 없는 DELETE 세 경로를 쏘아 모두 차단되는 것과, git status·rm -f·git checkout .gitignore가 통과하는 것을 확인했다.

2. 훅이 덮지 못하던 우회로 3개

인터프리터를 고쳐도 남는 문제가 있었다. matcher가 "Bash" 하나였다. 이 세션에는 PowerShell 툴이 별도로 있고, Rider MCP는 터미널과 SQL을 각각 자기 툴로 실행한다. 전부 "Bash"에 걸리지 않는다.

남은 구멍을 어떻게 다룰 것인가 — ue_execute_python은 임의 코드라 문자열 패턴으로는 못 막는다. 현실적인 방어는 CLAUDE.md에 이미 있던 규칙 ("임의 코드를 실행하는 툴은 무엇을 실행할지 먼저 보고한다")을 실제 툴 이름으로 고쳐 유지하는 것과, 에디터 조작 전 git status 클린 확인이다. 이 세션에서도 BP 전수 조사 전에 그 순서를 지켰다. (원문은 execute_tool_script라는 실존하지 않는 이름을 쓰고 있었다. 실물은 execute_tool.)

3. 3티어 신뢰 경계 — Redis가 유일한 연결점

문서가 주장하던 "인증 티어와 게임 티어를 잇는 건 Redis뿐"은 코드와 일치했다. 다만 흥미로운 것은 이 규칙을 강제하는 게 코드가 아니라는 점이다.

왜 두 DB가 서로 다른 LocalDB 인스턴스에 있나 — 진단 결과 의도가 아니라 우연으로 보인다. AuthServer는 기본 인스턴스(MSSQLLocalDB)를 .env로, GameServer는 별도 인스턴스 (ProjectModels)를 config.h 컴파일 타임 상수로 잡았을 뿐이다. 그런데 결과적으로 이 우연이 아키텍처 규칙을 물리적으로 강제하고 있다 — 게임 서버 프로세스는 UserDB 접속 문자열을 아예 갖고 있지 않아서, 실수로 조회하려 해도 못 한다. 그래서 부채 목록에서 이 항목의 처방은 "합쳐라"가 아니라 "의도임을 문서로 못 박아라"가 됐다.

4. 패킷 18개가 갈라지는 네 갈래

Protocol.proto의 메시지는 40개(PKT_* 1000~1039)다. 접두사가 방향을 정한다 — C_* 18개가 클라→서버, S_* 22개가 서버→클라. 서버가 받은 18개는 네 갈래로 갈린다.

5. 수신 펌프가 레벨 블루프린트에 산다

클라 네트워크 스레드는 UObject를 만지지 않는다. 수신 큐는 게임 스레드에서 UP1GameInstance::HandleRecvPackets()가 비운다 — 여기까지는 문서대로다. 그런데 이 함수를 호출하는 C++ 코드가 없다.

P1/Source/P1/ 전체 grep 결과 호출부는 정의 자신뿐이었다. UE 에디터를 붙여 확인하니 호출부는 레벨 스크립트 블루프린트의 ReceiveTick 안에 있었다.

지금 사고가 안 난 이유 — C_Map.json을 보면 게임플레이 룸 4개 (마을 / 초·중·고급 사냥터, TemplateId 10·20·30·40)가 전부 MapId: 1111 하나를 공유한다. 즉 서버의 "룸"은 UE 레벨이 아니라 InGameMap 안의 논리 분할이다. 펌프가 있는 레벨만 실제로 쓰이고 있어 지뢰가 아직 안 밟혔을 뿐이다.
왜 레벨 BP에 두면 안 되나 — 대안은 UP1GameInstance::Init()에서 FTSTicker나 UTickableWorldSubsystem으로 자기가 도는 것이다. 게임 인스턴스는 레벨 전환에 살아남으므로 소켓을 소유한 주체가 펌프도 소유하는 게 수명 주기상 맞다. 레벨 BP 방식의 유일한 이점은 "레벨마다 켜고 끌 수 있다"인데, 이 프로젝트에서 그걸 원한 흔적은 없고 끄고 싶지 않은 레벨에서 꺼지는 사고만 가능하다.

6. 빌드 실패의 범인은 C++가 아니었다

Server.sln 전체 빌드는 실패한다. 그런데 Rider의 Problems 뷰는 비어 있고 MCP는 진단 없이 실패만 돌려준다.

{"state":"Completed","buildIsSuccess":false,"problems":[],
 "errorMessage":"Build failed without diagnostic output (check Rider's build log)."}

빌드 로그 실물을 열어보니 에러는 정확히 하나였고, C++와 무관했다.

부수 소득 — DummyClient 빌드는 2026-08-11 커밋 286eee9에서 이미 복구됐고, 이번 빌드에서 Server/Binary/Debug/DummyClient.exe가 정상 재생성되는 것으로 재확인했다. 범위 빌드로 DummyClient.cpp·GameServer.cpp·Inventory.cpp· JobQueue.cpp를 각각 컴파일해도 전부 통과한다.
왜 DummyClient가 아직 검증 도구가 아닌가 — 빌드는 되지만 하는 일이 문제다. DummyClient.cpp(86줄)는 접속 후 토큰이 비어 있는 C_LOGIN을 보내고, C_CHAT "Hello World !"를 1초마다 무한 브로드캐스트한다. 서버에서 이 흐름은 반드시 실패한다 — Redis 조회 실패 → 플레이어 없음 → Handle_C_CHAT이 return false. 거기에 DummyClient/Main/ClientPacketHandler.cpp의 Handle_S_LOGIN은 본문이 통째로 주석이고, 주석 안의 코드마저 set_playerindex(0)라는 현재 proto에 없는 필드를 쓴다(지금은 character_id). 즉 로그인이 통해도 C_ENTER_GAME을 안 보내고, session->player가 끝내 nullptr이라 Handle_C_CHAT이 항상 조기 반환한다. 승격하려면 (1) 호스트·포트·세션 수 인자화, (2) AuthServer에서 받은 실 토큰 주입, (3) 봇 상태 머신(로그인→입장→맵) 복원, (4) 기대 패킷 수신 여부에 따른 종료 코드가 필요하다.

6-1. 정정 — "그런 툴은 없다"고 잘못 단정했다

초판의 오류 — 이 문서는 처음에 build_project를 "실존하지 않는 툴 이름"으로 적고, 그 근거로 CLAUDE.md를 고쳐 커밋했다(063c7cb). 틀렸다. 근거는 "세션에 주어진 툴 목록에 없다"뿐이었는데, 그 목록은 이 클라이언트에 노출된 것이지 툴이 존재하는지가 아니다. 둘을 같은 것으로 취급했다.

왜 이 오류가 났나 — "내가 호출할 수 있는 것"과 "존재하는 것"을 구분하지 않았다. 에이전트에게는 노출된 목록이 세계의 전부처럼 보이기 때문에 이 착각은 구조적으로 재발한다. 그래서 CLAUDE.md에 규칙을 양방향으로 박았다: 문서에 있다는 이유로 이름을 되돌리지 말 것, 그리고 노출 목록에 없다고 해서 "그런 툴은 없다"고 단정하지도 말 것. 확정이 필요하면 tools/list를 직접 치거나 IDE 설정을 본다.
부수 발견 — MCP 서버가 3개 등록돼 있다: rider(64482, 연결됨) · jetbrains(64342, 연결 거부 — 같은 Rider를 가리키던 낡은 포트) · unreal-mcp(8000, UE 에디터가 직접 서빙, P1/.mcp.json에만 있어 미연결). unreal-mcp는 toolset 55개 게이트웨이이고 그중 AutomationTestToolset이 테스트 발견·실행·결과 조회를 제공한다 — 세션 2의 L2~L4 계층에 직결된다.
