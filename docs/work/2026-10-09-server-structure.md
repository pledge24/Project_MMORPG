# 서버 구조 정리: 게임 서버 리팩토링과 서버 tech-debt 해소

## 목표

- DB 스레드, IOCP 워커, 다른 룸의 큐가 자기가 소유하지 않은 상태를 읽거나 쓰지 않는다
- 불러오기와 저장이 같은 진행 사본(`PlayerProgress`)을 쓰고, 저장 하나가 한 트랜잭션이다
- 엔티티의 틱을 룸이 일괄로 돌리고, 몬스터 AI와 장비·인벤토리가 컴포넌트로 나뉜다
- 서버를 종료해도 접속 중인 플레이어의 진행이 남는다
- `docs/tech-debt.md`에 서버 TD가 남지 않는다(backlog로 보낸 TD-002 제외)

## 세션 시작 절차

1. `refactor/205-server-structure`를 체크아웃한다. `dev`에 새 커밋이 있으면 merge한다(rebase하지 않는다)
2. 진행 표에서 차단이 모두 「머지」인 첫 「대기」 티켓을 고르고, 그 이슈 본문을 읽는다. 「진행」인 티켓이 있으면 「기록」에서 어디까지 했는지 먼저 읽는다
3. 티켓 브랜치를 통합 브랜치에서 따고 PR은 통합 브랜치로 보낸다. 그 PR에 진행 표의 해당 줄을 「머지」로
   고치는 변경을 함께 넣는다. 머지되면 `close-merged-issues` 워크플로가 PR 본문의 `Closes #N` 이슈를 닫는다.
   닫히지 않았으면 손으로 닫는다

## 지킬 것

- 티켓이 다시 쓰는 코드에 있는 TD만 그 티켓에서 고친다. 그 코드를 건드리지 않는 TD는 #213으로 미룬다
- 한 티켓 안에서 동작을 유지하는 이동·정리 커밋을 먼저, 결함 수정 커밋을 나중에 둔다. 결함 수정에는 빨강 단계를 거친 테스트를
  붙인다. PR의 「주요 변경 사항」에 바뀌는 동작과 TD 번호를 적는다
- 옮기다가 새로 찾은 결함은 그 자리에서 고치지 않는다. 「기록」에 적고 `docs/tech-debt.md`에도 적는다. 이 작업의 티켓이 그 코드를
  다시 쓰면 그 티켓 본문에 더하고, 아니면 #213 본문에 더한다
- 고친 코드의 표준 출력 스트림 호출은 그 티켓에서 #206의 로거로 옮긴다
- client TD는 서버 변경 없이 맞아지지 않는 것만 다룬다. #208은 클라이언트 클래스 이름을 바꾸고, #213은 생성 템플릿을 고치므로
  클라이언트 빌드를 함께 확인한다
- #209와 #212는 PR이 크다. 이슈 본문의 커밋 순서를 지키고, 커밋마다 빌드와 테스트가 통과하는 상태를 유지한다
- 진행 표의 「검증」에는 실제로 돌린 것만 적는다. 서버 MSBuild 종료 코드, `GameServerTests.exe`, 클라이언트 빌드 종료 코드,
  `Run-UeTests.ps1`, 사람의 확인(PIE, 실제 DB 왕복, 서버 종료 뒤 재입장)을 구분한다
- 통합 브랜치를 `dev`에 넣을 때는 merge commit으로 한다. 티켓별 커밋이 `dev` 이력에 남아야 한다

## 결정

| 결정 | 틀렸다는 신호 |
|---|---|
| 서버 컴포넌트는 소유자와 `Start`/`Tick`만 공유하는 작은 베이스이고, 범용 조회를 두지 않는다(ADR-0013) | 컴포넌트를 타입으로 찾아야 하는 호출자가 셋 이상 생긴다 |
| 장비 컴포넌트의 이름은 기능을 드러내는 `EquipmentComponent`이고, 클라이언트는 접미사 없이 `UP1Equipment`다 | 서버와 클라이언트의 이름 차이 때문에 대응 클래스를 못 찾는 일이 반복된다 |
| 진행 내용은 `PlayerProgress` 하나이고, 저장 사본이 그것을 감싼다(ADR-0012) | 불러오기에만 있거나 저장에만 있는 필드가 생긴다 |
| 엔티티의 틱은 룸이 일괄로 돌린다(ADR-0011) | 엔티티마다 다른 주기를 누적 시간으로 맞추는 코드가 컴포넌트마다 반복된다 |
| 로거는 서드파티 없이 직접 만든다 | 파일 회전이나 비동기 출력 같은 기능을 직접 구현하는 데 티켓 하나 이상이 든다 |
| 몬스터의 일반 공격은 피격 시점에 거리를 다시 확인한다 | 클라이언트의 공격 연출과 서버 판정이 어긋난다는 보고가 나온다 |
| 진행 상태는 이 파일의 진행 표가 원천이다 | 진행 표와 PR 상태가 어긋난 채 발견된다 |
