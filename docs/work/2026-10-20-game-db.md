# GameDB 재구성: 새 인스턴스, 새 스키마, 새 인증 티켓 계약

## 목표

- 게임 서버가 새 인스턴스 `(localdb)\P1Game`의 `GameDB`를 쓰고, `ProjectModels` 인스턴스가 남지 않는다
- `GameDB`의 스키마가 `Server/GameServer/Migrations/`의 파일로 관리되고, 그 스키마가 `GameDB.target.sql`을 따른다
- 게임 서버가 인증 서버의 인증 티켓 계약(`docs/ARCHITECTURE.md`의 「Server/AuthServer」 절)으로 로그인을 받는다
- 계정, 캐릭터, 진행 저장과 불러오기의 코드가 새 스키마에 맞게 다시 쓰여 있다
- DB 기본값과 코드 상수에 있던 기획 값이 기획 데이터로 옮겨져 있다

## 세션 시작 절차

1. `refactor/247-game-db`를 체크아웃한다. `dev`에 새 커밋이 있으면 merge한다(rebase하지 않는다)
2. 진행 표에서 차단이 모두 「머지」인 첫 「대기」 티켓을 고르고, 그 이슈 본문을 읽는다. 「진행」인 티켓이 있으면 「기록」에서 어디까지 했는지 먼저 읽는다
3. 티켓 브랜치를 통합 브랜치에서 따고 PR은 통합 브랜치로 보낸다. 그 PR에 진행 표의 해당 줄을 「머지」로
   고치는 변경을 함께 넣는다. 머지되면 `close-merged-issues` 워크플로가 PR 본문의 `Closes #N` 이슈를 닫는다.
   닫히지 않았으면 손으로 닫는다

## 지킬 것

- `.proto`는 고치지 않는다. 다다음 작업에서 프로토콜을 다시 짠다. DB의 표현과 패킷의 표현이 다르면 서버의 변환 지점에서 바꾸고, 그 지점을 아래 「패킷과 DB 사이의 변환 지점」에 적는다
- 티켓 PR을 머지한 시점에 게임 서버 빌드와 `GameServerTests`가 통과한다. 실제 DB 테스트가 있는 티켓은 그 테스트도 통과한다
- 마이그레이션 적용(#255)부터 진행 저장(#257)까지는 게임 입장이 깨지는 것을 허용한다. 그 구간의 PR은 「머지 시 주의」에 이를 적는다
- 인스턴스와 데이터베이스와 로그인을 만들고 지우는 일, Rider 데이터 소스, 훅 파일의 적용, 마이그레이션의 적용은 사람이 한다. Claude는 명령과 패치의 초안을 쓰고, 사람이 실행한 결과를 받은 뒤에 이어 간다
- Claude는 #254가 머지된 뒤부터 `claude_rw` 연결로 `GameDB`와 `GameDB_Test`의 행을 쓴다. 이 로그인은 두 DB의 `db_datareader`와 `db_datawriter`에만 속하므로 스키마를 바꾸지 못한다
- 기획 원본은 새 워크북만 Claude가 만든다. 기존 워크북을 고쳐야 하면 사람에게 넘긴다
- 클라이언트를 고친 티켓은 클라이언트 빌드를 함께 확인한다. 클라이언트에서 실제로 해 보는 확인은 사람이 한다
- 옮기다가 새로 찾은 결함은 그 자리에서 고치지 않는다. 「기록」에 적고 `docs/tech-debt.md`에도 적는다. 이 작업의 티켓이 그 코드를 다시 쓰면 그 티켓 본문에 더한다
- 진행 표의 「검증」에는 실제로 돌린 것만 적는다. 빌드 종료 코드, 단위 테스트, 실제 DB 테스트, 훅 테스트, 사람의 확인을 구분한다
- 통합 브랜치를 `dev`에 넣을 때는 merge commit으로 한다. 티켓별 커밋이 `dev` 이력에 남아야 한다

## 결정

| 결정 | 틀렸다는 신호 |
|---|---|
| 새 인스턴스는 `P1Game`이고 `GameDB`와 `GameDB_Test`를 둔다. `GameDB`는 게임 서버가 쓰고, `GameDB_Test`는 실제 DB에 붙는 테스트만 쓴다. 테스트가 넣고 지우는 행이 개발 중의 게임 데이터와 섞이지 않게 하고, 기존 행에 따라 테스트 결과가 흔들리지 않게 하려고 나눈다. `ProjectModels`는 인스턴스까지 지운다(ADR-0014) | 게임 서버가 아닌 티어가 `P1Game`의 DB를 읽어야 한다 |
| 옛 GameDB의 데이터는 옮기지 않는다 | 보존해야 하는 캐릭터 데이터가 생긴다 |
| 스키마는 `Server/GameServer/Migrations/NNN_<이름>.sql`이고 형식은 인증 서버의 `migrations/`와 같다. `Queries/`는 지운다 | 어느 파일까지 적용했는지 사람이 놓쳐 스키마가 어긋난다 |
| 스키마는 `GameDB.target.sql`을 따르되 세 가지가 다르다. 아이템 칸의 고유 제약이 `(OwnerId, Container, ItemType, SlotIndex)`이고, `Account.CharacterSlotCount`에 기본값이 없고, `ItemType` 주석이 코드의 값(3은 기타)을 따른다 | 인벤토리가 아닌 컨테이너에서 한 칸에 종류가 다른 아이템이 둘 들어간다 |
| `GameDB.example.sql`은 앞으로의 설계 메모로 `docs/references/`에 둔다. `docs/references/`는 앞으로의 설계에 참고할 자료의 자리가 되고, 하네스 v1 이력은 `docs/references/harness-v1/`로 옮긴다 | 참고 자료를 현행 제약으로 읽는 일이 생긴다 |
| `.proto`는 이번 작업에서 고치지 않는다. 다다음 작업에서 다시 짠다 | 프로토콜을 고치지 않으면 동작을 유지할 수 없는 지점이 나온다 |
| 캐릭터 ID와 아이템 UID는 Snowflake 발급기 하나가 발급한다. 41비트 밀리초, 10비트 노드, 12비트 순번, 기준 시각 2026-01-01 UTC다. 논리 시계로 기다리지 않고, 부팅할 때 이 노드의 최대 ID보다 뒤에서 시작한다. 노드 번호는 `P1_SERVER_NODE_ID`이고 Debug 빌드만 기본값 0을 쓴다 | 노드가 1024개를 넘거나, 노드 번호를 손으로 나눠 주다 겹친다 |
| 소모품과 기타 아이템도 아이템 UID를 받는다 | 묶음을 나누고 합치는 일이 잦아 UID가 지나치게 빨리 쓰인다 |
| 경험치는 누적값으로 저장한다. 레벨은 입장할 때 레벨 표로 다시 계산하고, 저장된 레벨은 목록용 사본이다. 최대 레벨을 넘는 값은 자르고 경고한다 | 기획이 레벨 표를 바꾸면서 기존 캐릭터의 레벨이 바뀌면 안 된다는 요구가 나온다 |
| 사망 페널티는 그 레벨 요구치의 10%이고, 레벨 안에 쌓인 양보다 많이 잃지 않아 레벨이 내려가지 않는다. 클라이언트에는 레벨 안의 경험치를 보낸다 | 기획이 레벨 하락을 원한다 |
| DB와 기획 데이터는 맵만 안다. 입장할 룸은 서버의 배정 함수가 맵과 좌표로 고른다. 룸 정의를 기획 데이터 밖으로 옮기는 일은 backlog에 둔다 | 같은 맵의 여러 룸 중 어디에 넣을지 좌표만으로 정할 수 없는 기획이 나온다 |
| 컨테이너는 서버 C++ enum이다. 1 인벤토리, 2 착용 장비다. 인벤토리는 컨테이너 하나이고 구역은 아이템 종류로 나뉜다 | 구역마다 다른 규칙(정렬, 잠금 등)이 생겨 구역이 컨테이너처럼 다뤄진다 |
| 아이템은 저장할 때마다 그 캐릭터의 전체를 MERGE 한 문장으로 동기화한다. 칸 단위의 바뀐 표시는 버린다 | 아이템 수가 늘어 접속 종료 저장 시간이 눈에 띄게 길어진다 |
| 장비의 추가 공격력은 DB에서 없애고 패킷에는 0을 채운다. `ItemGearOption`은 쓰지 않는다. 내구도는 0을 넣는다 | 장비 옵션 기능을 만들기 시작한다 |
| 골드는 `CharacterCurrency` 행이다. 재화는 기획 표가 정의하고, 서버는 재화 종류 열(`GOLD`)로 골드를 찾는다 | 재화 종류 열로 구별할 수 없는 재화(같은 종류가 여럿)가 생긴다 |
| 시작 맵, 시작 좌표와 방향, 시작 골드, 기본 캐릭터 슬롯 수, 구역별 칸 수를 기획 데이터로 옮긴다. 표는 재화, 캐릭터 생성(행 하나), 인벤토리 구역 셋이다 | 직업마다 시작 값이 달라진다 |
| 새 워크북은 Claude가 `openpyxl`로 만든다. 기존 워크북은 사람이 고친다. 변환기는 PyInstaller exe이므로 `openpyxl`은 Claude가 엑셀을 다루기 위해서만 설치한다 | 새 워크북을 사람이 엑셀에서 열고 저장할 때 형식이 깨진다 |
| 캐릭터는 소프트 삭제한다. 슬롯 한도는 삭제되지 않은 캐릭터만 세고, 이름은 바로 다시 쓸 수 있고, 복구는 만들지 않는다. 이름 중복은 고유 인덱스 위반(2601)을 결과로 바꾼다 | 삭제한 캐릭터를 복구해 달라는 요구가 나온다 |
| 캐릭터 이름은 최대 32자다. DB 열 크기에 묶인 제약이므로 기획 데이터로 옮기지 않는다 | 기획이 이름 길이를 바꾸고 싶어 한다 |

| Claude의 쓰기 연결은 `claude_rw`(두 DB의 `db_datareader`와 `db_datawriter`)다. 문장의 제한은 DB 권한이 맡고, 훅은 기존 연결 허용 목록에 이 연결을 더할 뿐이다. 스키마를 바꾸는 문장은 DB가 거부하므로 마이그레이션은 사람이 적용한다. WHERE 없는 갱신과 삭제는 기존 훅 판정이 막는다 | 마이그레이션이 잦아져 사람이 적용하는 일이 작업을 막는다 |
| SQL은 `GameDB_Test`에 붙는 `DISABLED_` gtest로 검증하고, Claude가 실행한다. 게임 전체는 마지막 티켓에서 사람이 PIE로 확인한다 | 실제 DB 테스트가 다른 테스트의 데이터에 영향을 받아 결과가 흔들린다 |
