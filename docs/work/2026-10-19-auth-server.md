# 인증 서버 재구성: 역할 확정, 패키지와 계정 DB 정리, 계층 구조로 다시 쓰기

## 목표

- 인증 서버는 회원가입과 로그인만 맡고, 로그인에 성공한 계정에 일회용 인증 티켓을 발급한다
- 설치된 패키지가 모두 쓰이고, 쓰이는 패키지가 모두 설치되어 있다
- 인증 서버가 새 인스턴스 `(localdb)\P1Auth`의 `AccountDB`를 쓰고, 기본 인스턴스에 `UserDB`가 남지 않는다
- 인증 서버가 TypeScript로 다시 쓰이고, 판정 코드가 계정 저장소와 티켓 저장소를 인터페이스로 받는다
- 보고서 한 장으로 인증 서버의 역할, 흐름, 구조, 패키지를 설명할 수 있다

흐름과 계약의 원문은 `docs/ARCHITECTURE.md`의 「Server/AuthServer」 절이다. 이 파일에 계약을 다시 적지 않는다.

## 세션 시작 절차

1. `refactor/231-auth-server`를 체크아웃한다. `dev`에 새 커밋이 있으면 merge한다(rebase하지 않는다)
2. 진행 표에서 차단이 모두 「머지」인 첫 「대기」 티켓을 고르고, 그 이슈 본문을 읽는다. 「진행」인 티켓이 있으면 「기록」에서 어디까지 했는지 먼저 읽는다
3. 티켓 브랜치를 통합 브랜치에서 따고 PR은 통합 브랜치로 보낸다. 그 PR에 진행 표의 해당 줄을 「머지」로
   고치는 변경을 함께 넣는다. 머지되면 `close-merged-issues` 워크플로가 PR 본문의 `Closes #N` 이슈를 닫는다.
   닫히지 않았으면 손으로 닫는다

## 지킬 것

- 티켓 PR을 머지한 시점에 `npm start`로 인증 서버가 뜨고 회원가입과 로그인이 된다. 구조를 다시 쓰기 전의 티켓(#233, #234)은 기존 JS 코드를 최소한으로만 고쳐 이 상태를 지킨다
- 게임 서버와 GameDB는 고치지 않는다. 인증 서버가 새 인증 티켓 계약으로 발급하기 시작하면(#236) 게임 서버 입장이 실패하는 것은 허용한 결과다. PR의 「머지 시 주의」에 적는다
- 인스턴스와 데이터베이스를 만들고 지우는 일, 스키마 스크립트의 실행, `claude_ro` 연결을 만드는 일은 사람이 한다. Claude는 명령 초안을 쓰고, 사람이 실행한 결과를 받은 뒤에 이어 간다
- 클라이언트를 고치는 티켓(#235, #236)은 클라이언트 빌드를 함께 확인한다. 클라이언트에서 실제로 회원가입하고 로그인하는 것은 사람이 확인한다
- 옮기다가 새로 찾은 결함은 그 자리에서 고치지 않는다. 「기록」에 적고 `docs/tech-debt.md`에도 적는다. 이 작업의 티켓이 그 코드를 다시 쓰면 그 티켓 본문에 더한다
- 진행 표의 「검증」에는 실제로 돌린 것만 적는다. `npm test`, `npm run lint`, 타입 검사, `npm start`와 실제 요청, 클라이언트 빌드 종료 코드, 사람의 확인을 구분한다
- 통합 브랜치를 `dev`에 넣을 때는 merge commit으로 한다. 티켓별 커밋이 `dev` 이력에 남아야 한다

## 결정

| 결정 | 틀렸다는 신호 |
|---|---|
| 인증 서버는 회원가입, 로그인, 로그인할 때의 정지 검사만 맡고 닉네임을 받지 않는다 | 화면에 캐릭터 이름이 아닌 계정 단위의 이름이 필요해진다 |
| 티어 사이는 일회용 인증 티켓과 Redis로 잇는다. JWT를 쓰지 않는다 | 게임 서버 말고도 인증 티켓을 검증해야 하는 티어가 생긴다 |
| 인증 티켓의 값은 계정 번호 하나다. GM 권한은 GameDB가 갖는다 | 게임 서버가 입장할 때 계정 DB에만 있는 값이 필요해진다 |
| DB 인스턴스는 티어마다 하나다(ADR-0014) | 한 티어가 다른 티어의 인스턴스를 읽어야 하는 요구가 생긴다 |
| 로그인 ID와 비밀번호의 형식 규칙은 지금 것을 유지하고, 로그인 ID만 소문자로 바꾼다 | 비밀번호에 특수문자를 쓰지 못한다는 불만이 나온다 |
| 스키마는 스크립트 하나로 관리하고 migration을 두지 않는다 | 보존해야 하는 계정 데이터가 생긴 뒤에 스키마를 바꿔야 한다 |
| TypeScript를 `tsx`로 실행하고 테스트는 `vitest`와 `supertest`로 한다 | 실행 시점의 변환 비용이나 `tsx`와 Node 버전의 호환 문제가 기동을 막는다 |
| node-redis는 5를 유지한다. 6의 기본 프로토콜 RESP3를 이 머신의 Redis 3.0이 지원하지 않는다 | node-redis 5가 보안 패치를 끝내거나, 쓰려는 Node 버전을 지원하지 않는다 |
| Redis 3.0을 유지하고, 인증 티켓 계약에는 소비 명령이 아니라 성질(읽고 지우며 지운 쪽만 통과)을 적는다 | 3.0에 없는 명령이 있어야만 풀리는 요구가 생긴다 |
| `typescript`는 6.0 계열로 고정한다 | `typescript-eslint`가 7을 지원하기 시작한다 |
| `bcrypt`는 네이티브 패키지를 유지한다 | Node를 올렸을 때 `bcrypt`의 미리 빌드된 바이너리가 없다 |
| `dotenv` 대신 Node의 `--env-file` 옵션을 쓴다 | 테스트나 스크립트가 `.env`를 따로 읽어야 하는 일이 반복된다 |
| 키 이름과 기본값만 채운 `.env.example`을 커밋하고, 설정 모듈이 요구하는 키와 대조하는 테스트를 둔다(#235) | 예시 파일과 실제 `.env`의 키가 어긋나 기동이 실패한 일이 테스트를 통과한 뒤에 나온다 |
| 진행 상태는 이 파일의 진행 표가 원천이다 | 진행 표와 PR 상태가 어긋난 채 발견된다 |
| `bcrypt`의 타입은 `@types/bcrypt`로 받고, `mssql`은 쓰는 API만 저장소 안의 선언 파일(`src/types/`)에 적는다(#235) | `mssql`을 올린 뒤 선언 파일과 실제 API가 어긋난 것을 실행해서야 안다 |
