# 맵 데이터를 에디터에서 추출하고 룸을 맵의 사본으로 바꾸기

## 목표

- 서버가 알아야 하는 공간 정보(배치, 영역, 맵 메타데이터, 내비게이션)와 에셋 정보(몽타주 타이밍, 루트 모션, 캡슐)가 에디터에서
  추출되고, 사람은 스크립트 하나로 추출을 돌린다
- 룸이 맵 하나 전체의 사본이 되고, 채널 변경과 AOI가 동작한다
- 몬스터가 레벨에 배치한 스폰 지점에서 나오고 리젠되며, navmesh 경로로 움직인다
- 상점이 NPC 엔티티에 딸리고, 서버가 판매 목록과 거리를 검사한다
- 인게임 PIE의 경고가 틱마다 쌓이지 않는다

결정과 근거는 `docs/adr/0023-treat-room-as-map-copy.md`, `docs/adr/0024-build-server-navmesh-from-extracted-geometry.md`,
`docs/adr/0025-place-spatial-data-with-editor-only-markers.md`와 #334 본문에 있다. 다음 작업(플레이어 공격과 피격 판정)이 이 작업의
추출 데이터를 쓴다.

## 세션 시작 절차

1. 통합 브랜치를 체크아웃한다. 없으면 `dev`에서 딴다. `dev`에 새 커밋이 있으면 merge한다(rebase하지 않는다)
2. 진행 표에서 차단이 모두 「머지」인 첫 「대기」 티켓을 고르고, 그 이슈 본문을 읽는다. 「진행」인 티켓이 있으면 「기록」에서 어디까지 했는지 먼저 읽는다
3. 티켓 브랜치를 통합 브랜치에서 따고 PR은 통합 브랜치로 보낸다. 그 PR에 진행 표의 해당 줄을 「머지」로 고치는 변경을 함께 넣는다.
   머지되면 `close-merged-issues` 워크플로가 PR 본문의 `Closes #N` 이슈를 닫는다. 닫히지 않았으면 손으로 닫는다

## 지킬 것

- 티켓 PR을 머지한 시점에 서버가 뜨고 게임이 동작한다. 서버를 고친 티켓은 서버 솔루션 빌드(DummyClient 포함)와 `GameServerTests`가
  통과하고, 입장 경로를 건드린 티켓은 실제 DB 테스트도 통과한다. 클라이언트를 고친 티켓은 클라이언트 빌드와 `Run-UeTests.ps1`이 통과한다.
  기획 표를 고친 티켓은 DataBuilder 테스트가 통과한다
- 게임플레이를 바꾸는 티켓은 클라이언트, 서버, 프로토콜 세 곳을 함께 고칠 대상으로 먼저 확인한다
- 추출 산출물 폴더에는 사람이 쓴 파일을 두지 않는다. DataBuilder 산출물 폴더에 추출 산출물을 쓰지 않는다
- 배치 마커에는 공간과 기획 데이터의 행 번호만 둔다. 수치와 규칙은 기획 표에 둔다(ADR-0025)
- 맵 단위 데이터(배치 데이터, navmesh)는 서버가 기동할 때 한 번 읽고 바꾸지 않는다. 룸들은 `const`로 함께 읽고, Detour 질의 객체만 룸마다 둔다
- 다른 룸의 오브젝트에 직접 손대지 않는다. 채널 변경도 퇴장과 입장을 거치는 룸 이동이다
- 레벨(`L_InGameMap`)과 에셋 테이블은 병합할 수 없다. 같은 에셋을 고치는 티켓(B와 G의 레벨, A와 E의 몬스터 에셋 테이블)은 동시에 진행하지 않는다
- 서버의 `Room.cpp`는 C, D, F, G가 모두 고친다. 2단계에서는 C와 E를 병렬로 진행하고, C를 머지한 뒤 D를 시작한다
- 추출 커맨드렛(`P1PlacementExtractCommandlet`)과 추출 스크립트(`Invoke-PlacementExtract.ps1`)는 D와 E가 모두 고친다. D와 E는 동시에 진행하지 않는다
- 에디터 작업(마커 배치, 에셋 이동과 삭제, 메뉴 실행)은 Claude가 그 직전까지 진행하고 절차를 사람에게 인계한다. 언리얼 MCP로 에디터를 바꾸기 전에는 커밋 상태를 확인한다
- 스키마 변경은 예상하지 않는다. 생기면 SQL 초안을 사람에게 넘긴다
- 작업하다가 새로 찾은 결함은 그 자리에서 고치지 않는다. 「기록」에 적고 `docs/tech-debt.md`에도 적는다
- 진행 표의 「검증」에는 실제로 돌린 것만 적는다
- 통합 브랜치를 `dev`에 넣을 때는 merge commit으로 한다

E를 D가 아니라 C와 묶은 것은 D와 E가 추출 커맨드렛과 추출 스크립트를 함께 고치기 때문이다. E는 이 작업의 어느 티켓도 막지 않으므로,
C와 묶어도 F까지 가는 경로(C → D → F)는 길어지지 않는다.

**설계 (2026년 10월 29일)**

  두므로(`bTickBeforeOwner`), 「액터 다음에 MoveSync」 조건이 순환을 만들어 버려진다. 지금 실제로 도는 순서는 MoveSync → 무브먼트 → 액터다
- 몬스터 BP 13개와 공격 시스템 BP 컴포넌트의 그래프를 언리얼 MCP로 열어 보았다. 말단 BP는 모두 비어 있고, 베이스에는 연결되지 않은 기본 이벤트만 있다

**#335 (2026년 10월 29일)**

- 몬스터 에셋 테이블의 행에 피격·사망 몽타주 칸을 넣지 않았다. 이슈 본문과 다른 결정이다. 피격 몽타주는 어느 몬스터 BP에도 없다.
  사망은 애니메이션 BP의 `Death` 상태가 시퀀스로 재생하고, 공격 시스템 BP 컴포넌트의 `DeathAnim`은 아무도 읽지 않는다(슈퍼 미니언의 값도
  근접 미니언의 몽타주를 가리켰다). #339는 공격 몽타주와 캡슐만 추출하므로 사망 몽타주가 필요 없다
- 행은 메시, 애니메이션 BP, 머티리얼 배열, 메시 오프셋, 메시 스케일, 공격 몽타주 배열, 캡슐 반지름과 반높이(cm)를 가리킨다.
  메시 오프셋은 이슈 본문에 없던 칸이다. 메시의 상대 위치 Z가 모델마다 달라서(근접 -67, 원거리 -62, 슈퍼 -88) 캡슐 반높이로 대신할 수 없다
- 몬스터 BP는 `Common/BP_Monster` 하나를 남겼다. 네임플레이트 위젯 컴포넌트가 위젯 블루프린트(`WBP_Nameplate`)를 가리켜야 하는데,
  ADR-0009가 에셋 경로를 코드에 적지 못하게 하기 때문이다
- 공용 몬스터 클래스는 스포너 BP(`BP_ObjectSpawner`)의 기본값에서 지정한다. 레벨(`L_InGameMap`)에 놓인 스포너를 고치지 않는다
- 행의 값은 지우기 전의 몬스터 BP에서 언리얼 MCP로 읽었다. 머티리얼 덮어쓰기, 메시 스케일, 액터 스케일은 모든 BP에서 기본값이었고,
  말단 BP는 모델별 베이스의 메시 위치·캡슐·몽타주를 덮어쓰지 않았다
- 사람의 PIE 확인을 마쳤다. 인게임에 약 2분 44초 머무는 동안 에디터 로그에 `LogTick`, `LogSpawn`, 슬롯 수, PoseAsset, 몬스터 스폰 경고가
  한 건도 없었다
- 언리얼 MCP의 `AssetTools.delete`가 `true`를 돌려주고도 BP 파일 일부를 디스크에 남겼다. 로그에는 메모리에서만 지웠다는 기록(`Force Deleting`)이 있었다.
  남은 파일은 에디터를 닫은 뒤 `git rm`으로 지웠다
- 슈퍼 미니언의 공격 몽타주(`Attack_D_SetA_Montage`)는 `Minion_Lane_Core_Skeleton` 기반이고, 슈퍼 메시는 `SK_Minion_Lane_Super`를 쓴다.
