# 슬롯 구조 재설계: 전용 상태 타입, 구역 컨테이너, 위젯 역할 분리, 퀵슬롯

## 목표

- 게임 서버와 클라이언트가 아이템과 칸의 상태를 전용 타입으로 들고, Protocol 타입은 패킷 경계에서만 쓴다
- 인벤토리의 구역 셋과 착용 장비가 같은 칸 주소 체계를 쓰는 컨테이너다. 컨테이너를 다루는 코드에 컨테이너 종류별 분기가 없다
- 패킷이 칸 주소와 아이템 uid로 칸을 가리키고, 칸 변경을 칸 변경 목록 하나로 싣는다
- 클라이언트 컨테이너가 자기 칸을 고친 뒤에 알리고, 위젯은 컨테이너만 보고 그리며 의도만 넘긴다
- 플레이어가 소모품을 퀵슬롯에 등록하고 1~9 키로 쓰며, 배치가 진행으로 저장된다

## 결정

| 결정 | 틀렸다는 신호 |
|---|---|
| 아이템과 칸의 상태는 티어마다 전용 타입으로 든다. 서버는 표준 라이브러리 타입, 클라이언트는 `USTRUCT`다. Protocol 타입은 변환 함수에서만 쓰고, 변환 함수는 티어마다 파일 하나에 모은다(ADR-0019) | 변환 함수에서 필드 누락이 반복된다 |
| 칸의 `UpdateState`를 프로토콜에서 지운다. 칸 변경은 「이 주소의 칸은 이제 이 내용이다」로만 표현한다 | 받는 쪽이 추가와 수정을 구별해야 하는 표시(획득 연출 등)가 생긴다 |
| 인벤토리의 구역은 각각 컨테이너다. 칸 주소는 컨테이너 종류와 칸 번호다. DB는 지금처럼 `(Container, ItemType)`으로 저장하고 대응은 서버의 한 곳에만 둔다(ADR-0018). game-db 작업의 「인벤토리는 컨테이너 하나」는 DB 열 값에 관한 결정이고, 그 값은 바뀌지 않는다 | 아이템 종류와 무관한 구역이 생기거나, 구역을 가리지 않는 인벤토리 전체의 규칙이 생긴다 |
| 서버는 범용 칸 배열 클래스 `ItemContainer`를 두고, 인벤토리와 장비 컴포넌트가 그 위에 규칙을 얹는다. 규칙을 정책 객체로 범용화하지 않는다 | 컴포넌트 셋 이상이 같은 규칙 코드를 복제한다 |
| 응답은 칸 변경 목록으로 칸 변경을 싣는다. 이동(`from/to`) 형태로 표현하지 않는다. 스탯과 외형은 착용 응답의 별도 필드다 | 클라이언트가 칸 변경 목록만으로 그릴 수 없는 연출(이동 애니메이션 등)이 필요해진다 |
| 요청은 칸 주소와 아이템 uid로 칸을 가리키고 의도별로 유지한다. 칸 이동 요청은 드래그 이동이 생길 때 만들고, 그때 착용과 해제를 합친다 | 플레이어가 도착 칸을 고르는 조작이 생긴다 |
| 착용 장비의 칸 번호는 장비 부위 값(1~6)이고 0번 칸이 없다. 컨테이너가 유효한 칸 번호 집합을 든다 | 같은 부위에 칸이 둘인 장비(반지 둘 등)가 생긴다 |
| 장비 정보의 추가 공격력 두 필드를 지운다 | 장비 옵션 기능을 만들기 시작한다 |
| 클라이언트는 컨테이너마다 같은 클래스 `UP1ItemContainer`의 인스턴스를 하나씩 둔다. 서브클래스를 두지 않는다. 컨테이너가 자기 칸을 고친 뒤에 자기 델리게이트를 쏜다 | 클라이언트 컨테이너가 종류마다 다른 행동을 해야 한다 |
| 클라이언트 아이템 상태의 소유자는 `UP1MyPlayerData`다. 아이템 전용 서브시스템을 따로 두지 않는다. 응답 하나가 칸과 골드·스탯·재사용 대기를 함께 바꾸기 때문이다. 접속 종료 때 비운다 | 아이템 상태만 다른 생명주기를 가져야 한다 |
| 슬롯 위젯은 표시할 내용만 받는다. 컨테이너 위젯은 클릭을 의도로 바꾼다. 판정과 응답 대기와 송신은 위젯이 아닌 `UP1ItemActions`가 맡는다. 상속은 컨테이너 위젯 베이스 한 단계(격자형, 고정 배치형)만 둔다 | 컨테이너 종류마다 위젯 클래스가 생긴다 |
| 인벤토리 창은 지금의 탭 전환(격자 셋)을 유지하고 격자마다 컨테이너를 고정한다. 격자 하나에 컨테이너를 바꿔 끼우지 않는다 | 탭이 늘어 격자를 미리 만드는 비용이 문제가 된다 |
| 아이콘과 툴팁 조회를 전역 설정 한 곳으로 모은다 | — |
| 데이터는 서버 응답으로만 바뀐다. 낙관적 갱신을 하지 않는다 | 원격 서버에서 조작 지연이 체감된다 |
| 퀵슬롯은 컨테이너가 아니라 아이템 정의를 가리키는 참조다. 소모품만 등록하고, 데이터 형태는 「종류 + id」로 두어 스킬을 더할 길을 연다 | 장비 교체처럼 특정 아이템 하나를 가리켜야 하는 퀵슬롯이 필요해진다 |
| 퀵슬롯은 서버가 진행의 일부로 저장한다. 테이블은 `QuickSlot(CharacterId, SlotIndex, RefType, RefId)`이고 빈 퀵슬롯은 행이 없다. `RefType`의 검사는 `>= 1`이다 | — |
| 퀵슬롯을 쓰면 서버가 소모품 구역에서 칸 번호가 가장 작은 칸을 고른다 | 플레이어가 어느 묶음을 먼저 쓸지 고르고 싶어 한다 |
| 퀵슬롯 등록은 드래그앤드롭이다. 인벤토리 안의 칸 이동은 범위 밖이다 | — |
| 퀵슬롯 개수는 기획 데이터 한 곳에서 오고 키는 1~9다 | — |
| 등록한 소모품이 다 떨어져도 등록을 유지한다. 서버는 등록 요청에서 소모품 종류인지만 검사한다 | — |
| `Item.md`의 dirty 칸 집합, 창고, `UTileView`, UMG MVVM은 들이지 않는다 | 저장 시점이 접속 종료 밖으로 늘어난다(dirty) · 칸 수가 수백이 된다(`UTileView`) |

## 기록

- 2026-10-21: 설계 논의에서 위 결정을 정했다. 판단 과정과 고르지 않은 대안은 `docs/reports/2026-10-21-slot-structure-decisions.html`에 있다(git이 추적하지 않는다). 위젯 BP 그래프는 언리얼 MCP 연결이 거부되어 보지 못했다. #275와 #276에서 먼저 확인한다
- 2026-10-21: #272에서 서버 소지품을 전용 타입(`Game/Items/`)과 범용 칸 배열 `ItemContainer`로 옮겼다. 패킷은 옛 계약 그대로지만 두 가지가 달라졌다.
  응답의 바뀐 칸은 아이템이 남으면 `MODIFIED`, 비면 `REMOVED`이고 `ADDED`를 쓰지 않는다. 입장 패킷의 칸은 모두 `NONE`이고 착용 장비 맵에 0번 키가 없다.
  클라이언트는 `REMOVED`만 읽고 장비 부위가 아닌 키를 건너뛰므로 동작은 같다고 코드로 판단했다. PIE 확인은 하지 않았다
- 2026-10-21: #273에서 계약을 바꿨다. 칸 주소는 `SlotAddress`, 칸 변경은 `SlotChange`, 입장 패킷의 컨테이너 하나는 `ContainerSlots`(칸 번호와 내용인 `Slot`의 목록)다.
  착용과 해제 응답의 외형 필드 `slot_id`를 `gear_type`으로 바꿨다. 판매 응답도 칸 변경 목록을 싣는다. 서버는 요청의 uid가 0이거나 칸의 아이템 uid와 다르면 거절하고, 템플릿 번호는 대조하지 않는다.
  클라이언트는 #274 전까지 칸 사본으로 `Protocol::SlotChange`를 쓴다. `UP1Inventory`와 `UP1Equipment`가 입장 패킷에서 칸을 복사해 들고, `UP1MyPlayerData`는 골드만 `int64`로 든다.
  슬롯 위젯은 아이템이 없는 칸 변경을 받으면 그 위젯이 아이템을 들고 있을 때만 비운다. 옛 `NONE` 칸처럼 한 번도 채운 적 없는 칸의 초기 텍스처를 남기기 위해서다. PIE 확인은 사람이 한다
- 2026-10-22: #274에서 클라이언트가 아이템과 칸을 `USTRUCT`(`Game/Items/`)로 든다. `UP1MyPlayerData`가 컨테이너 넷을 `UP1ItemContainer`의 인스턴스로 소유하고, 응답의 칸 변경을 컨테이너별로 나눠 준다.
  유효한 칸 번호는 입장 패킷에 실린 칸들이 정하고, 그 밖의 칸 변경은 경고를 남기고 버린다. 접속이 끊기면 `UP1GameInstance`가 컨테이너를 비우고, 입장 패킷에 없는 컨테이너도 입장 때 빈다.
  장비의 강화 수치와 내구도는 읽는 곳이 없어 변환하지 않았다. `FP1InventorySlotAction::Decide`는 컨테이너 인자로 `EP1ContainerType`을 받는다.
  위젯 BP는 고치지 않았다. 바뀐 C++ 멤버가 BP에 노출되지 않았기 때문이다. 수용 기준의 「Protocol 타입이 없다」는 ADR-0019의 범위대로 아이템과 칸의 상태로 읽었다. 플레이어 정보와 스탯은 아직 Protocol 타입이다
- 2026-10-22: #275에서 아이템 요청을 `UP1ItemActions`(`Game/Progress/`, `UP1MyPlayerData`의 하위 객체)로 모았다. 의도는 `EP1ItemIntent`(사용, 해제, 판매)이고,
