# 프로젝트를 마무리하고 README와 최종 문서 만들기

## 목표

- 공개 저장소의 README만 읽고 무엇을 만들었는지, 어떻게 띄우는지 알 수 있다
- 면접 전에 다시 읽을 최종 문서가 `docs/final/`에 있다
- 시연 영상이 README에 연결되어 있다

## 결정

2026년 11월 12일에 사람과 정했다. 참고한 양식은 `Project_Dedicated` 저장소의 README와 그 PC의 `Docs/Final/`이다.

**범위**

- 코드는 `dev`의 `6186a77f`에서 동결한다. 시연 경로를 막는 결함만 고치고, 나머지는 README 「알려진 한계」에 적는다
- 독자는 둘이다. README는 게임 서버 프로그래머 채용의 담당자와 면접관이 읽고, `docs/final/`은 면접을 준비하는 본인이 읽는다
- 공개하는 것은 README, `docs/assets/`의 아키텍처 도해와 스크린샷, 영상 링크다. `docs/final/`은 추적하지 않는다
- 기능으로 적지 않는 것: 아이템 드롭(표와 조회 함수만 있고 판정이 없다), 마법사, 원거리 몬스터 전용 AI, PvP, 스킬, 퀘스트, 봇과 부하 테스트, 게임 서버와 UE의 CI
- ServerCore는 강의를 따라 작성한 코드가 90%쯤 그대로 남아 있다. DummyClient와 클라이언트의 패킷 송수신 계층에도 일부 남아 있다.
  README 「개발 방식」과 어필 가이드에 밝히고, 강의 이름 자리는 비워 둔다. 사람이 채운다

**글**

- 본문은 「-다」 평서체의 완결된 문장으로 쓴다. 대시로 부연하지 않는다. 화면에 띄울 자막과 면접에서 말할 대사만 존댓말이다
- 낱말은 `CONTEXT.md`를 따른다. README는 저장소 고유의 낱말을 처음 쓸 때 한 번 풀이한다
- 분량을 늘리지 않는다. 코드를 열면 보이는 것(파일 목록, 메서드 목록)은 적지 않는다
- README의 테스트 건수는 동결 검증에서 실제로 돌린 값만 적는다

문서에 넣은 `파일:줄`은 스크립트로 동결 커밋과 전수 대조한다. 중간 산출물과 스크립트는 `docs/final/` 아래에 둔다.

**어필 가이드의 A급 후보** (순위는 기능 설명 문서를 다 쓴 뒤에 정한다. ServerCore는 내세우지 않는다)

1. 티어 경계: 인증 서버와 게임 서버를 Redis 계약 하나로 잇고, 월드 선택이 일회용 인증 티켓을 발급한다
2. 진행 저장의 정합성: 진행 사본 하나, DB 스레드는 살아 있는 플레이어를 만지지 않음, 저장 뒤에만 재입장
3. 서버 권한의 전투 판정: 액션 단위 판정, 공격 범위는 기획 데이터, 타격 시점은 추출 데이터
4. 룸의 동시성 모델: 맵 사본, 룸 틱, 셀 시야. 잡 큐의 동작 방식은 강의에서 온 것이라고 나눠 적는다
5. 데이터 파이프라인: 기획 데이터 타입 생성과 기동 대조, 서버 navmesh 직접 빌드

**영상**

- 증명할 명제는 「세 티어가 한 바퀴 돌고, 결과는 서버가 정한다」다. PIE 클라이언트 둘과 게임 서버 콘솔을 한 화면에 담는다
- 서버의 판정이 드러나는 장면: 같은 계정의 새 접속이 앞 연결을 끊음, 재접속 뒤 위치와 진행 복원, 공격 범위 디버그 표시와 실제 피격의 일치, 한 클라이언트의 처치가 다른 클라이언트에 같게 보임
- 유튜브에 일부 공개로 올린다. README의 스크린샷을 누르면 영상으로 간다

## 세션 시작 절차

1. 진행 표에서 첫 「대기」 단계를 고른다. 「진행」인 단계가 있으면 「기록」에서 어디까지 했는지 먼저 읽는다
2. PR이 있는 단계는 이슈를 만들고 `dev`에서 브랜치를 딴다. 그 PR에 진행 표의 해당 줄을 고치는 변경을 함께 넣는다
3. `docs/final/`만 고치는 단계는 PR이 없다. 진행 표와 「기록」은 다음 PR에 함께 넣는다
