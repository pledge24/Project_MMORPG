# 하네스

어떤 스킬이 언제 도는지, 그리고 스킬이 답해주지 않는 판단 기준.
절차 상세는 각 스킬에 있다. 여기에 옮겨 적지 않는다.

---

## 스킬

| 스킬 | 언제 | 무엇을 |
|---|---|---|
| `new-work` | 며칠 걸리는 작업, 되물을 것이 셋 이상, 되돌리기 어려운 변경 | work 파일 3스텝 생성. 커밋 2회 |
| `end-session` | 작업이 끝났거나 중단할 때 | work 마감 → 증명 대조 → tech-debt → ADR → `NEXT.md` |
| `new-adr` | 되돌리기 비싼 결정, 기존 ADR 대체, work 결정 승격 | MADR 작성 + `index.md` 갱신 |
| `project/tdd-slice` | GameServer 순수 로직, AuthServer 설정 | 슬라이스 하나 (seam 승인 → 빨강 → 커밋 → 초록) |
| `project/three-tier-change` | `.proto` 수정이 필요한 변경 | 프로토콜·서버·클라 세로 슬라이스 |

에이전트: `test-auditor` — 실패 테스트 커밋 직전 감사. `tdd-slice` 4번 스텝에서 호출.

외부: `grill-me` — `new-work` 스텝 1에서만.

---

## 스킬을 만들지 규칙으로 둘지

**절차가 3스텝 이상이고 순서가 중요하면 스킬, 그 외는 `CLAUDE.md` 규칙.**

같은 실수가 두 번이면 규칙, 세 번이면 훅 승격을 검토한다.

---

## 문서를 고를 때

| 쓰려는 것 | 어디 |
|---|---|
| 다음에 무엇을 할지 | `NEXT.md` — 미래를 말하는 유일한 문서 |
| 깨면 안 되는 제약 | `ARCHITECTURE.md` 불변식 |
| 지금 틀린 것 | `tech-debt.md` D-NN |
| 이번에 무엇을 했나 | `work/` |
| 왜 그 방식인가 | `decisions/` |
| 이 결정을 남에게 설명 | `reports/` |

**work 파일에 「다음에 할 것」을 적지 않는다.** tech-debt 에 순서를 적지 않는다. 세션 프롬프트를 따로 커밋하지 않는다.

---

## work 「결정」인가 ADR인가

> 다음 작업을 할 때 이 결정을 다시 봐야 하나?

봐야 하면 ADR, 안 봐도 되면 work 「결정」. **애매하면 work 에 남긴다.** ADR 개수가 늘면 각각이 가벼워진다.

| | work 「결정」 | ADR |
|---|---|---|
| 유효 범위 | 이 작업 안에서만 | 앞으로의 작업에도 |
| 수정 | 계속 고침 | 고치지 않음. 새 번호로 대체 |
| 예 | 콘솔 UTF-8 을 `TestMain.cpp` 로 설정 | UE LLT 기각, 판정은 종료 코드 |

ADR 대상이 아닌 것: 함수 하나의 에러 처리, 모듈의 재시도 로직, 네이밍. 커밋 메시지의 영역이다.

---

## 규모 판단

| 규모 | 기준 | 하는 것 |
|---|---|---|
| 가벼움 | 파일 1~2개, 되돌리기 쉬움, 테스트가 이미 덮음 | 플랜 모드만. 커밋 없음, 브랜치 없음 |
| 보통 | 파일 3개 이상, 새 엔드포인트나 화면 | `new-work` 스텝 3만. 브랜치 + 스쿼시 머지 |
| 무거움 | 스키마 변경, 인증·프로토콜, 되돌리기 어려움 | `new-work` 전체 |

「왜 이 작업인가」를 쓸지의 실제 기준은 길이가 아니다.

> **지금 이걸 남에게 설명하면, 되물을 것이 셋 이상 있는가?**

있으면 쓴다. 하루짜리여도 쓴다. 없으면 며칠 걸려도 건너뛴다.

## TDD가 도는 범위

| 대상 | 러너 | 루프 |
|---|---|---|
| GameServer 순수 로직 | `GameServerTests.exe`, 종료 코드 | 가능 |
| AuthServer 설정 | `npm test` | 가능. 가장 빠름 |
| GameServer Room·DB·IOCP | 없음 | **불가.** JobQueue 비동기 |
| AuthServer 라우터·인증 | 없음 | 가능하나 비쌈 (bcrypt+MSSQL+Redis) |
| UE 클라 | 없음 | **불가.** L2 는 에디터 필요, L3 는 Live Coding 비호환 |

불가 영역은 빌드 통과 + DummyClient 스모크가 하한이다.

## seam

관찰 가능한 공개 경계. 여기서 테스트하면 내부를 전부 다시 써도 동작이 살아남는다.

**합의하지 않은 seam 에는 테스트를 쓰지 않는다.** 사람이 먼저 승인한다.

| seam | 상태 |
|---|---|
| `Inventory` 공개 API | 존재 |
| protobuf 메시지 왕복 | 존재. 리플렉션으로 자동 확장 |
| 프로토콜 ID 목록 | 존재 |
| 전투 판정 | 없음. `Room` 안에 얽혀 있다 |
| `Gamedata` 테이블 로딩 | 미확인 |

seam 이 없으면 만드는 작업이 선행되고, 그것은 리팩토링이므로 별도 work 파일이 필요하다.

---

## 채점자가 셋이다

| 채점자 | 답하는 질문 | 성격 | 빈도 |
|---|---|---|---|
| 사람 | 이 seam 이 맞나 | 판단 | 슬라이스 시작 |
| `test-auditor` | 이 **테스트**가 좋은 테스트인가 | 판단 | 테스트 커밋 직전 |
| 러너 | 이 **코드**가 맞나 | 결정론 | 매 사이클 |

**`test-auditor` 를 빨강-초록 루프 안에 넣지 않는다.** 기계적 채점을 만들려고 TDD를 쓰는데 채점을 다시 판단에 맡기게 된다. 감사 대상은 코드가 아니라 테스트다.

실패 테스트는 코드 에이전트가 쓴다. 안전장치는 에이전트 분리가 아니라 **커밋 + 잠금 훅**이다.

---

## 안티패턴 셋

러너가 잡지 못한다. 동어반복 테스트는 통과한다.

| 이름 | 뜻 |
|---|---|
| 구현 결합 | 내부 구현을 검사한다 |
| 동어반복 | 실질적으로 아무것도 주장하지 않는다 |
| **수평 슬라이싱** | 하나의 동작이 아니라 한 계층을 자른다 |

세 번째가 이 프로젝트의 최대 위험이다. 게임플레이 변경이 클라·서버·프로토콜 3곳을 건드리는 구조라 계층별로 자르고 싶어진다. **하나의 동작을 세로로 자른다.**

---

## 리팩터링 위치

**빨강-초록 루프 안에서 하지 않는다.** 완료 조건이 없어 멈출 지점을 정할 수 없고, 슬라이스 규율이 깨지고, 슬라이스 하나로는 중복이 아직 안 보인다.

슬라이스가 전부 끝난 뒤 리뷰에서 스멜을 뽑고, 행선지를 나눈다.

| 스멜 | 어디로 |
|---|---|
| 이번 work 범위 안이고 30분 내 | 지금 고침 |
| 범위 밖 | `tech-debt.md` (D-NN 부여) |

---

## 계획 밖 발견

**즉석에서 고치지 않는다.** `tech-debt.md` 에 기록하고 넘어간다.

즉석 수정은 work 파일과 실제 diff 의 대조를 무의미하게 만들고 범위를 두 배로 키운다.

구현이 계획에서 벗어나면 같은 커밋에서 work 파일의 Phase 도 갱신한다.

---

## 머지

기능 브랜치는 스쿼시한다. 계획은 이미 main 에 있으므로 스쿼시 대상에 들어가지 않는다.

```bash
git checkout main
git merge --squash '#<issue>-<Topic>'
git commit -F <메시지 파일>
git branch -D '#<issue>-<Topic>'
```

스쿼시하지 않는 경우는 둘이다. 커밋이 서른 개쯤 되어 `git bisect` 로 좁힐 수 없을 때(브랜치를 미리 쪼갠다), 그리고 외부 기여를 받게 됐을 때.
