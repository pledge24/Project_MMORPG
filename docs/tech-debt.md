# Tech Debt

지금 틀린 것만 담는다. 해결이 확정되면 항목을 지운다 — 수정 완료 표기를 남기지 않는다.
무엇을 어떻게 고쳤는지는 커밋이 갖는다.

항목 27개 (높음 1 · 중간 1 · 낮음 25) · 다음 번호 TD-077

## 작성 방법

항목마다 `TD-NNN` 번호를 붙인다. 번호는 항목을 만든 순서다. 새 항목에는 파일 맨 위의 「다음 번호」를 쓰고,
「다음 번호」를 하나 올린다. 항목을 지워도 그 번호를 다시 쓰지 않는다. 다른 문서에서 항목을 가리킬 때는 번호와
제목을 함께 적는다.

항목은 심각도 절(`# 높음`, `# 중간`, `# 낮음`)에 넣는다. 세 절은 `---`로 나누고, 항목이 없는 절도 지우지 않는다.
심각도를 바꾸면 항목을 그 절로 옮기고 번호는 그대로 둔다. 한 절 안에서는 난이도가 낮은 항목을 위에 두고,
난이도가 같으면 번호 순서로 둔다.

### 새 항목 양식

아래 블록을 복사해서 쓴다.

```markdown
## TD-NNN 무엇이 틀렸는가를 한 줄로
> **심각도:** 높음 · **난이도:** 중간 · **범위:** 기능 · client
> 위치: `경로` N~N줄
> 등록일: 2026년 0월 0일

문제 상황을 적는다. 필요하면 표를 쓴다.

### 영향

**문제 유형** · **문제 유형** — 방치했을 때의 손실과 리스크를 실측 결과로 적는다.
```

- 줄 번호는 특정할 수 있을 때만 적는다. 파일 전체가 문제면 괄호에 총 줄 수를 적는다
- 경로가 넷을 넘거나 특정할 수 없으면 공통 상위 디렉터리를 적는다
- 영역은 하나만 고른다. 나머지는 본문에서 언급한다
- 문제 유형은 최대 두 개까지 적는다
- 항목을 추가하거나 지우면 파일 맨 위의 개수 줄을 함께 고친다. 추가할 때는 「다음 번호」도 고친다
- 항목을 고칠 GitHub 이슈에는 `tech-debt` 라벨을 붙인다. 이슈를 먼저 열고 나중에 항목을 적었으면 그때 붙인다

|---|---|---|

### 범위

부채가 영향을 미치는 코드의 범위다.

| 값 | 기준 |
|---|---|
| 함수 | 특정 함수 또는 메서드에 한정된다 |
| 파일 | 하나의 파일에 한정된다 |
| 모듈 | 하나의 모듈이나 패키지에 영향을 준다. 한 폴더의 동종 에셋 여러 개도 여기에 넣는다 |
| 기능 | 하나의 기능이나 사용자 시나리오 전반에 영향을 준다 |
| 프로젝트 | 프로젝트 전반의 구조나 여러 기능에 영향을 준다 |

## TD-008 클라이언트가 엔티티를 디스폰할 때 맵에서 지운 원소를 역참조한다
> **심각도:** 중간 · **난이도:** 낮음 · **범위:** 함수 · client
> 위치: `P1/Source/P1/Sync/P1StatefulEntityManager.cpp` 136~149줄 (`DespawnEntity`)
> 등록일: 2026년 10월 5일

`DespawnEntity`는 `Players.Find`로 얻은 원소 포인터를 쥔 채 `UnRegisterEntity`를 부른다. `UnRegisterEntity`가
그 원소를 맵에서 `Remove`한 뒤에 `(*FindPlayer)->Destroy()`로 포인터를 역참조한다. 몬스터 분기도 같은 순서다.
제거된 TMap 원소를 읽는 것은 정의되지 않은 동작이다. 지금은 원소가 있던 메모리가 바로 재사용되지 않아서
동작하는 것으로 보인다. 코드를 읽고 판단했다.

### 영향

**버그 발생 가능성 증가** — 엔진 버전이나 할당 패턴이 바뀌면 디스폰할 때 다른 액터를 지우거나 클라이언트가 죽는다.

## TD-050 DB에서 읽는 캐릭터 이름이 48자에서 잘린다
> **심각도:** 낮음 · **난이도:** 낮음 · **범위:** 함수 · server
> 위치: `Server/ServerCore/DB/DBBind.h` 109~113줄 (`BindCol(int32, WCHAR(&)[N])`)
> 등록일: 2026년 10월 10일

`SQLBindCol`의 버퍼 길이는 바이트 수인데, `DBBind::BindCol`은 `WCHAR` 배열에 문자 수인 `N - 1`을 넘긴다.
`WCHAR[100]` 버퍼는 99바이트로 알려지므로, 드라이버는 널 문자를 빼고 48자까지만 쓴다. 캐릭터 목록
(`CharacterListDAO.cpp`)과 입장 불러오기(`CharacterStateDAO.cpp`)가 이 경로로 `character_name`을 읽는다.
이름 상한(`CharacterCreation`의 `MAX_NAME_LENGTH`)은 50이고 생성 쿼리도 이름을 `NVARCHAR(50)` 변수로 받으므로,
49자나 50자 이름은 읽을 때 잘린다. DB 테이블 열의 실제 폭은 확인하지 않았다. 저장 경로는 이름을 쓰지 않아 DB 값은 그대로 남는다. 코드를 읽고 판단했고 실제 DB에서 재현하지 않았다.

### 영향

**버그 발생 가능성 증가** — 49자 이상인 이름은 캐릭터 목록과 게임 안에서 잘려 보인다. 같은 헬퍼로 다른 문자열 열을
읽으면 같은 비율로 잘린다.

## TD-064 260자 이상의 DB 접속 문자열을 받으면 연결이 실패하지 않고 프로세스가 죽는다
> **심각도:** 낮음 · **난이도:** 낮음 · **범위:** 함수 · server
> 위치: `Server/ServerCore/DB/DBConnection.cpp` 34~35줄 (`Connect`)
> 등록일: 2026년 10월 21일

`Connect`는 접속 문자열을 `WCHAR stringBuffer[MAX_PATH]`(260자)에 `wcscpy_s`로 복사한다. 문자열이 버퍼보다 길면
`wcscpy_s`가 잘못된 매개변수 처리기를 불러 프로세스를 끝내므로, `Connect`가 `false`를 돌려주지 못한다. 실제 DB 테스트를
처음 돌릴 때 찾았다. 터미널에서 복사하다 공백, 줄바꿈, 테두리 문자(`│`)가 섞여 259자가 된 `P1_GAME_DB_TEST_CONNECTION_STRING`으로

259자는 널 문자까지 버퍼에 들어가는 길이다. 그래도 넘친 것은 `Config::ReadProcessEnv`의 `_dupenv_s`가 값을 UTF-8이 아닌
ANSI 코드 페이지로 돌려주고, UTF-8로 읽는 변환에서 `│`가 더 많은 글자로 바뀌었기 때문으로 추정한다. 이 추정은 확인하지 않았다.
게임 서버도 같은 함수로 `P1_GAME_DB_CONNECTION_STRING`에 연결하므로, 긴 값을 주면 사유를 로그에 남기지 못하고 부팅 중에 죽는다.

### 영향

**변경 비용 증가** — 설정 실수가 원인을 알리는 로그 없이 비정상 종료로만 드러나서, 접속 문자열이 원인인지 알아내기 어렵다.

## TD-049 룸 이동에 실패한 플레이어가 끊기면 저장 대기가 풀리지 않는 창이 남는다
> **심각도:** 낮음 · **난이도:** 중간 · **범위:** 기능 · server
> 위치: `Server/GameServer/Game/Room/Room.cpp` (`EnterPlayer`의 `AddEntity` 실패 분기) · `Server/GameServer/Network/ProgressCoordinator.cpp` (`OnDisconnected`)
> 등록일: 2026년 10월 10일

#213은 룸 이동 중에 끊긴 플레이어가 들어갈 룸에 들어가지 못하면 그 분기에서 저장을 넘기게 고쳤다(TD-047). 그 분기는 진행
표시를 CAS 없이 한 번 읽으므로 두 경우가 남는다.

| 경우 | 결과 |
|---|---|
| 실패 분기가 IN_ROOM을 읽은 직후에 끊긴다 | 접속 종료가 떠난 룸에 퇴장을 넣지만 그 룸에는 플레이어가 없어 저장도 대기 해제도 하지 않는다 |
| 끊기지 않은 채 입장에 실패하고 나중에 끊긴다 | 위와 같다. 플레이어는 어느 룸에도 없이 접속해 있다 |

`AddEntity`는 같은 엔티티 번호가 이미 있을 때만 실패하므로 지금은 일어나지 않는다고 보았다. 고치려면 「어느 룸에도 없음」을
진행 표시의 상태로 두고, 실패 분기와 접속 종료 중 정확히 한쪽만 저장하도록 순서를 다시 정해야 한다. #213의 리뷰에서 찾았고,
코드를 읽고 판단했다.

### 영향

**버그 발생 가능성 증가** — 그 플레이어의 진행이 저장되지 않고, 그 계정은 서버를 다시 띄울 때까지 입장하지 못한다.

## TD-058 인증 서버 로그에 남는 ODBC 오류 문구의 한국어가 `?`로 깨진다
> **심각도:** 낮음 · **난이도:** 중간 · **범위:** 모듈 · server
> 위치: `Server/AuthServer/src/main.ts` 33~36줄(기동 실패 로그) · `Server/AuthServer/src/common/db.ts` · `mssql/msnodesqlv8` 드라이버
> 등록일: 2026년 10월 19일

없는 LocalDB 인스턴스를 가리키는 접속 문자열로 `npm start`를 실행하면, 기동 실패 로그의 `ConnectionError` 문구가
`[Microsoft][ODBC Driver 17 for SQL Server]SQL Server? ??? ???? ...`처럼 찍힌다. 한국어 Windows의 ODBC 드라이버가 낸 문구를
드라이버나 `msnodesqlv8`가 유니코드로 바꾸지 못하는 것으로 보인다. 원인이 드라이버, `msnodesqlv8`, 콘솔 중 어디인지는
가리지 않았다. 오류 코드(`code`)와 스택은 깨지지 않는다. 인증 서버 재구성의 회원가입 티켓에서 기동 실패를 확인하다가 찾았다.

### 영향

**유지보수 어려움** — DB 연결이 실패한 이유를 로그만으로 알 수 없어, 같은 접속을 다른 도구로 다시 시도해야 한다.
