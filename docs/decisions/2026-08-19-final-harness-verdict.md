## 수정·확정 항목

### 1. Planner-Generator-Evaluator / AI 역할 분리

- **결정:** 원형 폐기 + 축소형 채택 유지. Plan Mode=Planner, 본 세션=Generator,
  code-reviewer 서브에이전트=Evaluator(🔜 2단계). 단 판정표의 근거 문구
  "1인+현 단계에 과함"을 아래로 교체한다.
- **근거:** 격리(서브에이전트)가 결정적인 역할은 Evaluator뿐이다 — 자기평가 편향은
  자기가 생성한 코드를 전제하므로 계획 시점에는 그 메커니즘이 성립하지 않는다.
  Planner의 본질은 격리가 아니라 쓰기 금지+계획 선행+사람 승인 게이트이며 Plan Mode가
  이를 도구 수준에서 강제한다. 컨텍스트 분리는 세션 경계+docs/plans/ 외부화가 담당한다
  (파일 기반 P-G-E: 계획 세션 → plans 파일 → 구현 세션). Planner 서브에이전트 분리는
  당시 미검토였으나 사후 검증으로 기각 — 계획 품질은 사람과의 왕복(Plan Mode
  승인/반려 루프, grilling 채택 시 계획 심문)에서 나오는데 서브에이전트는 자율 실행 후
  결과 보고 모델이라 이 루프에 사람을 태울 수 없고, 본 세션이 쌓은 코드베이스 이해를
  격리된 Planner가 재탐색하는 토큰 비용도 발생한다.
- **재검토 조건:** (1) Plan Mode 계획의 품질 문제(범위 누락, 잘못된 전제)가 반복되는데
  사람 게이트가 못 잡는 경우, (2) 계획 단계의 탐색 잔해가 구현 품질을 떨어뜨리는 것이
  체감되는데 세션 분리 운영이 번거로워 지켜지지 않는 경우.

### 2. 프롬프트·툴 로그

- **결정:** 판정표의 "reports로 갈음" 폐기. 제3안 채택 — (a) Claude Code transcript
  보존 기간 설정을 연장하고, (b) 세션 종료 루틴에 해당 세션 jsonl을 아카이브(레포 밖
  백업 또는 레포 내 gitignore 디렉토리)로 복사하는 단계를 넣는다. docs/reports/는
  원래 목적(사람용 tech report — 이해 병목 해소 자료)으로 역할을 복원한다.
- **근거:** 재현성 원본은 Claude Code가 이미 전부 기록 중(세션 전체 transcript jsonl)
  이므로 별도 로그 시스템은 이중 기록("기록 시스템이 둘이면 한쪽이 부패한다" 원칙 위반).
  단 자체 transcript는 보존 기간 제한과 레포 외부 위치라는 구멍이 있어 아카이브로 메운다.
  reports는 로그가 아니다 — 사람용 이해 자료와 기계용 재현 기록은 성격이 다르다.
- **역할 분리 명문화:** 원본(재현성) = transcript 아카이브 / 색인(어느 세션이었는지 찾기)
  = docs/reports/. 둘의 역할을 갈라 적어 부패를 방지한다.
- **재검토 조건:** 아카이브만으로 과거 세션 추적이 실패하는 사례 발생 시(색인 부족).

### 3. 프롬프트 획일화

- **결정:** ✅ → ✅(부분)+🔜. 현 prompts/는 우발적 관행의 씨앗(세션 프롬프트의 반복
  골격: 목표 선언→제약 명시→단계→산출물 정의→확인 질문)까지만 인정. 원칙의 완성형은
  동일 유형 작업이 반복될 때 해당 프롬프트를 .claude/commands/ 슬래시 커맨드로
  승격하는 것으로 정의한다.
- **근거:** 원 판정은 "저장소가 존재한다"와 "원칙이 실행되고 있다"를 뭉뚱그렸다
  (판정 작성 세션 자인). prompts/는 획일화를 의도하고 만든 폴더가 아니다. 표본 2~3개
  단계에서 템플릿을 고정하는 대신, 반복이 증명된 뒤 표준화하는 승격 방식이
  "두 번이면 문서, 세 번이면 규칙" 사다리와 일관된다 — 프롬프트도 같은 사다리를 탄다.
- **재검토 조건(=승격 시점):** 같은 유형의 세션 프롬프트를 세 번째 쓰게 되는 시점.

### 4. 레이어 종속성 기계 강제

- **결정:** 2단계 계획으로 재정의. 1단계(지금): code-reviewer 서브에이전트 지시문에
  레이어 경계 체크리스트로 포함(소프트, 확률적). 2단계(리팩토링으로 경계 확정 후):
  #include 경로가 경계 규칙 테이블을 위반하는지 검사하는 자작 스크립트로 승격
  (하드, 결정적 — PreToolUse 훅 또는 리뷰 단계 실행).
- **근거:** 판정표의 "C++ 등가물 부재"는 절반만 맞다 — 완제품이 없을 뿐, 이 규모에서
  필요한 것은 include 검사 스크립트 수준이라 자작 가능하다(stdin JSON 훅+테스트 27개를
  자작한 전례). UE 클라 쪽은 UBT의 Build.cs 모듈 의존성이 일부를 이미 기계 강제 중.
  지금 만들지 않는 이유는 도구 부재가 아니라 **레이어 경계 자체가 미확정**이기 때문 —
  D-01~D-21 리팩토링 전 코드에 규칙을 선언하면 위반 투성이라 예외 처리 속에서 규칙이
  무의미해진다.
- **재검토 조건(=2단계 착수):** 리팩토링으로 서버 레이어 경계가 확정되는 시점.

### 5. 포트폴리오: 숫자 기록

- **결정:** "세션 리포트에 손으로 누적" 폐기. 발생 지점 자동 집계로 수정 —
  (a) 훅 차단 건수: block_dangerous.py가 차단 시 append-only 카운터 파일에 기록
  (훅에 소량 추가), (b) 문서 정정 건수·CLAUDE.md 변경 이력: git log가 이미 집계,
  (c) 테스트가 잡은 회귀 수: 유일한 수동 항목(실패 중 "회귀" 판별이 필요)으로 세션
  리포트에 기록. 세션 리포트는 집계 장부가 아니라 카운터·git에서 읽어오는 조회 창.
- **근거:** 원문의 설득력은 숫자가 파이프라인에서 자동으로 나온다는 데서 온다. 손 집계는
  몇 세션 안에 부패한다(로그 항목과 동일 구조의 문제). 훅 카운터는 소급 생성이 불가능한
  데이터(지나간 차단은 다시 셀 수 없음)라 조기 도입이 정당하다.
- **재검토 조건:** 카운터 유지비가 체감되거나 집계 항목이 포트폴리오 서사에 쓰이지 않는
  것이 확인되면 축소.

### 6. revise-claude-md / claude-md-improver (+ /doctor)

- **결정:** /gc 통합 철회. 스킬을 독립 채택하되(둘 중 하나 — 실제 내용을 열어 선택,
  docs/ 구조에 맞게 수정), 트리거를 주기가 아니라 **"CLAUDE.md를 수정한 세션의
  마무리"**로 건다. /doctor의 기능(하네스가 모델 자유도를 억압하는지·낡은 규칙 탐지)도
  /gc가 아니라 이 스킬에 통합한다. /gc는 문서-코드 드리프트 대조 전담으로 역할을 좁힌다.
- **근거:** 두 작업은 주기가 다르다. 문서-코드 대조는 주기 작업(주 1회)이지만 CLAUDE.md
  수정은 이벤트 구동("같은 실수 2회" 규칙이 이미 그렇게 설계됨)이다. /gc에 통합하면
  수정 주기가 /gc 실행 주기에 종속되고, CLAUDE.md 변경 커밋이 /gc 실행일에 몰려
  "실수→규칙 승격" 서사의 시간적 인과가 git 이력에서 사라진다(포트폴리오 관점 손실).
  이벤트 트리거로 걸면 수정이 일어난 그 자리에서 품질 패스(비대 규칙 정리, 낡은 규칙
  폐기, 중복 병합)가 돈다.
- **재검토 조건:** 트리거 발동 빈도가 지나치게 높아 세션 마무리 비용이 체감되면
  빈도 조절(예: N회 수정마다 1회).

### 7. 스킬: Im-not-ai

- **결정:** ❌ → 🔜 시험 채택. 단 채택 형태를 먼저 판정한다 — 스킬 내용을 열어
  CLAUDE.md 규칙 서너 줄("주석·리포트는 자연스러운 한국어 산문 / 정착 번역어 없는
  전문용어는 영문 그대로 / 발음 전사식 번역 금지")로 압축 가능하면 규칙으로 흡수하고
  스킬은 들이지 않는다. 압축 불가한 구체 패턴 목록이 있으면 스킬로 들이되 적용 범위를
  주석+리포트로 명시한다.
- **근거:** 원 판정 ❌("문체 교정은 코드 프로젝트와 무관")는 주석과 리포트도 문체를
  가진다는 사실을 놓쳤고, 이전 프로젝트의 실증(번역체 주석, 발음 전사식 용어 번역
  남발)이 제시됐다. "필요가 증명되면 재검토" 원칙의 성립 사례. 문체 교정이 매 세션
  상시 적용될 성격이라면 호출형 스킬보다 CLAUDE.md 상시 규칙이 메커니즘상 맞을 수
  있어 형태 판정을 선행한다.
- **재검토 조건:** 세션 2~3의 실제 주석 산출물로 효과 검증. 개선이 확인되지 않으면 제거.

### 8. 스킬: insane-search

- **결정:** ❌ → 🔜 조건부 채택. 호출형이라 미사용 시 무게가 0에 가까우므로 들여놓되,
  승격/제거 조건을 명시한다.
- **근거:** 원 판정의 폐기 근거("필요가 증명된 적 없음")가 이전 프로젝트 실증(웹 자료
  획득의 빈번한 실패)으로 무효화됐다. 단 이전 실패가 접근 실패(차단·403)인지 품질
  실패(쿼리 전략)인지에 따라 처방이 달라지고, 이 프로젝트의 조사 대상(UE 문서·포럼)에서
  실패 양상이 재현될지는 미확인이므로 정식 채택이 아닌 조건부로 둔다.
- **재검토 조건:** 이 프로젝트에서 검색 실패가 2회 재현되면 정식 워크플로우로 승격 /
  상당 기간(수 세션) 호출 0회면 제거. — 2회/3회 승격 원칙을 스킬 채택에 적용.

### 9. 소스 3: harness.md + scripts/execute.py (배치 실행 모드)

- **결정:** "웹용 추정 ❌" 폐기(오판 — 언리얼 전용으로 재작성된 물건임을 확인).
  본체는 🔜 해동 조건부 보류, 즉시 가치가 있는 설계 4건은 ✅ 현행 하네스에 편입.
  판정 경위·충돌 3건·해동 체크리스트·사용법은 **batch-mode-archive.html**에 보관
  (해동 시 이 문서에서 시작, 수확 4건 중복 도입 금지).
- **근거:** 제1 근거는 하네스 복잡도 상한 — 채택 시 실행 모드 2개·커밋 체제 2개·
  빌드 경로 2개를 동시 유지하게 되며 1인 프로젝트에서 유지비가 편익을 앞선다.
  전제 조건도 미성립: AC 재실행이 shell 커맨드 전제라 CLI 빌드 경로 재개방 필요
  ("Rider MCP 전용" 결정과 충돌 — "CI 필요 시 재검토" 단서의 해석은 해동 시점에 확정),
  AC 사다리 3단을 채울 테스트 인프라 부재, 적용 지형(UE 클라 신규 기능 국면) 미진입.
- **편입 4건:** ① 자기신고 불신 원칙(완료 선언 전 검증 커맨드 실제 실행 — CLAUDE.md
  검증 절), ② blocked=정상 인계(plans 체크리스트에 `[B] blocked — 무엇을/어디서` 상태,
  에디터 작업은 우회 금지·기록 후 중단), ③ summary 한 줄 누적(plans 완료 항목 옆
  "생성 파일 경로+핵심 결정" — 차기 세션 프롬프트의 원료), ④ AC 사다리+step 설계 원칙
  6종(세션 프롬프트·계획 작성 지침으로).
- **재검토 조건(=해동):** UE 클라 신규 기능 국면 진입 시. 전제: CLI 빌드 경로 결정,
  테스트 인프라 존재, 저위험 phase 파일럿, CLAUDE.md 배치 모드 커밋 조건 분기.
  상세는 batch-mode-archive.html §03.
