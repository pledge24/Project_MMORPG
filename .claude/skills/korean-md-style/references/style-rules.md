# 한국어 마크다운 문서 규칙 전문

절 번호는 진단 리포트의 규칙 번호와 일치한다. 예문은 모두 가상이다.
파일 종류를 가리지 않고 적용한다. 문서의 구성과 목차는 다루지 않는다.

- 0절 원칙
- 1절 문체와 어미
- 2절 간결성
- 3절 번역투
- 4절 주체와 구체성
- 5절 일관성
- 6절 표기
- 7절 기호
- 8절 체크리스트

---

## 0. 세 가지 원칙

1. **읽는 쪽을 정하고 쓴다.** 에이전트가 읽는 문서에는 판단 근거와 행동 지침을 쓴다. 사람이 읽는 문서에는 맥락을 먼저 준다. 어느 쪽이든 감상은 쓰지 않는다.
2. **한 문장에 하나의 생각.** 문장이 길어지면 읽는 쪽이 문장을 두 번 읽는다.
3. **모호하면 규칙이 아니다.** "적절히", "필요하면", "가급적"은 규칙이 아니라 회피다.

## 1. 문체와 어미

### 1.1 지시 문장은 `~한다` / `~하지 않는다`

무언가를 하라는 문장은 단정형으로 끝낸다.

✅ 좋은 예
```markdown
- 테스트를 먼저 작성한다.
- 커밋 메시지에 이슈 번호를 넣지 않는다.
```

❌ 나쁜 예
```markdown
- 테스트를 먼저 작성해 주시기 바랍니다.
- 커밋 메시지에 이슈 번호를 넣지 않으셨으면 합니다.
```

### 1.2 한 문서 안에서 종결어미를 섞지 않는다

규칙은 단정형, 설명은 `-니다`체로 나누는 방식은 쓰지 않는다. 어미가 다른 두 문장이 붙어 있으면 뒤 문장이 앞 문장에 얹히지 못하고 떠 버린다.

❌ 나쁜 예
```markdown
마지막 항목이 이 절의 핵심입니다. 문서를 채우는 것이 목적이 아닙니다.

**사용자가 읽고 고칠 때까지 넘어가지 않는다.**
```

✅ 좋은 예
```markdown
**마지막 항목을 비우지 않는다.**
— 아직 정하지 않은 것을 드러내는 것이 목적이다. 문서를 채우는 것이 목적이 아니다.

**사용자가 읽고 고칠 때까지 넘어가지 않는다.**
```

문서 전체를 단정형(`~한다`, `~이다`)으로 통일한다. 층위는 어미가 아니라 **줄과 표시**로 가른다(→ 1.3).

### 1.3 근거는 규칙 아래 별도 줄에 줄표로 단다

규칙과 근거를 한 줄에 이어 쓰지 않는다. 이어 쓰면 어디까지가 지켜야 할 규칙인지 경계가 사라진다.

✅ 좋은 예
```markdown
**마이그레이션은 배포 전에 실행한다.**
— 배포 후 실행하면 구버전 코드가 새 스키마를 읽는다.
```

❌ 나쁜 예
```markdown
배포 후에 마이그레이션을 실행하면 구버전 코드가 새 스키마를 읽게 되는 문제가
발생할 수 있기 때문에, 이러한 점을 고려하여 마이그레이션은 배포 전에 실행하는
것이 바람직합니다.
```

- 근거가 한두 문장이면 줄표(`—`) 줄로 붙인다
- 근거가 한 문단을 넘으면 별도 문단으로 뺀다
- 줄표 줄도 본문과 같은 단정형으로 쓴다

### 1.4 금지 어미

`~하시기 바랍니다`, `~하십시오`, `~하세요`, `~해 주세요`는 쓰지 않는다.

| 금지 | 대체 |
| --- | --- |
| 확인해 주시기 바랍니다 | 확인한다 |
| 실행하십시오 | 실행한다 |
| 참고하세요 | 참고한다 / (참고: 링크) |

### 1.5 존칭 `-시-`를 넣지 않는다

✅ `설정 파일을 수정한 뒤 서버를 재시작한다.`
❌ `설정 파일을 수정하신 뒤 서버를 재시작하시면 됩니다.`

### 1.6 목록과 표는 개조식으로 쓴다

목록 항목에 서술형 문장을 넣지 않는다.

✅ 좋은 예
```markdown
- `--dry-run`: 실제 변경 없이 결과만 출력
- `--force`: 확인 절차 생략, CI에서만 사용
```

❌ 나쁜 예
```markdown
- `--dry-run`은 실제 변경 없이 결과만 출력하는 옵션입니다.
- `--force`는 확인 절차를 생략하며 CI에서만 사용하는 것이 좋습니다.
```

## 2. 간결성

### 2.1 한 문장에 하나의 생각만 담는다

생각이 둘이면 문장을 나눈다. 접속 조사(`~고`, `~며`, `~므로`)로 이어 붙인 자리가 대부분 나눌 자리다.

❌ 나쁜 예
```
인증을 마치면 토큰이 발급되고, 이 토큰은 1시간 뒤 만료되므로 만료 전에
갱신 요청을 보내야 하며, 갱신에 실패하면 다시 인증해야 합니다.
```

✅ 좋은 예
```
인증을 마치면 토큰이 발급된다. 토큰은 1시간 뒤 만료되므로 만료 전에 갱신한다.
갱신에 실패하면 다시 인증한다.
```

### 2.2 문장에서 뺄 수 있는 것을 뺀다

문장을 읽고 지웠을 때 뜻이 그대로면 지운다.

| 나쁜 예 | 좋은 예 |
| --- | --- |
| 이 기능은 기본적으로 활성화되어 있는 상태입니다 | 이 기능은 기본으로 켜져 있다 |
| 대부분의 경우에 있어서 이 값을 바꿀 필요는 없습니다 | 이 값은 대개 바꾸지 않는다 |
| 다음과 같은 방식으로 설정을 진행할 수 있습니다 | 아래처럼 설정한다 |

### 2.3 메타 담화를 지운다

말에 대한 말은 핵심을 가린다. 아래 표현이 보이면 문장째로 지우거나 앞뒤를 붙인다.

- 흐름을 설명하는 말: `먼저`, `다음으로`, `앞서 설명했듯이`, `이제 알아보겠습니다`, `결론적으로`
- 강조하는 척하는 말: `사실`, `솔직히 말하면`, `무엇보다`
- 독자에게 동의를 구하는 말: `아시겠지만`, `여러분도 아실 것입니다`, `물론`

❌ `먼저, 앞서 설명했듯이 이 값은 반드시 설정해야 합니다. 물론 예외도 있습니다.`
✅ `이 값은 반드시 설정한다. 예외는 아래 두 가지다.`

순서가 중요하면 흐름 표현 대신 번호를 매긴다.

### 2.4 이중 부정과 겹말을 피한다

✅ `모든 요청에 인증 헤더가 필요하다.`
❌ `인증 헤더가 없는 요청은 허용되지 않는 것은 아니지만 권장되지 않습니다.`

## 3. 번역투

한국어 문서가 어색하게 읽히는 원인의 대부분은 이 절에 있다.

### 3.1 명사형 나열을 동사로 되돌린다

영어는 동사를 명사로 바꿔(`-tion`, `-ing`, `-ment`) 쓰는 게 자연스럽지만 한국어는 동사를 그대로 쓰는 쪽이 자연스럽다.

✅ 좋은 예
```
API 키로 사용자를 인증한 뒤 데이터베이스에 접속한다.
로그를 수집해서 오류 발생 시점을 찾는다.
```

❌ 나쁜 예
```
API 키를 이용한 사용자 인증 처리가 완료된 후 데이터베이스 접속 설정 진행이 가능합니다.
로그 수집 수행을 통해 오류 발생 시점 파악 작업을 실시하게 됩니다.
```

### 3.2 껍데기 한자어를 제거한다

`수행하다`, `실행하다`, `진행하다`, `실시하다`, `처리하다`는 대부분 빼도 의미가 그대로다.

| 나쁜 예 | 좋은 예 |
| --- | --- |
| 삭제 작업을 수행한다 | 삭제한다 |
| 배포를 진행한다 | 배포한다 |
| 검증 처리를 실시한다 | 검증한다 |
| 설정 변경을 수행한 후 적용을 진행한다 | 설정을 바꾼 뒤 적용한다 |

### 3.3 `~을 통해`를 쓰지 않는다

✅ `이 API로 데이터를 가져온다.`
❌ `이 API를 통해 데이터를 가져올 수 있습니다.`

### 3.4 영어식 대명사를 넣지 않는다

`당신`, `여러분`, `우리`는 한국어 기술 문서에서 거의 항상 군더더기다.

✅ `설정을 마쳤다면 서버를 재시작한다.`
❌ `당신이 설정을 마쳤다면, 우리는 서버를 재시작해야 합니다.`

### 3.5 문장 끝에 콜론을 붙이지 않는다

한국어에서 콜론은 항목 열거나 부연 설명에 제한적으로 쓴다. 영어처럼 문장 끝에 붙이는 용법은 없다.

✅ `아래 예제를 참고한다.`
❌ `다음 예제를 참고하세요:`

## 4. 주체와 구체성

이 절의 위반은 뜻을 바꾸거나 지시를 모호하게 만든다. 진단에서 우선순위가 가장 높다.

### 4.1 문장의 주체를 분명하게 한다

누가 무엇을 하는지 드러낸다. 수동태는 주체를 지운다.

✅ `빌드 스크립트가 산출물을 `dist/`에 만든다.`
❌ `산출물은 빌드 스크립트에 의해 `dist/`에 생성되어집니다.`

행동을 지시하는 문장에서는 도구가 아니라 **읽는 쪽**이 주체가 되게 한다.

✅ `배포 전에 마이그레이션을 실행한다.`
❌ `마이그레이션은 배포 전에 실행되어야 한다.`

✅ ``--force`를 붙이면 확인 절차를 건너뛴다.`
❌ ``--force` 옵션에 의해 확인 절차가 생략된다.`

### 4.2 모호한 말을 쓰지 않는다

아래 말이 보이면 무엇을 뜻하는지 되묻고 구체적인 말로 바꾼다. 되물을 상대가 없으면 「판단이 필요한 것」에 올린다.

`적절히`, `가급적`, `되도록`, `너무`, `충분히`, `필요하면`, `상황에 따라`, `등`, `기타`

❌ `설정 파일이 너무 커지면 적절히 분리한다.`
✅ `설정 파일이 300줄을 넘으면 환경별로 분리한다.`

### 4.3 조건은 관찰 가능한 형태로 쓴다

읽는 쪽이 그 자리에서 참·거짓을 판정할 수 있어야 한다.

✅ `테스트 파일이 200줄을 넘으면 파일을 나눈다.`
❌ `테스트 파일이 길어지면 나눈다.`

✅ `응답이 3초를 넘으면 캐시를 확인한다.`
❌ `응답이 느리면 캐시를 확인한다.`

### 4.4 금지는 금지형으로 쓴다

권고형은 예외를 만든다.

✅ `운영 데이터베이스에 직접 쿼리를 실행하지 않는다.`
❌ `운영 데이터베이스 직접 쿼리는 되도록 피하는 것이 좋습니다.`

### 4.5 예외를 명시한다

예외를 적지 않으면 읽는 쪽이 스스로 만든다.

```markdown
- 커밋 하나에 파일 하나만 변경한다.
  - 예외: 이름 변경(rename)에 따른 import 경로 수정은 같은 커밋에 포함한다.
```

### 4.6 지시어에 대상을 붙인다

`아래`, `위`, `마지막 항목`, `이 절`처럼 가리키기만 하는 말은 대상을 함께 적는다. 참조할 목록이 있으면 번호를 매겨 번호로 가리킨다.

❌ `아래가 다 나올 때까지 멈추지 않는다.`
✅ `아래 다섯 가지에 모두 답이 나올 때까지 멈추지 않는다.`

❌ `마지막 항목이 이 절의 핵심이다.`
✅ `5번을 비우지 않는다.`

### 4.7 제목은 내용을 그대로 드러낸다

목차만 읽어도 무엇이 있는지 알 수 있어야 한다. 절을 새로 만들라는 뜻이 아니라, 이미 있는 절의 이름을 구체적으로 쓰라는 뜻이다.

✅ `## 마이그레이션 롤백 절차`
❌ `## 기타 참고 사항`

## 5. 일관성

### 5.1 한 개념에 한 단어

같은 것을 `저장소`, `리포지토리`, `repo`로 번갈아 부르지 않는다. 문서 안에서 한 번 정하고 끝까지 지킨다.

### 5.2 같은 종류의 항목은 같은 형태로 쓴다

한 목록 안에서 어떤 항목은 명사구, 어떤 항목은 문장이면 읽는 쪽이 규칙을 짐작해야 한다.

❌ 나쁜 예
```markdown
- 토큰 발급
- 발급된 토큰을 저장소에 넣습니다
- 갱신 (1시간 주기)
```

✅ 좋은 예
```markdown
- 토큰 발급
- 토큰 저장
- 토큰 갱신 (1시간 주기)
```

### 5.3 외래어

국문 표현이 있으면 국문을 쓴다. 없을 때만 외래어를 쓰고, 최초 언급 시 괄호에 영문을 병기한 뒤 이후에는 국문만 쓴다.

```
메서드(Method), 파라미터(Parameter), 리다이렉트(Redirect)
```

플랫폼, 프로그래밍 언어, 라이브러리, 명령어처럼 국문 표기가 어색한 것은 영문 그대로 쓴다.

```
Android, Kotlin, PostgreSQL, git rebase
```

### 5.4 약어

본문에 쓸 형태를 먼저 적고 괄호에 풀어쓴 말을 넣는다. 이후에는 본문 형태로 일관되게 쓴다.

```
CLI(Command Line Interface), ADR(Architecture Decision Record)
```

## 6. 표기

### 6.1 코드와 UI 표기

- 코드, 파일 경로, 명령어, 데이터 타입: 고정폭 글꼴(`` ` ``)
- UI 요소: 대괄호. 계층은 `>`로 잇는다 — `[설정] > [계정] > [연결된 서비스]`
- 코드를 가리킬 때 수식어를 붙이지 않는다

✅ `` `target_id`에 대상을 지정한다.``
❌ `` `target_id` 파라미터 값으로 대상을 지정합니다.``

### 6.2 라틴 문자 뒤에도 조사를 붙여 쓴다

| 나쁜 예 | 좋은 예 |
| --- | --- |
| Phase 를 나눈다 | Phase를 나눈다 |
| ADR 을 쓴다 | ADR을 쓴다 |
| `main` 에서 커밋한다 | `main`에서 커밋한다 |

### 6.3 강조

굵은 글꼴은 문단당 한 번, 첫 언급에만 쓴다. 여기저기 굵게 쓰면 아무것도 강조되지 않는다.

### 6.4 링크 문구

링크 문구는 대상의 제목이나 명칭으로 쓴다. `여기`, `이 링크`는 쓰지 않는다.

✅ `[마이그레이션 롤백 절차](./rollback.md)를 참고한다.`
❌ `자세한 내용은 [여기](./rollback.md)를 참고하세요.`

### 6.5 위·아래로 가리킨다

문서 요소를 가리킬 때 `이전`, `다음` 대신 `위`, `아래`를 쓴다. 문서는 종이가 아니라 스크롤되는 화면이다.

### 6.6 숫자·날짜·예시

| 항목 | 규칙 | 예 |
| --- | --- | --- |
| 숫자 | 아라비아 숫자. 네 자리 이상은 세 자리마다 쉼표 | `3,000,000건` |
| 시간 단위 | 국문으로 표기 | `2026년 3월 28일 오후 2시 49분` |
| 날짜 데이터 | 시간대와 형식을 괄호에 병기 | `만료 시각(UTC 기준 RFC3339 형식)` |
| 예시 | 괄호 안 또는 줄바꿈 후 `예:` | `요청을 받는 서버 도메인이다. (예: api.example.com)` |
| 참고 | 괄호 안에 `참고:` + 링크 | `(참고: [인증 방법](./auth.md))` |

## 7. 기호

아래 기호만 정해진 용법으로 쓴다.

| 기호 | 용법 |
| --- | --- |
| 온점 `.` | 서술형 문장의 끝. 생략한 코드는 공백 없는 온점 3개 `...` |
| 쉼표 `,` | 나열. 개조식 문장의 부연. 큰 수의 자릿점 |
| 콜론 `:` | 부연 설명. 앞은 붙이고 뒤는 띄운다. 시간 표기 |
| 붙임표 `-` | 표에 넣을 내용이 없음을 표시 |
| 줄표 `—` | 규칙 바로 아래 줄에서 근거를 표시(→ 1.3). 줄 맨 앞에만 쓴다 |
| 괄호 `()` | 용어·문장의 추가 설명 |
| 대괄호 `[]` | UI 요소 |
| 홑낫표 `「」` | 문서 내부의 절 이름 |
| 꺾쇠 `>` | 계층 관계 |

물결표(`~`)는 범위 표시에만 쓰고 어미 대용으로 쓰지 않는다. 느낌표와 이모지는 쓰지 않는다.

## 8. 체크리스트

**문체**
- [ ] 지시 문장은 `~한다` / `~하지 않는다`로 끝난다
- [ ] 문서 전체의 종결어미가 단정형으로 통일돼 있다
- [ ] 규칙과 근거가 한 줄에 이어 붙어 있지 않다
- [ ] `하시기 바랍니다`, `하십시오`, `하세요`가 없다
- [ ] `-시-`가 들어간 문장이 없다
- [ ] 목록 항목이 개조식이다

**간결성**
- [ ] 한 문장에 생각이 하나만 들어 있다
- [ ] 지웠을 때 뜻이 그대로인 말을 남기지 않았다
- [ ] `먼저`, `앞서 설명했듯이`, `물론`, `사실`이 없다
- [ ] 이중 부정이 없다

**번역투**
- [ ] `수행/진행/실시/처리`를 뺐을 때 뜻이 달라지지 않는 자리는 모두 뺐다
- [ ] `~을 통해`가 없다
- [ ] `당신`, `여러분`, `우리`가 없다
- [ ] 문장 끝에 콜론이 없다

**주체와 구체성**
- [ ] 각 문장의 주체가 드러난다
- [ ] 행동 지시에서 도구가 아니라 읽는 쪽이 주체다
- [ ] `적절히`, `가급적`, `너무`, `등`이 없다
- [ ] 조건을 그 자리에서 참·거짓으로 판정할 수 있다
- [ ] 금지 규칙이 금지형으로 쓰여 있다
- [ ] 예외가 명시되어 있다
- [ ] `아래`, `이 절`, `마지막 항목`에 가리키는 대상이 붙어 있다

**일관성**
- [ ] 같은 개념을 같은 단어로 부른다
- [ ] 한 목록 안의 항목 형태가 같다
- [ ] 외래어와 약어는 최초 언급 시에만 병기했다

**표기**
- [ ] 코드·경로·명령어에 고정폭 글꼴을 썼다
- [ ] 라틴 문자 뒤의 조사를 붙여 썼다 (`Phase를`, `ADR을`)
- [ ] `이전`, `다음` 대신 `위`, `아래`를 썼다
