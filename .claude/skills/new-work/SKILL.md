# work 파일 생성

**사용자가 `/new-work`로 호출할 때만 실행한다.** 대화 맥락만 보고 이 스킬을 먼저 꺼내지 않는다.
— 문제 정의를 사용자가 직접 시작해야 하는 절차다. 에이전트가 먼저 열면 1단계의 되묻기가 형식만 남는다.

**언제 쓰는가**: 며칠 걸리는 작업, 되물을 것이 셋 이상인 작업, 되돌리기 어려운 변경을 시작할 때.
**쓰지 않을 때**: 한 세션에 끝나는 작업. 이때는 work 파일을 만들지 않는다.
**산출물**: `docs/work/YYYY-MM-DD-{작업명}.md`, 커밋 2개, 작업 브랜치.

세 단계다. **순서를 지킨다.** 코드베이스는 3단계에서만 읽는다.
— 플랜 모드에서 코드를 많이 읽은 세션이 1단계를 쓰면 구현 가능성에 이끌려 문제를 축소한다. "지금 구조로는 어려우니 범위를 줄이자"가 문제 정의에 섞여 들어온다.

---

## 시작 전

`docs/NEXT.md`를 읽는다. 이 작업이 후보 목록에 있으면 「왜 지금」과 「완료 신호」를 1단계와 3단계의 재료로 쓴다.

`assets/work-template.md`를 `docs/work/YYYY-MM-DD-{작업명}.md`로 복사한다. 아래 세 단계는 이 파일을 채우는 절차다.

---

## 1단계: 왜 이 작업인가

- **도구**: 대화만. grilling 스킬이 있으면 사용한다
- **코드베이스**: 읽지 않는다
- **종료 조건**: 아래 다섯 가지에 모두 답이 나왔다

사용자에게 되묻는다. 한 번에 하나씩. 다섯 가지에 모두 답이 나올 때까지 멈추지 않는다.

1. 지금 무엇이 안 되는가 (해결책이 아니라 현상)
2. 나아진 상태는 어떤 모습인가 (구현 방법이 아니라 결과)
3. 어느 화면, 모듈, 데이터가 건드려지는가
4. 반드시 지켜야 할 것과 하지 말아야 할 것
5. 지금 답을 모르는 것

**5번을 비우지 않는다.**
— 사용자가 아직 정하지 않은 것을 드러내는 것이 1단계의 목적이다. 문서를 채우는 것이 목적이 아니다.

**사용자가 직접 읽고 고칠 때까지 2단계로 넘어가지 않는다.**

---

## 2단계: 결정

- **도구**: 대화. 선택지를 판별하는 데 필요한 파일만 읽는다. 전체 구조 파악은 3단계에서 한다
- **종료 조건**: 각 선택지에 채택 근거와 기각 근거가 붙는다

선택지가 하나뿐이면 「결정」 절을 만들지 않고 3단계로 간다.

선택지가 여럿이면 아래 형식으로 각각을 적는다.

```markdown
### <결정 제목>
**채택**: ...
**기각**: ... (왜 아닌지)
**근거**: ...
**틀렸다는 신호**: 무엇을 보면 이 결정이 틀렸다고 알 수 있는가
**승격**: ADR-00NN 또는 "없음"
```

규칙:

- 선택지는 같은 추상 수준에 둔다
- 동작하지 않는 선택지를 들러리로 세우지 않는다
- **「틀렸다는 신호」를 비우지 않는다**
  — 결정이 옳은지 지금 판단할 수 없어도, 무엇을 보면 틀렸는지는 지금 적을 수 있다

### ADR 승격 판단

기준은 하나다. 다음 작업을 할 때 이 결정을 다시 봐야 하는가.

- 봐야 한다 → new-adr 스킬로 ADR을 쓰고 「결정」 절에는 번호만 남긴다
- 안 봐도 된다 → 「결정」 절에 전문을 남긴다
- 애매하다 → 「결정」 절에 남긴다

---

### 커밋 1

```bash
git add docs/work/YYYY-MM-DD-{작업명}.md
git commit -F <메시지 파일>   # 📝 plan: {작업} 의도와 결정
```

**플랜 모드 진입 전에 커밋한다.**
— 코드를 읽기 전 상태를 고정하기 위해서다. 3단계를 다시 짜도 앞부분이 흔들리지 않는다.

- 예외: 1단계와 2단계가 30분 안에 끝났으면 커밋 2와 합친다. 플랜 모드 진입 전이라는 경계는 그대로 지킨다

## 3단계: 위험 요소, 증명, Phase

- **도구**: 플랜 모드(`Shift+Tab`). 파일을 읽되 고치지 않는다
- **종료 조건**: 이 대화를 한 번도 본 적 없는 사람이 계획만 보고 구현할 수 있다

### 3-1. Phase 목록

작업을 Phase로 묶고 각 Phase를 항목으로 나눈다. 바뀌는 파일 경로를 항목에 적는다.

### 3-2. 계획을 심문한다

아래 세 가지를 묻고 답을 「위험 요소」 절에 적는다.

```
이 계획에서 뭐가 깨질 수 있어?
어느 Phase가 가장 위험해?
고려했지만 하지 않기로 한 다른 방법이 있었어?
```

**세 답에서 새로 나온 것이 하나도 없으면 다시 묻는다.**
— 새로 나온 것이 없다는 것은 계획이 아직 얕다는 신호다.

### 3-3. 「증명」을 채운다

각 Phase 완료를 무엇으로 확인하는지 **실행 가능한 검사**로 적는다.

- 테스트가 있는 영역: 어느 테스트가 통과해야 하는가
- 테스트가 없는 영역: 빌드 통과와 눈으로 확인할 대상

**「증명」을 작업이 끝난 뒤에 채우지 않는다.**
— 미리 정해 두는 것이 「증명」 절의 존재 이유다.

### 3-4. tech-debt 확인

`docs/tech-debt.md`에서 이 작업이 건드리는 파일의 D-NN 항목을 찾아 프론트매터 `관련:`에 적는다.
— 같은 자리를 두 번 열지 않기 위해서다.

---

### 커밋 2

```bash
git commit -F <메시지 파일>   # 📝 plan: {작업} 실행 계획
```

**브랜치를 파기 전, `main`에서 커밋한다.**
— 브랜치를 버려도 계획이 남는다.

그다음 브랜치를 판다.

```bash
git checkout -b '#<issue>-<Topic>'
```

## 세션이 끊겼을 때

프론트매터 `상태:`와 채워진 절로 판단한다.

| 채워진 곳 | 다음 단계 |
| --- | --- |
| 「왜 이 작업인가」만 있음 | 2단계 |
| 「결정」까지 있고 커밋 1이 있음 | 3단계 |
| Phase까지 있고 커밋 2가 있음 | 구현 |
