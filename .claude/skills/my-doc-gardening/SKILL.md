# 문서 gardening

문서를 두 축으로 리뷰한다.

- **드리프트**: 문서의 주장이 지금의 코드, 환경, GitHub 상태와 맞는가
- **정책**: 문서가 이 저장소의 문서 규칙(담을 것, 양식, 상호 참조)을 지키는가

두 축은 서로 다른 서브에이전트가 맡고, 리포트에서도 합치지 않는다. 한 축이 통과해도 다른 축이 실패할 수 있다.
문체는 이 스킬이 보지 않는다. 문체가 걸리면 리포트 끝에서 `/korean-md-style`을 권한다.

## 대상 문서

| 묶음 | 보는 것 |
|---|---|
| `CLAUDE.md`, `CONTEXT.md`, `docs/` 바로 아래, `docs/agents/` | 두 축 전부 |
| `docs/work/` | 두 축 전부. 「기록」은 그때의 서술이라 드리프트로 올리지 않는다 |
| `.claude/skills/*/SKILL.md` | 두 축 전부 |
| `docs/adr/` | 두 축 전부. 본문은 고치지 않고 날짜를 적은 덧붙임을 수정안으로 낸다 |
| `docs/reports/` | 규범 문서로 옮기지 않은 결론이 남았는지만 본다 |
| `docs/references/` | 보지 않는다 |

## 1. 대상을 확정한다

인자에 따라 기준을 정한다.

| 인자 | 기준 |
|---|---|
| 없음 | `git merge-base origin/dev HEAD` |
| `<ref>` | 그 ref와 `HEAD`의 merge-base |
| `--all` | 기준 없음. 위 표의 대상 문서 전부 |
| 문서 경로 | 그 문서들만 |

기준이 있으면 서브에이전트를 띄우기 전에 아래 두 가지를 확인한다. 하나라도 실패하면 이유를 말하고 끝낸다.

- `git rev-parse <기준>`이 성공한다
- `git diff <기준>...HEAD --name-only`가 비어 있지 않다. 비어 있으면 `--all`이나 다른 ref를 쓰라고 안내한다

바뀐 파일 목록에서 대상 문서를 고른다.

1. 바뀐 파일 중 대상 문서에 속하는 것
2. 바뀐 코드 파일의 경로, 파일 이름, 그 diff에서 이름이 바뀌거나 지워진 심볼을 대상 문서 본문에서 찾았을 때 나오는 문서
3. 바뀐 파일이 `.github/workflows/`, `P1/Scripts/`, `Tools/`, `.claude/` 아래에 있으면 `CLAUDE.md`, `docs/build.md`, `docs/testing.md`

고른 문서 목록과 각 문서가 뽑힌 이유를 사용자에게 보여 준다.
완료 기준: 목록의 문서마다 위 세 경로 중 어느 것으로 뽑혔는지 적혀 있다.

## 2. 기계 검사를 돌린다

```
py -3 Tools/DocLint/check_docs.py --self-test
py -3 Tools/DocLint/check_docs.py
```

자기 검증이 실패하면 기계 검사 결과를 쓰지 않고 그 사실을 리포트 맨 위에 적는다.
기계 검사는 저장소 전체를 보므로, 대상 문서에 속한 위반만 리포트로 가져간다. `--all`이면 전부 가져간다.

## 3. 두 축을 병렬로 리뷰한다

서브에이전트 둘을 한 메시지에서 함께 띄운다. 두 프롬프트에 공통으로 넣는 것은 아래 다섯 가지다.

- 대상 문서 목록
- 기준과 diff 명령(`git diff <기준>...HEAD`). `--all`이나 경로 인자면 「기준 없음」
- 판정 기준 파일의 경로와, 그 파일을 처음부터 끝까지 읽으라는 지시
- 2단계의 기계 검사 결과 전문과, 거기 나온 위반은 다시 올리지 말라는 지시
- 아래 「발견 형식」 절

| 축 | 판정 기준 파일 |
|---|---|
| 드리프트 | `.claude/skills/my-doc-gardening/references/drift-criteria.md` |
| 정책 | `.claude/skills/my-doc-gardening/references/policy-criteria.md` |

### 발견 형식

서브에이전트는 발견마다 아래 여섯 가지를 적는다. 600단어를 넘기지 않는다.

1. 파일 경로와 줄 번호
2. 규칙 ID (판정 기준 파일의 표 첫 열)
3. 원문 인용
4. 근거: 드리프트는 실행한 명령과 그 결과, 정책은 어긴 규칙의 출처
5. 수정안: 바꿀 문장 그대로. 지우는 것이 맞으면 「삭제」
6. 확신: **확정**(근거로 참·거짓이 갈린다) 또는 **판단 필요**(사람이 정할 문제)

확정이 아닌 것을 확정으로 올리지 않는다. 판단 필요로 올리고 무엇을 정해야 하는지 한 줄로 적는다.

## 4. 리포트를 낸다

아래 형식을 그대로 쓴다. 번호는 세 절을 통틀어 이어 매긴다. 축 사이에서 항목을 합치거나 순위를 다시 매기지 않는다.

```markdown
## 문서 gardening 결과

기준: <기준 또는 「--all」> · 대상: <문서 수>개 · 기계 <N>건 · 드리프트 <N>건 · 정책 <N>건

## 기계 검사

| # | 파일 | 줄 | 검사 | 문제 |
| --- | --- | --- | --- | --- |
| 1 | docs/codegen.md | 40 | section-ref | docs/build.md에 「생성 순서」 절이 없다 |

## 드리프트

| # | 파일 | 줄 | 규칙 | 확신 | 문제 |
| --- | --- | --- | --- | --- | --- |
| 2 | docs/testing.md | 52 | D4 | 확정 | 스위트 수를 8개로 쓰지만 12개다 |

### 2 · docs/testing.md 52행 · D4 · 확정

원문:
> 게임 서버 L1 스위트는 8개다.

근거: `Server/GameServerTests/`의 `*Tests.cpp`가 12개다(`git ls-files 'Server/GameServerTests/*Tests.cpp'`).

수정안:
> 게임 서버 L1 스위트는 12개다.

## 정책

(드리프트와 같은 형식)

## 판단이 필요한 것

- (확신이 「판단 필요」인 항목의 번호와 정해야 할 것)
```

기계 검사 항목의 수정안은 상세 절 없이 표만 둔다. 고칠 자리가 메시지에 드러난다.

## 5. 승인을 받는다

번호로 고르게 묻는다. 예: 「1~4번, 7번을 적용할까?」, 「확정만 적용할까?」
**승인 없이 파일을 고치지 않는다.**
— 문서 수정은 다음 세션의 판단을 바꾼다. 리포트에 없던 변경이 섞이면 무엇이 바뀌었는지 추적할 수 없다.

## 6. 승인된 것만 고친다

- 승인된 번호만, 수정안에 적힌 그대로 고친다
- ADR은 본문 문장을 고치지 않는다. 해당 절 끝에 `**YYYY년 M월 D일 덧붙임 — 요지.**`로 시작하는 문단을 더한다
- 정보를 지우는 수정안은 승인된 경우에만 지운다
- 현재 작업 트리에 고치고 커밋하지 않는다
- 고친 뒤 `py -3 Tools/DocLint/check_docs.py`를 다시 돌려 새 위반이 생기지 않았는지 확인한다

## 7. 결과를 보고한다

- 고친 파일과 항목 번호
- 적용하지 않은 항목과 이유 한 줄
- 6단계에서 다시 돌린 기계 검사의 위반 건수와 종료 코드
- 문체 문제가 눈에 띈 문서가 있으면 `/korean-md-style` 진단을 권한다
